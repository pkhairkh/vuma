## Validation Methodology

For each module, the following line-by-line comparison was performed:

1. **Vector file integrity check**: For each of the 20 test vectors in the module's
   `test_results/standard_vectors/<module>.json`, the expected output was recomputed
   from the input using the Python reference library. All recomputed references were
   confirmed to match the JSON vector `expected_hex` field.

2. **VUMA harness compilation**: Each `test_<module>_b<N>.vuma` harness (4-7 per module,
   depending on the number of vectors per batch) was compiled using the standalone
   `compile_dump` compiler targeting x86_64 with `--no-verify` (skipping IVE PMT
   verification to focus on functional correctness).

3. **VUMA harness execution**: Each compiled binary was executed, producing output in
   the form `1000+byte` values separated by `999` record separators.

4. **Output comparison**: The VUMA output bytes were parsed, grouped into records
   (one per test vector), and compared byte-for-byte against the reference
   `expected_hex`. For modules with multi-record output (e.g. ECDSA sign produces
   r || s as two records), all records from one harness were concatenated to form
   the comparison value.

5. **Status reporting**: A module is marked PASS only if ALL 20 vectors match the
   reference byte-for-byte. Otherwise it is marked PARTIAL or FAIL.

## Known Issues (Not Fully Resolved)

### 1. ecdsa_p384 (0/20)
- **Symptom**: Produces 192-byte r||s output but bytes don't match expected.
- **Fix applied**: Alias-safe local temporaries in `p384_point_double_bn` (commit 47dddde5),
  same pattern as the ecdsa_p256 fix (commit 987fd6be).
- **Remaining issue**: Deeper arithmetic bug in bn384_mod_mul or bn384_mod_inv_fermat.
- **Suggested next step**: Compare intermediate values (slope, slope_sq, rx, ry) with
  Python cryptography's ECDSA P-384 to find the divergence.

### 2. falcon (0/20)
- **Symptom**: Verify returns 0 (failure) for all valid signatures.
- **Root cause**: The simplified verify body doesn't decompress standard Falcon-512
  pk/sig format or implement NTT.
- **Suggested fix**: Implement full Falcon-512 per FIPS 206 (NTT + decompression +
  hash-to-point). This is a large implementation effort (~2000 lines of VUMA).

### 3. ml_dsa (0/20)
- **Symptom**: Verify dumps core (SIGABRT exit 134 = arena overflow).
- **Root cause**: The `MlDsaBuf` layout (65536 bytes) is allocated many times inside
  `ml_dsa_verify`, exceeding the arena limit.
- **Suggested fix**: Reduce the number of `state_new(MlDsaBuf)` calls by reusing
  buffers, or increase the arena size limit.

### 4. hqc (0/20)
- **Symptom**: Produces 128-byte output but bytes don't match expected.
- **Root cause**: Decaps logic bug — first 32 bytes have data, last 32 are zeros.
- **Suggested fix**: Debug the decaps path against pqcrypto HQC-192 reference.

### 5. slh_dsa (0/20)
- **Symptom**: Verify returns 0 (failure) for all valid signatures.
- **Root cause**: The sign/verify bodies are simplified (return 0 / no-op).
- **Suggested fix**: Implement full FIPS 205 (SLH-DSA-SHA2-128s): WOTS+, FORS,
  hypertree. This is a very large implementation effort (~3000+ lines of VUMA).

### 6. rsa_pkcs1_ecdsa_extra (N/A)
- **Symptom**: No test harnesses exist.
- **Root cause**: The module contains stubs for Ed448 and P-521 (return 0).
- **Suggested fix**: Implement Ed448 (RFC 8032) and P-521 ECDSA, then generate
  harnesses and test vectors.
