## 1. What VUMA actually is (the mental model v1 lacked)

VUMA is not "a systems language with some verification tacked on."
It is a **verification-first systems language** where the entire
architecture is shaped by the verification discipline. Three
architectural facts that the v1 draft missed:

### 1.1 Two-SCG architecture

VUMA has **two parallel SCGs** that serve different consumers:

1. **Semantic SCG** (`vuma_scg::graph::SCG`, produced by
   `parser::to_scg::AstToScg`) — consumed by IVE. Carries
   `NodePayload` variants like `StateReadNode`, `StateWriteNode`,
   `StateTransformNode` with layout/field name metadata for the
   verifiers.

2. **Codegen SCG** (`vuma_codegen::scg_to_ir::Scg`, built by
   `pipeline::bridge_ast_to_codegen_scg_with_meta`) — consumed by
   codegen. Carries `ScgStatement` variants with typed-state
   information for IR lowering.

The two are bridged by `VerificationInput::typed_state_meta` (a
`Vec<TypedStateMeta>` populated by the pipeline) and a **hard-gate
cross-check** `verify_typed_state_conformance` that promotes to
`VerificationStatus::Violated` if the two disagree. This is documented
in the `src/ive/src/verification.rs` file-level docstring.

**Implication for the catalog**: bugs in the codegen-side bridge
functions (`bridge_type_to_ir_type`, `bridge_type_size`) affect
CODEGEN, not IVE. Bugs in the parser-side `type_size_from_name` affect
the SEMANTIC SCG, which IVE consumes — but IVE's `PmtLayoutSpec` table
is built by `build_pmt_layout_specs` (codegen-side), not by the
parser-side `register_layout`. The two paths are independent.

### 1.2 The `__oob_trap` runtime bounds check is structural

VUMA's memory-safety story is **defense in depth**:

1. **Compile-time (Z3)**: IVE emits `contract_assert(off + size ≤
   layout.total_size)` for every `state.field` access. Z3 discharges
   or the pipeline hard-fails.
2. **Runtime (`__oob_trap`)**: `inject_bounds_check_ir` in
   `src/codegen/src/memory_safety.rs` emits a `UGe` bounds check
   before every arena-allocated access. On failure, calls
   `__oob_trap` which exits with code 134 (SIGABRT).
3. **Lean (formal spec)**: `pmt_soundness` + `no_oob_trap_for_well_typed_strong`
   prove that well-typed-strong programs never trap with `.oob`.

**Implication for the catalog**: a "wrong IRType" bug (V-34, V-36) is
NOT necessarily a memory-safety bug. If the runtime bounds check uses
the LAYOUT's size (not the IRType's size), then loading 8 bytes when
the field is 4 bytes is a PERFORMANCE issue (loads 4 extra bytes that
get discarded), not a CORRECTNESS issue. F-1 verified that
`classify_pointer` in `memory_safety.rs` returns `Safe` on
`offset: None`, meaning the runtime check is structurally incapable of
catching V-34/V-36 — but the LAYOUT-based check (via IVE's
`StateReadVerifier`) does catch genuine OOB. The wrong-IRType bug
produces wrong ARITHMETIC (integer ADD instead of float ADDSD), not
wrong MEMORY ACCESS.

### 1.3 The Lean proof layer is substantial

A-3 read `Basic.lean` and `PmtInstr.lean` and concluded the Lean
layer is "purely memory-safety, only `alloc_preserves_capacity` via
`omega`." F-2 read the full `proof/` tree and found:

- **82 Lean files** (not "20+ modules")
- **280 theorems** (not "~90 theorems")
- **0 actual `sorry` tokens** (the language-reference.md §10 "2
  sorries" claim is stale — verified by `grep -rn 'sorry' proof/`)
- **Real Iris separation-logic layer** in `proof/PMT/Iris/` (9 files):
  `CapBndInvariant.lean`, `LiveMirrorInvariant.lean`,
  `GuardInvariant.lean`, `Composition.lean` (the
  `alloc_preserves_pmt_invariants` theorem over
  `[cap_bnd] ∗ [live_mirror] ∗ [guard]`, sorry-free), `HeapModel.lean`,
  `FractionalPerm.lean`, `SepGenuine.lean`, `WeakestPrecond.lean`,
  `ArenaRes.lean`
- **Faithful Lean↔Rust simulation** in `proof/PMT/Faithful/` (22
  files): `Model.lean`, `Simulation.lean`, `SimSound.lean`,
  `SimTransform.lean`, `SimWrite.lean`, `RustConformance.lean`,
  `UafProof.lean`, `OverflowProof.lean`, etc.
- **`BitVecArena.lean`** — fixed-width usize overflow model (more
  faithful than `Nat`)
- **`MmapArena.lean`** — allocator-failure model (`MAP_FAILED` paths)
- **`PipelineSim.lean`** — Lean↔Rust simulation refinement (`SimRel`)
- **`WellTypedStrong.lean`** — strengthened well-typedness predicate
  with `DataflowOk` + per-step `FieldBounds`
- **`RawArena.lean`** — 6-field Arena model (the primary faithful
  model; includes `layout` and `created_thread` that A-3 claimed were
  "not modeled anywhere in Lean")

**Implication for V-14**: the f32 PMT proof is NOT greenfield. The
existing `BitVecArena` + Iris layer provides a foundation. The missing
piece is an f32 bit-pattern model on top of `BitVec 32` and
`verified_float_add` runtime checks. F-2 estimates 2-4 weeks for a
bit-pattern model, 2-3 months for full IEEE-754 — not the 3-6 months
A-3 claimed.

### 1.4 The capability model is compile-time-only by design

A-3 framed `verify_capability` being "never called from emitted
binaries" as security theater. F-2 verified that this is actually the
**correct design** for VUMA's threat model:

- `capability_grant` / `capability_delegate` (in `ipc_lowering.rs`)
  expand at COMPILE TIME to token MINTING. The signing key, signature,
  and delegation chain are compile-time-only artifacts.
- Only the `cap_id` (low 64 bits) survives into the emitted binary, as
  `BinOp(Add, cap_id_immediate, 0)`.
- The IVE is supposed to verify the signature at compile time — but
  F-2 found that IVE's `l1l3_collapse` has `let known = true;` (a
  dead branch, A-3's V-A3-6) that folds 1 L2 check per
  `Intrinsic`-tagged node WITHOUT actually verifying any signature.

**Revised framing**: V-16 is NOT "verify_capability is never called."
It is "the IVE capability verifier is a stub (`let known = true`), so
the compile-time check that SHOULD happen doesn't." This is a real P0
security gap (V-A3-2: hardcoded `b"vuma_dev_signing_key"`), but the
framing is different — the fix is to wire the IVE verifier, not to add
runtime checks to emitted binaries.

## 3. What VUMA gets RIGHT (that v1 framed as bugs)

This section is the most important correction. The v1 draft, by
pattern-matching on `_ =>` arms without understanding the
architecture, framed several correct-by-design choices as bugs.

### 3.1 `contains_fork` opt-out is a correctness requirement

**v1 (V-A2-9)**: "regalloc doesn't model syscall arg/dst interference —
root cause of the `contains_fork` opt-out (which is correct but
over-conservative)."

**Reality (F-3)**: `resolve_register_reuse_conflicts` at
`regalloc.rs:2836-2897` EXPLICITLY models the syscall arg/dst
interference case. `architecture.md` §7.3 directly cites
`IRInstr::Syscall` as "the classic case." The `contains_fork` opt-out
is a **documented correctness requirement** for `clone(2)`/`vfork(2)`:
the child process's register state diverges from the parent's at the
syscall return, which is incompatible with the register-based
prologue/epilogue. The stack-slot path is used because every vreg
lives in its own stack slot, so the child's divergent register state
is irrelevant.

The opt-out was NARROWED in v0.2.0-alpha.10 (commit `bb0c2f24`) from
a broad "syscall-hazard fallback" to only `clone`/`fork` — coupled
with the addition of `resolve_register_reuse_conflicts`. The W4-fix
broadening A-2 cited is a STALE COMMENT.

**Action**: Drop V-A2-9 from the catalog. Document `contains_fork` as
a correct design decision in the ADR that covers regalloc.

### 3.2 The two-SCG architecture is intentional

**v1**: treated the codegen-side bridge functions as the only path.

**Reality (F-1)**: IVE runs on the semantic SCG; codegen runs on the
codegen `Scg`. The two are bridged by `typed_state_meta` +
`verify_typed_state_conformance` hard-gate. Bugs in the codegen-side
bridge affect codegen; bugs in the parser-side `type_size_from_name`
affect the semantic SCG. The two paths are independent, and the
hard-gate cross-check catches disagreements.

**Action**: ADRs that touch bridge functions must specify WHICH SCG
they affect. V-34/V-36 are codegen-side; V-35/V-42/V-44 are
parser-side (semantic SCG); V-03/V-NEW-2 are IVE-side
(`PmtLayoutSpec` table).

### 3.3 The Lean proof layer is not "purely memory-safety"

**v1 (V-14)**: "f32 PMT Lean proof is greenfield — there is no
existing arithmetic-verification infrastructure to extend."

**Reality (F-2)**: 82 Lean files, 280 theorems, 0 `sorry` tokens.
Real Iris separation-logic layer (`proof/PMT/Iris/`). Real Lean↔Rust
simulation refinement (`proof/PMT/PipelineSim.lean`). Real overflow
model (`proof/PMT/BitVecArena.lean`). Real allocator-failure model
(`proof/PMT/MmapArena.lean`). The f32 extension builds on
`BitVecArena`, not on `Nat`.

**Action**: Revise ADR-0006. The f32 PMT proof is NOT greenfield. The
defer-to-v2 decision still stands (v1 ships with runtime
`__float_overflow_trap` only), but the v2 effort estimate drops from
3-6 months to 2-4 weeks (bit-pattern model) or 2-3 months (full
IEEE-754).

### 3.4 The capability model is compile-time-only by design

**v1 (V-16)**: "`verify_capability` is never called from emitted
binaries — the capability model is write-only (security theater)."

**Reality (F-2)**: This is the CORRECT design. Capabilities are
minted and signed at compile time; only the `cap_id` (low 64 bits)
survives into the emitted binary. The IVE is supposed to verify the
signature at compile time — but the IVE verifier is a STUB
(`let known = true` at `verification.rs:2379`, V-A3-6).

**Action**: Revise ADR-0007. The fix is NOT "wire `verify_capability`
into emitted binaries" (wrong layer). The fix is "wire the IVE
capability verifier to actually check signatures instead of
`let known = true`." The HMAC-SHA256 migration (V-16) and the
hardcoded-key fix (V-A3-2) remain valid.

### 3.5 Per-backend QEMU workarounds are not VUMA bugs

**v1**: listed alpha/m68k/hppa/riscv32 among the "weakest backends"
implying VUMA bugs.

**Reality (F-3, `caveats.md` §2.4)**: These backends have KNOWN QEMU
translator bugs that VUMA's encoder works around:
- `alpha` CMPULE → CMPULT emulation (QEMU 10.0 bug, real hardware OK)
- `m68k` QEMU 7.2 TCG bugs (QEMU 8.x/10.x fixes them)
- `hppa` QEMU 7.2 LDIL/BL decoder bugs (QEMU 8.x fixes them)
- `riscv32` QEMU default CPU lacks D extension (requires `-cpu max`)

**Action**: ADR-0009 (re-run test suite) must use QEMU 10.0+ to avoid
re-flagging these as VUMA bugs.

### 3.6 The `Effect` enum is decorative but not a bug

**v1 (V-A3-7)**: framed as a bug ("Effect enum is dead code — IVE has
zero references").

**Reality (F-1)**: Confirmed dead. `analyze_program_effects` is called
at `pipeline.rs:4431`, result used ONLY for a `vuma_log!(debug)`
pure-count. The optimizer uses its own `has_side_effects` at
`opt.rs:527`. IVE has zero references.

**Action**: This is a cleanup decision (wire-vs-delete), not a bug.
Demote to P3. The decision depends on whether V-02 (rendering IR
instructions) lands — if yes, wire it; if no, delete it.

## 6. Open questions (revised)

1. **Should V-34/V-36 be fixed at all if the production path doesn't
   use them?** F-1 found V-36 fires only for test/deserialized SCGs.
   V-34 affects only scalar f32 state fields (arrays are fine via
   `resolve_state_array_access`). The fix is cheap (1-line + 1-line),
   so probably yes — but the urgency is P2, not P0.

2. **Should the unified `VumaType` refactor happen?** v1 said it would
   eliminate 8 P0 bugs. v2 says those 8 bugs are mostly P2 and live
   in non-production paths. The refactor is still architecturally
   correct but no longer urgent.

3. **What's the right QEMU version for the test suite?** F-3 found
   QEMU 7.2 has known translator bugs that VUMA works around. ADR-0009
   should mandate QEMU 10.0+ to avoid re-flagging QEMU bugs as VUMA
   bugs.

4. **Should the IVE capability verifier be wired (V-16) or should the
   capability model be deleted entirely?** If VUMA doesn't ship
   capability-checked host imports in v1, the stub verifier is
   harmless. If it does, V-16 is P0. This is a product decision, not
   an engineering one.

5. **Is the `discharge_rate` metric worth fixing (V-A3-3)?** The
   correct `pass_rate()` method exists on `VerificationSummary` —
   `compile_dump.rs` just doesn't call it. 3-line fix, but the metric
   is published in every compile summary, so the impact is visible.
