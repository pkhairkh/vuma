# ADR-0005: Delete unused build-dependencies and legacy `bridge_type_size`

- **Status**: Accepted
- **Date**: 2026-08-01
- **Decision Maker**: VUMA compiler team

## Context

The VUMA workspace has a "small-deps" policy: every external crate must earn its
place. A-4's dependency audit (`research/A-4-pipeline-runtime-tests-deps.md`
§2 "Dependency manifest") found that the workspace currently carries 8 external
crates in `Cargo.lock` — 3 declared + 5 transitive. One declared crate,
`cc 1.4.0`, is dead code.

The `cc` build-dependency is declared in the **root** `Cargo.toml:67-75`
(not in `src/codegen/Cargo.toml` — the task brief mislocated it; the codegen
crate has no `[build-dependencies]` section at all, see
`src/codegen/Cargo.toml:1-32`):

```toml
# Cargo.toml (root), lines 67-75
[build-dependencies]
# HISTORICALLY used by build.rs to compile the Lean-extracted (or stub) C
# archive into the vuma binary when the `pmt-runtime-check` feature was
# enabled. The Lean FFI bridge has been REMOVED (see build.rs file-level
# doc ...); build.rs no longer compiles any C. The `cc` dependency is
# retained unconditionally so the workspace still builds in one shot if a
# future change reintroduces a C build step.
cc = "1"
```

The comment itself admits the dependency is retained "so the workspace still
builds in one shot if a future change reintroduces a C build step" — i.e., as
speculative future-proofing, not because anything currently calls `cc::Build`.

The root `build.rs` confirms the dependency is unused. Its file-level doc
(`build.rs:6-9`) states: *"Lean FFI bridge removed. Z3-based contract
discharge replaces it. PMT state verification uses hand-written Rust
verifiers."* The actual `main()` at `build.rs:55-69` performs only two actions:
(a) detect the `rustc` version and emit `RUSTC_VERSION_{MAJOR,MINOR,PATCH}`
env vars (`build.rs:71-105`), and (b) declare the `lean_ffi_linked` cfg via
`cargo::rustc-check-cfg` so legacy `#[cfg(lean_ffi_linked)]` references in
`tests/*.rs` stay lint-clean (`build.rs:66`). **There is no `cc::Build`
invocation anywhere in `build.rs`.** The cfg is declared but never emitted
(`build.rs:46-51`).

`cc 1.4.0` drags in two transitive crates — `find-msvc-tools 0.1.9`
(Windows-only MSVC locator) and `shlex 2.0.1` (shell-quoting helper for cc's
command-line) — both of which die with `cc` (A-4 §2 "Full external dependency
inventory"). Removing `cc` therefore drops the external-crate count from 8 to 5
(only `bitflags` + the `z3`/`z3-sys`/`pkg-config`/`log` cluster remain).

Independently, V-40 (catalog §"P2 — Cleanup and coverage", verified by A-4 at
`research/A-4-pipeline-runtime-tests-deps.md` §1 "V-40") notes that the legacy
`bridge_type_size` function at `src/pipeline.rs:6532` will become dead code
once V-03 lands. A-4's caller inventory (`research/A-4-pipeline-runtime-tests-deps.md`
§1 "V-03 / V-40 — Legacy `bridge_type_size`...") is exact:

| Caller | File:line | Status |
|---|---|---|
| `bridge_type_size` self-recursion on `Type::Array` | `src/pipeline.rs:6547` | internal — dies with the function |
| `build_pmt_layout_specs` field size lookup | `src/pipeline.rs:6724` | **the V-03 bug site** — migrates to `bridge_type_size_with_layouts` per ADR-0004 |

A grep for `bridge_type_size\b` (word-boundary, excluding `_with_layouts` and
comments) across `src/` returns only those two hits — zero external callers
once `:6724` migrates. The legacy function is also referenced in three stale
doc comments in `src/ive/src/verification.rs:247, 255, 295` (citing
`pipeline.rs:8669`, which is wrong — the actual line is `:6532`); these doc
refs need updating regardless.

The fixed variant `bridge_type_size_with_layouts` at `src/pipeline.rs:6557`
already exists and consults a `layout_sizes: &HashMap<String, u64>` table for
user-defined layout names. ADR-0004 (V-03) migrates `build_pmt_layout_specs`
to call it; this ADR removes the now-dead legacy function so the V-03 bug
class cannot regress.

## Decision

1. **Remove the `cc` build-dependency.** Delete the `[build-dependencies]`
   section at `Cargo.toml:67-75` (the whole section — `cc` is its only entry).
   The `build.rs:55-69` `main()` function does not call `cc::Build` and is
   unaffected. No code change in `build.rs` is required beyond the
   file-level doc-comment tidy-up at `build.rs:11-44` (the "History" block
   can be shortened to a one-line note that the Lean FFI bridge was removed
   and `cc` is no longer needed).

2. **Delete the legacy `bridge_type_size` function** at
   `src/pipeline.rs:6530-6550` (the `///` doc comment + the 19-line `fn`
   body) **after ADR-0004 (V-03) lands** and `build_pmt_layout_specs:6724`
   has migrated to `bridge_type_size_with_layouts`. The self-recursive
   `Type::Array` arm at `:6547` dies with the function — no orphaned
   reference remains.

3. **Update the three stale doc-comment references** in
   `src/ive/src/verification.rs:247, 255, 295` to point at
   `bridge_type_size_with_layouts` (`src/pipeline.rs:6557`) instead of the
   deleted `bridge_type_size`. While we're here, correct the wrong line
   number `pipeline.rs:8669` to `pipeline.rs:6557`.

4. **Regenerate `Cargo.lock`** via `cargo update` so the `cc`,
   `find-msvc-tools`, and `shlex` entries disappear. Verify with
   `cargo tree | grep -E 'cc|find-msvc-tools|shlex'` that no stragglers
   remain.

5. **Run the full test suite** (`just test` or
   `scripts/pi5_test_suite.sh`) to confirm 93.42% pass rate is unchanged
   — this is a pure deletion, so the pass rate must not move.

## Consequences

### Positive

- External crate count drops from 8 → 5 (3 declared → 2 declared; 5
  transitive → 3 transitive). Only `bitflags` and the `z3` cluster
  (`z3`/`z3-sys`/`pkg-config`/`log`) remain. This is the leanest the
  workspace has been since the Wave-43 serde/toml purge.
- `cargo clean && cargo build` is faster (no `find-msvc-tools`/`shlex`
  compilation) and `Cargo.lock` shrinks by ~15 lines.
- The V-03 catch-all bug class (`_ => 8` for user-defined layout names)
  cannot regress: the only `bridge_type_size` variant that remains is
  `bridge_type_size_with_layouts`, which has no catch-all and requires a
  `layout_sizes` table.
- The `build.rs` doc-comment stops lying about "Lean FFI bridge" linkage
  that was removed; the spec/impl divergence flagged by A-3 as V-A3-4
  (lean-rust-parity.yml tests non-existent FFI bridge) becomes easier to
  reason about because `build.rs` no longer retains speculative C-build
  infrastructure.
- Reviewers reading `Cargo.toml` no longer see a `[build-dependencies]`
  section whose own comment admits it's dead-code policy.

### Negative

- If a future change reintroduces a C build step (e.g., linking a verified
  float library per ADR-0006 Alternative B, or re-adding a Lean C-extraction
  FFI bridge), `cc` must be re-added to `[build-dependencies]`. This is a
  1-line `Cargo.toml` change — re-adding is trivial. The cost of
  re-addition is vastly smaller than the cost of carrying speculative dead
  weight through every clean build.
- Anyone with a stale `Cargo.lock` checked out locally will get a one-time
  `cargo update` diff. Document this in the PR description.
- The legacy `bridge_type_size` is referenced by name in two `.vuma`
  source files (`womb/kernel/ipc/pipe.vuma:102, 135, 149` and
  `womb/kernel/ipc/shm.vuma:296-297`) — but only in comments, not in
  code. Those comments become stale; either update them to reference
  `bridge_type_size_with_layouts` or leave them as historical markers.

### Neutral

- The `lean_ffi_linked` cfg declaration at `build.rs:66` stays (it's still
  referenced by `tests/*.rs` via `#[cfg_attr(not(lean_ffi_linked), ...)]`).
  Only the `cc` invocation that historically *would have* emitted the cfg
  is gone — and it was already gone before this ADR.
- `Cargo.lock` line count drops from ~140 to ~125. Negligible but tidy.

## Alternatives Considered

### Alternative A: Keep `cc` for future C FFI

The `Cargo.toml:73-74` comment ("retained unconditionally so the workspace
still builds in one shot if a future change reintroduces a C build step") is
the YAGNI anti-pattern: pay a recurring cost (compile `cc` + `find-msvc-tools`
+ `shlex` on every clean build, larger `Cargo.lock`, reviewer confusion)
to avoid a one-time cost (re-add `cc = "1"` to `Cargo.toml` when actually
needed). Re-adding a build-dep is a 1-line change in a single file; the
speculative retention has no offsetting benefit. **Rejected.**

### Alternative B: Mark `bridge_type_size` `#[deprecated]` instead of deleting

A `#[deprecated(note = "use bridge_type_size_with_layouts instead")]`
attribute on the legacy function would let the function linger in the
source tree as a footgun-with-a-warning. Problems:

1. The V-03 bug class is a *correctness* bug (`_ => 8` for user-defined
   layouts), not a style issue. A `#[deprecated]` attribute doesn't
   prevent the bug from regressing — it only complains at compile time
   if a caller exists. Once V-03 lands and `:6724` migrates, there are
   zero callers, so `#[deprecated]` would emit no warnings and provide
   zero protection against a future contributor re-introducing a caller.
2. The function would remain in the public surface area of `pipeline.rs`
   indefinitely, inviting exactly the misuse the V-03 fix is meant to
   prevent.
3. The two-line grep-based audit ("does `bridge_type_size\b` still exist
   in `src/`?") becomes a one-line audit only if the function is deleted.

Deleting the function makes the audit trivial and the regression
impossible. **Rejected.**
