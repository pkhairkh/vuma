# ADR-0026: Vulkan Host Layer for GPU Compute

- **Status**: Accepted
- **Date**: 2026-08-04
- **Decision Maker**: VUMA project lead
- **Supersedes**: (none)
- **Superseded by**: (none)

## Context

ADR-0022 established that VUMA's GPU path uses pre-compiled SPIR-V
embedded as const byte arrays (V-26 Phase 2). The SPIR-V bytecode is
passed to the host runtime, which dispatches it to the GPU via Vulkan
(Linux/Windows) or Metal (macOS).

This ADR documents the Vulkan host layer implementation: the C shim
that wraps libvulkan.so and exposes the `vk_*` functions declared in
`womb/ui/render/gpu_dispatch.vuma`.

## Decision

**The Vulkan host layer is a thin C shim (`gpu_vulkan.c`) that wraps
libvulkan.so and provides a compute-pipeline dispatch API.**

### Architecture

```
VUMA program (womb/ui/render/gpu_dispatch.vuma)
  ↓ calls vk_* extern "C" functions
gpu_vulkan.c (C shim, wraps libvulkan.so)
  ↓ calls Vulkan API
libvulkan.so (OS-provided, Mesa lavapipe on Linux CPU, GPU drivers)
  ↓ dispatches to GPU
GPU execution
```

### Key design decisions

1. **Headless compute-only**: No surface, no swapchain, no graphics
   pipeline. Suitable for compute shaders and offscreen rendering. The
   3D mesh rendering path (vertex/fragment pipeline) requires a graphics
   pipeline, which is a follow-up.

2. **Single-device, single-queue**: One VkDevice, one compute queue.
   Multi-device / multi-queue is deferred (not needed for single-GPU
   workstations).

3. **Synchronous dispatch**: `vk_queue_submit_and_wait` blocks until
   the GPU finishes. Async dispatch (with fences + semaphores) is
   deferred — the current use case (UI rendering at 60fps) can tolerate
   synchronous dispatch.

4. **Single shared descriptor set**: One descriptor set (set 0) is
   allocated per pipeline and shared across all bindings (uniform
   buffer at binding 0, storage image at binding 1, etc.). This avoids
   the bug where each `vk_cmd_bind_*` allocated a separate descriptor
   set, causing only the last binding to be active at dispatch time.

5. **Std140 layout**: The C uniform buffer struct must match the GLSL
   std140 layout (vec2[3] → vec4[3], padded to 16-byte alignment).

### Verified

- `gpu_vulkan_test.c` end-to-end test: creates instance → device →
  compute pipeline (from triangle_fill.spv) → dispatches a 64×64
  triangle → reads back the framebuffer → 512/4096 pixels filled (12.5%).
- `gpu_vulkan_cube_test.c` end-to-end 3D test: creates render pass
  (color + depth) → graphics pipeline (vertex + fragment SPIR-V) →
  uploads 24-vertex cube + 4×4 checkerboard texture → draws with MVP
  matrix + depth test → 3136/16384 pixels filled (128 red + 170 white
  from texture sampling).
- Async dispatch: vk_queue_submit_async + vk_wait_fence verified.
- Tested on Rocky Linux 10 with Mesa lavapipe (CPU-based Vulkan).
- Vulkan SDK 1.4.328.

### Graphics Pipeline (v0.2.0-alpha.14)

The Vulkan shim now supports both compute AND graphics pipelines:

**Graphics pipeline functions:**
- `vk_create_render_pass` — color (R8G8B8A8_UNORM) + depth (D32_SFLOAT)
  attachments, framebuffer creation.
- `vk_create_graphics_pipeline` — vertex + fragment shader stages,
  vertex input (vec3 position + vec2 tex_coord, stride 32), depth test
  (LESS compare), back-face culling.
- `vk_cmd_begin_render_pass` / `vk_cmd_end_render_pass` — clear color
  to black, depth to 1.0.
- `vk_cmd_bind_gfx_pipeline` — bind graphics pipeline.
- `vk_cmd_bind_vertex_buffer` / `vk_cmd_bind_index_buffer` — upload +
  bind vertex/index data.
- `vk_cmd_bind_gfx_uniform_buffer` — bind MVP matrix uniform.
- `vk_cmd_draw_indexed` — indexed draw call.
- `vk_read_color_image` — read back color attachment for testing.

**Texture support:**
- `vk_create_texture_2d` — RGBA8 texture from host data via staging
  buffer, with image view + sampler (linear filtering, repeat addressing).
- `vk_cmd_bind_texture` — bind combined image sampler to graphics
  descriptor set.

**Async dispatch:**
- `vk_queue_submit_async` — submit without waiting, returns fence.
- `vk_wait_fence` — wait for fence with timeout (ns).

## Consequences

### Positive
- VUMA programs can dispatch GPU compute work via Vulkan on Linux/Windows.
- No Rust GPU crates (wgpu, gfx-rs) — consistent with ADR-0010's 5-crate policy.
- The C shim is ~500 LOC, easy to audit and maintain.

### Negative
- Compute-only (no graphics pipeline yet). 3D mesh rendering requires
  extending the shim with render passes + graphics pipelines.
- Synchronous dispatch (no pipelining of CPU/GPU work).
- Single-device (no multi-GPU support).

### Neutral
- The Vulkan host layer is a "Wrap" decision per ADR-0022 — the Vulkan
  API is OS-provided and wrapped by a thin shim.

## Alternatives Considered

### Alternative A: Use wgpu (Rust GPU crate)
Rejected — violates ADR-0010's 5-crate policy and ADR-0022's "no Rust
GPU crates" requirement.

### Alternative B: Use MoltenVK on macOS
Partially accepted — MoltenVK translates Vulkan → Metal, so the same
`gpu_vulkan.c` shim works on macOS via MoltenVK. However, native Metal
(`gpu_metal.m`, ADR-0027) avoids the translation overhead and is
preferred on macOS.

### Alternative C: No GPU support (CPU-only rendering)
Rejected — ADR-0022 requires GPU path tessellation for acceptable UI
rendering performance.
