# ADR-0011: Re-audit Corrections to ADR-0001 through ADR-0010

- **Status**: Accepted
- **Date**: 2026-08-01
- **Decision Maker**: VUMA compiler team
- **Supersedes**: Partial supersedence of ADR-0001, ADR-0002, ADR-0003,
  ADR-0004, ADR-0006, ADR-0007 (severity and framing corrections only;
  the technical fixes remain valid)
- **Superseded by**: (none)

## Context

The v1 research draft (`docs/vuma-side-research-draft.md`) and the
ADRs written against it (ADR-0001 through ADR-0010) were produced by
four parallel subagents (Wave A) that pattern-matched on `_ => <default>`
arms in the VUMA source without fully understanding:

1. **The two-SCG architecture** — IVE runs on the semantic SCG
   (`vuma_scg::graph::SCG`); codegen runs on the codegen `Scg`
   (`vuma_codegen::scg_to_ir::Scg`). The two are bridged by
   `VerificationInput::typed_state_meta` + a hard-gate
   `verify_typed_state_conformance` cross-check. Bugs in the
   codegen-side bridge functions do NOT affect IVE, and vice versa.

2. **The `__oob_trap` runtime bounds check** — VUMA's memory-safety
   story is defense-in-depth: Z3 at compile time, `__oob_trap` at
   runtime, Lean formal spec. A "wrong IRType" bug produces wrong
   ARITHMETIC (int ADD not float ADDSD), not wrong MEMORY ACCESS.
   The runtime bounds check uses the LAYOUT's size, not the IRType's
   size.

3. **The Lean proof layer's actual scope** — Wave A read `Basic.lean`
   and `PmtInstr.lean` and concluded the layer is "purely
   memory-safety, only `alloc_preserves_capacity` via `omega`." The
   actual layer is 82 files, 280 theorems, 0 `sorry` tokens, including
   a real Iris separation-logic layer (`proof/PMT/Iris/`), a Lean↔Rust
   simulation refinement (`proof/PMT/PipelineSim.lean`), and a
   faithful overflow model (`proof/PMT/BitVecArena.lean`).

4. **The capability model's compile-time-only design** — Wave A framed
   `verify_capability` being "never called from emitted binaries" as
   security theater. It is actually the CORRECT design: capabilities
   are minted and signed at compile time; only the `cap_id` survives
   into the emitted binary. The IVE is supposed to verify at compile
   time — but the IVE verifier is a STUB (`let known = true` at
   `verification.rs:2379`).

5. **The QEMU-workaround status of backend "stubs"** — Wave A
   conflated genuine VUMA stubs (V-A2-8 m68k F32), QEMU translator
   bugs (alpha CMPULE, m68k 7.2 TCG, hppa LDIL/BL — already worked
   around per `caveats.md` §2.4), and dead-code backend arms
   (`IRInstr::ChannelSend` etc. — never reached because
   `ipc_lowering.rs` lowers them to `Syscall` first).

Three follow-up subagents (Wave F: F-1, F-2, F-3) re-verified every
catalog claim against the actual source. Their reports are in
`docs/research/F-{1,2,3}-*.md`. The corrected consolidated draft is
`docs/vuma-side-research-draft-v2.md`.

This ADR documents the corrections to the prior ADRs. The technical
fixes in ADR-0001 through ADR-0010 remain valid; what changes is the
**severity**, **framing**, and **urgency**.

## Decision

### ADR-0001 (V-34: bridge_type_to_ir_type f32/f64) — severity revised, then REVERTED

**Prior (original)**: P0, "blocks all f32 state fields."
**Revised (Wave F)**: P1, "blocks only SCALAR f32 state fields; wrong
IRType = wrong arithmetic, not wrong memory."
**REVERTED (Wave S-Z, 2026-08-01)**: **P0** — the Wave F revision was
WRONG. Empirical testing on the remote machine proved V-34 causes
memory corruption, not just wrong arithmetic.

**Evidence (Wave S-Z, empirical)**:
- Compiled `scripts/v34_test.vuma` (layout `Point = { x: f32, y: f32 }`,
  writes 1.5 and 2.5, reads back, adds, returns as i32).
- Expected exit code: 4 (1.5 + 2.5 = 4.0). Actual: 0.
- IR dump (`dump_ir`) shows:
  ```
  Load { dst: %v2, addr: %v0, offset: 0, ty: U64 }   // p.x — U64, not F32!
  Load { dst: %v4, addr: %v3, offset: 0, ty: U64 }   // p.y — U64, not F32!
  Add  { dst: %v5, lhs: %v2, rhs: %v4, ty: Some(U64) }  // INTEGER ADD!
  Store { value: Immediate(4609434218613702656), addr: %v8, offset: 0, ty: U64 }  // 1.5 as f64, 8 bytes!
  Store { value: Immediate(4612811918334230528), addr: %v9, offset: 0, ty: U64 }  // 2.5 as f64, 8 bytes!
  ```
  - `4609434218613702656` = `0x3FF8000000000000` = 1.5 as **f64** (8 bytes)
  - The Store writes 8 bytes at offset 0, overwriting both `x` (offset 0-3) and `y` (offset 4-7)
  - This is **memory corruption** of the adjacent f32 field
- IVE reports `discharge_rate=100%` — the field-bounds check uses the
  wrong (8-byte) size, so `0 + 8 ≤ 8` passes. IVE is **unsound** for
  this case.
- The runtime `__oob_trap` doesn't catch it — the store is "in bounds"
  of the 8-byte layout.

**Why the Wave F revision was wrong**:
F-1 said "wrong IRType produces wrong ARITHMETIC, not wrong MEMORY
ACCESS." This is incorrect. The wrong IRType (`U64` instead of `F32`)
causes the wrong STORE SIZE (8 bytes instead of 4), which overwrites
the adjacent field. This IS a memory-safety bug, not a performance bug.

**Technical fix unchanged**: add `"f32" => IRType::F32, "f64" => IRType::F64`
arms to `bridge_type_to_ir_type` at `src/pipeline.rs:6515`. The fix is
still a 1-line change, but the urgency is **P0** (memory corruption +
IVE unsoundness), not P1.

**Test report**: `docs/test-report-waves-s-z.md` §2.

### ADR-0002 (V-35 + V-44: type_size_from_name + type_alignment) — severity revised

**Prior**: P0, "blocks all nested-struct layouts."
**Revised**: P2, "affects only the dormant stub
`state_merge_compatible_layouts`; IVE has zero references to
`StructDefNode`/`StructFieldInfo`."

**Evidence (F-1)**:
- IVE consumes `PmtLayoutSpec` (built by `build_pmt_layout_specs` —
  V-03, not by parser-side `register_layout`).
- The sole codegen consumer of `type_size_from_name` is the dormant
  stub `state_merge_compatible_layouts` at `bv_verify.rs:421`
  (documented in `language-reference.md` §9 caveat 8).
- `build_layout_registry` at `pipeline.rs:6625-6699` is a SEPARATE,
  CORRECT multi-pass algorithm that handles nested layouts. The
  codegen production path is NOT affected by V-35.

**Technical fix unchanged**: consult layouts table in
`type_size_from_name` and `type_alignment`. The fix is still correct;
the urgency is P2 cleanup, not P0 blocker.

### ADR-0003 (V-36 + V-A2-1: StateRead/StateWrite IRType threading) — severity revised

**Prior**: P0, "blocks f32 state field access even after V-34."
**Revised**: P2, "fires only for IVE-test-constructed or deserialized
SCGs; production path uses `AccessNode::Load` (affected by V-34, not
V-36)."

**Evidence (F-1)**:
- `language-reference.md` §7 explicitly states: "In the production
  AST→SCG path (`to_scg.rs:992`) and the AST→codegen bridge
  (`pipeline.rs:10370+`), `Expr::StateInit` / `ArenaNew` / `ArenaAlloc`
  / `ArenaGrow` / `ArenaFree` are lowered directly to
  `Allocation`/`Access`/`Call` nodes — so the `NodePayload` state arms
  above fire only for IVE-test-constructed or deserialized SCGs
  (`scg/src/serialize.rs:1377+`)."
- A-2's "worse than cataloged" claim was backwards: V-36 affects a
  NARROWER path than the catalog claimed, not a wider one.

**Technical fix unchanged**: thread IRType through StateRead/StateWrite
+ fix `Alloc { size: 0 }`. The fix is still correct; the urgency is P2.

### ADR-0004 (V-03 + V-NEW-2 + V-40: build_pmt_layout_specs migration) — framing revised

**Prior**: "V-03 is P0 — same class of bug as V-35 but on the codegen
side. The IVE proof of field-bounds safety reasons about wrong
offsets, so the discharge is technically unsound for any program that
nests a layout as a field of another layout."

**Revised**: P1 — "V-03 affects IVE-soundness (the `PmtLayoutSpec`
table IVE reasons about), not codegen-correctness. The codegen
production path uses `build_layout_registry` which is correct. The
parity between `build_pmt_layout_specs` and IVE's `rederive_layout` is
INTENTIONAL per the docstring at `verification.rs:264-267`."

**Evidence (F-1)**:
- `build_layout_registry` at `pipeline.rs:6625-6699` is a SEPARATE,
  CORRECT multi-pass algorithm. Codegen production is NOT affected by
  V-03.
- The IVE `rederive_layout` at `verification.rs:268` reproduces the
  same `_ => 8` behavior ON PURPOSE so that IVE and codegen agree.
- The docstring at `verification.rs:264-267` admits this.

**Technical fix unchanged**: migrate `build_pmt_layout_specs` +
`rederive_layout` to `bridge_type_size_with_layouts` in lockstep, then
delete the legacy function. The lockstep requirement is the most
important coupling to preserve — if V-03 is fixed on the codegen side
without fixing `rederive_layout`, the IVE `verify_layout_consistency`
check will FAIL for any program with a nested layout.

### ADR-0006 (V-14: defer f32 PMT Lean proof to v2) — effort revised

**Prior**: "3-6 months greenfield. There is no existing
arithmetic-verification infrastructure to extend."
**Revised**: "2-4 weeks for a bit-pattern model on top of `BitVec 64`;
2-3 months for full IEEE-754. The existing `BitVecArena` + Iris layer
provides a foundation."

**Evidence (F-2)**:
- 82 Lean files, 280 theorems, 0 `sorry` tokens (verified by
  `grep -rn 'sorry' proof/`).
- Real Iris separation-logic layer in `proof/PMT/Iris/` (9 files):
  `CapBndInvariant`, `LiveMirrorInvariant`, `GuardInvariant`,
  `Composition` (sorry-free `alloc_preserves_pmt_invariants` over
  `[cap_bnd] ∗ [live_mirror] ∗ [guard]`), `HeapModel`,
  `FractionalPerm`, `SepGenuine`, `WeakestPrecond`, `ArenaRes`.
- `BitVecArena.lean` — fixed-width usize overflow model (more faithful
  than `Nat`).
- `PipelineSim.lean` — Lean↔Rust simulation refinement (`SimRel`).
- `WellTypedStrong.lean` — strengthened well-typedness with
  `DataflowOk` + per-step `FieldBounds`.
- `RawArena.lean` — 6-field Arena model including `layout` and
  `created_thread` that A-3 claimed were "not modeled anywhere in
  Lean."

**Decision unchanged**: defer to v2, use runtime
`__float_overflow_trap` for v1. But the v2 effort estimate drops from
3-6 months to 2-4 weeks (bit-pattern) or 2-3 months (IEEE-754).

### ADR-0007 (V-16: HMAC-SHA256 + wire verify_capability) — framing revised

**Prior**: "Wire `verify_capability` into every capability-checked
host import (the import call site checks the signature before invoking
the host function)."
**Revised**: "Wire the IVE capability verifier to actually check
signatures at COMPILE TIME (replace `let known = true` at
`verification.rs:2379`). The capability model being compile-time-only
is CORRECT BY DESIGN — only the `cap_id` survives into the emitted
binary."

**Evidence (F-2)**:
- `capability_grant` / `capability_delegate` (in `ipc_lowering.rs`)
  expand at COMPILE TIME to token MINTING. The signing key, signature,
  and delegation chain are compile-time-only artifacts.
- Only the `cap_id` (low 64 bits) survives into the emitted binary as
  `BinOp(Add, cap_id_immediate, 0)`.
- The IVE is supposed to verify the signature at compile time — but
  `l1l3_collapse` has `let known = true` (V-A3-6) that folds 1 L2
  check per `Intrinsic`-tagged node WITHOUT verifying any signature.
- A-3's framing ("security theater") was wrong: the design is correct,
  the implementation is a stub.

**Severity revised**: P1 → P0. The IVE verifier stub + the hardcoded
signing key (V-A3-2) together form a P0 security gap. The fix is to
wire the IVE verifier, NOT to add runtime checks to emitted binaries.

**Technical fix partially revised**:
1. Hand-written HMAC-SHA256 in pure Rust (UNCHANGED — ~300 LOC, no deps).
2. Replace FNV-1a × 4 in `ipc.rs:996-1007` (UNCHANGED).
3. Replace hardcoded `b"vuma_dev_signing_key"` at `capability.rs:117`
   with per-process random 32-byte secret (UNCHANGED).
4. **REVISED**: Wire the IVE `l1l3_collapse` capability verifier to
   actually check HMAC-SHA256 signatures instead of `let known = true`.
   Do NOT add `verify_capability` calls to emitted binaries — the
   compile-time check is the correct design.

### ADR-0008 (V-A3-3: discharge_rate denominator) — confirmed

**Prior**: "Excludes `failed` from denominator; `unwrap_or(100)`
returns 100% on all-failed."
**Revised**: CONFIRMED. F-2 verified the formula at
`compile_dump.rs:233-235` uses `passed + unverified` (excludes
`failed`). `VerificationSummary::pass_rate()` uses the correct
denominator `total_checked`, but `compile_dump.rs` doesn't call it.

**Technical fix unchanged**: call `pass_rate()` instead of recomputing.
3-line fix.

### ADR-0009 (re-run test suite on main HEAD) — confirmed + QEMU version requirement

**Prior**: "Re-run full test suite on `main` HEAD before treating V-39
as ground truth."
**Revised**: CONFIRMED + mandate QEMU 10.0+.

**Evidence (F-3)**:
- `test_results/summary.json` is from commit `78e71a6b` (pre-`1d72d296`).
- `1d72d296` fixed phi+regalloc liveness — likely moved the needle on
  ~440 of the 1971 failures (9 backends).
- QEMU 7.2 has known translator bugs (alpha CMPULE, m68k TCG, hppa
  LDIL/BL) that VUMA works around. Re-running on QEMU 7.2 will
  re-flag these as VUMA bugs. QEMU 10.0+ is required.

**Technical fix unchanged**: re-run on `main` HEAD with QEMU 10.0+.

### ADR-0010 (5 external crates max) — confirmed

**Prior**: "Adopt 5 external crates maximum."
**Revised**: CONFIRMED. F-2/F-3 did not contradict the dependency
manifest.

### V-A2-9 (regalloc syscall interference) — DROPPED

**Prior (from A-2)**: "P1 — regalloc doesn't model syscall arg/dst
interference, root cause of `contains_fork` opt-out."
**Revised**: REFUTED. DROPPED from catalog.

**Evidence (F-3)**:
- `resolve_register_reuse_conflicts` at `regalloc.rs:2836-2897`
  EXPLICITLY models the syscall arg/dst interference case.
- `architecture.md` §7.3 directly cites `IRInstr::Syscall` as "the
  classic case."
- `contains_fork` is a documented CORRECTNESS REQUIREMENT for
  `clone(2)`/`vfork(2)`, not a workaround for a VUMA bug.
- The W4-fix broadening A-2 cited is a STALE COMMENT.
- `caveats.md` §2.1 documents the `contains_fork` opt-out as a
  correctness requirement, narrowed in v0.2.0-alpha.10 from a broad
  "syscall-hazard fallback" to only `clone`/`fork`.

## Consequences

### Positive
- The "bridge-fix epic" shrinks from ~10 weeks (8 false P0s) to ~4
  weeks of genuine urgency (1 true P0: V-A3-2; plus the V-03/V-NEW-2
  lockstep for IVE soundness).
- The f32 PMT Lean proof is achievable in v2 with 2-4 weeks of
  bit-pattern work, not 3-6 months of greenfield effort.
- The capability model fix is clearer: wire the IVE verifier, not the
  emitted binaries.
- The test suite re-run (ADR-0009) will likely show ~440 fewer
  failures than the stale baseline, focusing triage on 4 backends
  instead of 19.

### Negative
- The v1 ADRs (0001-0010) are now partially stale; engineers reading
  them without reading this ADR-0011 will over-prioritize V-34/V-35/
  V-36/V-03.
- The v1 research draft (`docs/vuma-side-research-draft.md`) is
  superseded by v2 but not deleted — engineers may read the wrong one.

### Neutral
- The technical fixes in ADR-0001 through ADR-0010 are all still
  valid. What changes is severity, framing, and urgency — not the
  code changes themselves.

## Alternatives Considered

### Alternative A: Silently rewrite ADR-0001 through ADR-0010
Rejected — ADR history should be append-only. Engineers reviewing the
PR history need to see the original decisions AND the corrections.

### Alternative B: Delete the v1 research draft
Rejected — the v1 draft contains the raw Wave A findings that are
still useful as a bug inventory. The v2 draft supersedes it for
severity/framing, but the v1 details (file:line citations, code
quotes) are still valid.

### Alternative C: Re-run the full Wave A audit with corrected methodology
Rejected — Wave F already did this for the high-stakes claims. The
remaining un-re-verified claims (V-11, V-26, V-41, V-45, V-47, V-48,
V-49, V-A3-5, V-A3-7, V-A3-8, V-NEW-7, V-NEW-8) are low-severity and
don't justify another audit wave.
