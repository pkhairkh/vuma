# ADR-0007: Wire `verify_capability` into emitted binaries and migrate to HMAC-SHA256

- **Status**: Proposed
- **Date**: 2026-08-01
- **Decision Maker**: VUMA compiler team

## Context

A-3's capability-model audit (`research/A-3-ive-proofs-capability.md` §1 "V-16"
and §"Capability model analysis") surfaces two coupled gaps that together make
the current capability model security theater.

**Gap 1 — FNV-1a × 4 is not a MAC.** The signature function at
`src/codegen/src/ipc.rs:996-1007` is four parallel FNV-1a 64-bit hashes with
1-byte salts (0, 1, 2, 3), concatenated into 32 bytes:

```rust
// src/codegen/src/ipc.rs:996-1007
pub fn compute_signature(token: &CapabilityToken, signing_key: &[u8]) -> [u8; 32] {
    let base = signature_input(token, signing_key);
    let mut sig = [0u8; 32];
    for i in 0..4u8 {
        let mut chunk = Vec::with_capacity(base.len() + 1);
        chunk.push(i);
        chunk.extend_from_slice(&base);
        let h = fnv1a_64(&chunk);
        sig[(i as usize) * 8..(i as usize + 1) * 8].copy_from_slice(&h.to_le_bytes());
    }
    sig
}
```

The signing key is mixed into the input via `signature_input` at
`ipc.rs:970-984` (`buf.extend_from_slice(signing_key)` at line 972), but
through FNV-1a's XOR-multiply folding, not HMAC's ipad/opad construction.
The module-level SECURITY NOTE at `src/codegen/src/capability.rs:31-54`
admits this explicitly: *"This is NOT HMAC, NOT a MAC, and NOT resistant
to a determined adversary with access to `signing_key`."*

Worse, `delegate_capability` at `src/codegen/src/capability.rs:117-137`
hardcodes the literal ASCII string `b"vuma_dev_signing_key"` (20 bytes) as
the signing key (line 117-118) and hardcodes `source_pid: 1,
target_pid: 2` (lines 129-130) for every delegated token. So the "secret"
key is publicly visible in the source tree, and every delegated token
claims to be from PID 1 to PID 2 regardless of the actual delegator.
This is bug **V-A3-2** (P0 — capability forgery) per the A-3 report.

**Gap 2 — `verify_capability` is never called from emitted binaries.** The
SECURITY NOTE at `src/codegen/src/capability.rs:49-54` discloses:

> *"`verify_capability` and `verify_delegation_chain` are **never called
> from emitted VUMA binaries**. The compiler's `channel_recv` codegen
> checks only `cap_count == 0` (rejecting any message that carries
> capability tokens, because it cannot verify them inline). A `.vuma`
> program that calls `channel_recv` on a frame with `cap_count > 0`
> receives `-4` (PERMISSION_DENIED)."*

So even if the signature scheme were HMAC-SHA-256, the receiver would
still reject any non-zero-cap_count message outright. The capability
model is a one-way write-only ledger: tokens are minted and signed, but
no emitted binary ever checks a signature. V-16's "fix" (HMAC migration)
would not change this on its own — the verify path is dead code.

**HMAC-SHA-256 already exists in the repo, but not in a usable form.**
A-3 confirmed that `womb/crypto/mac_kdf/hmac.vuma:75-116` contains a
real RFC-2104 HMAC-SHA-256 implementation (`transform hmac_sha256(key,
keylen, msg, msglen, out)`), with the underlying SHA-256 in
`womb/crypto/hash/sha256_sha224.vuma`. But these are **`.vuma` source
programs**, not Rust libraries. To use them from the codegen's
`compute_signature` (which lives in Rust at `src/codegen/src/ipc.rs`),
the project would have to either (a) compile the `.vuma` HMAC-SHA-256 at
codegen-time and link its symbols — requires VUMA self-compilation at
build time, chicken-and-egg; (b) add the `sha2` + `hmac` Rust crates
from crates.io — violates the small-deps policy reaffirmed by A-4 §2
(8 external crates today, 5 after ADR-0005); or (c) re-implement
HMAC-SHA-256 in pure Rust inside `src/codegen/src/`. Option (c) is the
only one that preserves the small-deps policy without build-time
chicken-and-egg.

SHA-256 is ~150 LOC of pure Rust (32-bit rotr/xor/add over an 8x8
round-constant matrix; no external deps, no `unsafe`). The HMAC
wrapper is ~50 LOC (RFC-2104 ipad/opad construction, two SHA-256
calls). Together ≈ 300 LOC including test vectors. This is well within
the "small enough to hand-write" threshold the project has already
applied to `toml_lite`, the hand-written JSON parser, and the hand-written
Debug/Clone derives (all documented in A-4 §2 "Wave 43 dependency purge").

## Decision

Re-implement HMAC-SHA-256 in pure Rust, replace the FNV-1a × 4 signature
function, key it with a per-process random 32-byte secret, and wire
`verify_capability` into every capability-checked host import. This
closes both Gap 1 (cryptographic forgery resistance) and Gap 2 (the
verify path is no longer dead code).

1. **Create `src/codegen/src/hmac_sha256.rs`** (~300 LOC, no external
   deps). Module structure:
   - `sha256(data: &[u8]) -> [u8; 32]` — the core hash function.
     Implement the standard FIPS 180-4 algorithm: 64-round compression
     over 512-bit blocks, with the standard initial hash values
     (`0x6a09e667`, etc.) and round constants (`0x428a2f98`, etc.).
     No `unsafe`, no SIMD intrinsics — portable pure Rust that compiles
     on every VUMA target including `aarch64-unknown-none`.
   - `hmac_sha256(key: &[u8], msg: &[u8]) -> [u8; 32]` — the RFC-2104
     wrapper: if `key.len() > 64`, hash it down to 32 bytes; pad to
     64 bytes; compute `H((K ^ opad) || H((K ^ ipad) || msg))`. Mirrors
     the algorithm in `womb/crypto/mac_kdf/hmac.vuma:75-116` exactly
     (so the two implementations are auditable against each other).
   - Unit tests with the FIPS-198a test vectors:
     `HMAC-SHA-256("Jefe", "what do ya want for nothing?") =
      5bdcc146bf60754e6a042426089575c75a003f089d2739839dec58b964ec3843`,
     plus three RFC 4231 vectors.

2. **Replace `compute_signature` at `src/codegen/src/ipc.rs:996-1007`**
   with a call to `hmac_sha256(signing_key, &signature_input(token, &[]))`.
   The `signing_key` is no longer concatenated into `signature_input`
   (the HMAC construction handles key separation via ipad/opad); pass
   the key separately. Update `signature_input` at `ipc.rs:970-984` to
   drop the `signing_key` argument (it now serializes only the token
   fields: `id`, `source_pid`, `target_pid`, `created_at`, `expires_at`,
   `delegation_depth`, `permissions`, `resource`).
   The signature size stays `[u8; 32]` (HMAC-SHA-256 output length
   matches the existing FNV-1a × 4 output length), so the wire format
   at `capability.rs:56-62` is unchanged.

3. **Replace the hardcoded `b"vuma_dev_signing_key"`** in
   `delegate_capability` at `src/codegen/src/capability.rs:117-118`
   with a per-process random 32-byte secret sourced from the codegen's
   process-wide RNG. Concretely: add a `static PROCESS_SIGNING_KEY:
   Lazy<[u8; 32]>` initialized at first use from `/dev/urandom` (or
   `getrandom` on Linux/aarch64-none). Thread the actual `source_pid`/
   `target_pid` through `delegate_capability`'s signature instead of
   the hardcoded `1`/`2` literals at `capability.rs:129-130`. This
   closes V-A3-2.

4. **Wire `verify_capability` into every capability-checked host import.**
   The import call site (currently `channel_recv` codegen at the path
   flagged by `capability.rs:49-54`) must, before invoking the host
   function, call `verify_capability(token, &PROCESS_SIGNING_KEY)` on
   each capability token in the received frame and trap with a new
   `__cap_verify_fail` exit code (suggested: 143 = 128 + SIGTERM(15),
   matching the existing exit-code conventions documented in A-4 §1)
   if any token's signature does not verify. This replaces the current
   `cap_count == 0` rejection at the same site — programs that legitimately
   receive capability tokens can now do so, and programs that receive
   forged tokens trap deterministically.
   - Audit scope: every backend's call ABI must accommodate the extra
     signature-verification step. On x86_64/aarch64 this is a `call` to
     a Rust helper that takes the token pointer and returns a bool; on
     soft-float / register-starved backends (hppa, m68k) the token may
     need to be spilled to a scratch stack slot first. **This is the
     part with medium confidence** — the wiring touches every backend's
     host-import call site, and the exact call-ABI accommodation needs
     per-backend verification before this ADR can move from Proposed to
     Accepted.

5. **Update the Lean model** in `proof/PMT/Capability.lean` (if it
   exists; A-3 did not find one in `proof/PMT/`, so this step may be a
   new file) to model HMAC-SHA-256 as an uninterpreted function with
   the RFC-2104 correctness property:
   `∀ key msg, hmac_sha256(key, msg) = sha256((key ^ opad) ++ sha256((key ^ ipad) ++ msg))`.
   The Lean model does not need to verify the SHA-256 compression
   function itself (that's a FIPS-standard implementation audited by
   test vectors); it only needs to prove that `verify_capability`
   accepts a token iff `compute_signature(token, key) =
   hmac_sha256(key, signature_input(token))`, which is true by
   definition once step 2 lands.

6. **Update the SECURITY NOTE at `src/codegen/src/capability.rs:31-54`**
   to reflect the new state: the signature is now HMAC-SHA-256, the
   signing key is per-process random, `verify_capability` is now called
   from emitted binaries, and the `cap_count == 0` rejection is replaced
   by per-token signature verification.

## Consequences

### Positive

- The capability model becomes cryptographically sound: HMAC-SHA-256
  with a per-process random key is resistant to forgery by any adversary
  who does not have the key, including adversaries who can read the
  source tree (the key is no longer `b"vuma_dev_signing_key"`).
- `verify_capability` is no longer dead code — every capability-checked
  host import actually verifies signatures at runtime. The
  `capability.rs:49-54` disclosure becomes historical.
- The wire format is unchanged (`[u8; 32]` signature, same
  `CAPABILITY_TOKEN_SIZE`), so existing `.vuma` programs that emit
  capability tokens continue to compile and run (though their tokens
  will fail verification under the new key, which is the point — old
  forged tokens must be invalidated).
- The small-deps policy is preserved: no new external crate is added.
  The hand-written `hmac_sha256.rs` is auditable against the existing
  `womb/crypto/mac_kdf/hmac.vuma:75-116` implementation (same algorithm,
  two languages) and against the FIPS-198a test vectors.
- The Lean model gains a real (if shallow) theorem: `verify_capability`
  accepts iff the signature matches. This is a non-tautological
  statement about the relationship between `compute_signature` and
  `verify_capability`, unlike the existing tautology theorems flagged
  by A-3 (`SessionType.lean:140-144`, `L1L3Collapse.lean:150-154`).
- Closes V-16 (catalog), V-A3-2 (hardcoded signing key + PIDs), and
  the V-16 amplification 2 (verify path is dead code) in a single
  coordinated change.

### Negative

- **Existing capability tokens are invalidated.** Any `.vuma` program
  that emitted tokens under the old FNV-1a × 4 scheme with
  `b"vuma_dev_signing_key"` will see those tokens fail verification
  under the new per-process random key. This is intentional (the old
  tokens were forgeable) but is a breaking change for any persisted
  capability state. Document in the migration notes.
- **Per-process random key breaks determinism.** The codegen currently
  produces deterministic output (same input → same binary). A
  per-process random signing key means two compiles of the same
  `.vuma` program produce binaries with different signing keys.
  This is fine for capability tokens (they're runtime artifacts,
  not compile-time constants), but the `delegate_capability` function
  at `capability.rs:117-137` currently produces a *deterministic* child
  id (the docstring at `:90-92` explicitly calls out "no randomness,
  no global state — important for compile-time codegen"). The
  deterministic-child-id property must be preserved — the random key
  signs the token, but the token id derivation stays deterministic
  (parent_id | high_bit + 1). Audit this carefully.
- **Runtime cost on every host import.** Each `verify_capability` call
  is one HMAC-SHA-256 (two SHA-256 calls over ~256 bytes of input) —
  roughly 1-2 µs on x86_64, more on soft-float backends. For
  capability-heavy workloads (e.g., a kernel that grants/revokes
  capabilities on every syscall), this is measurable. Mitigation:
  cache verified tokens by id in a small per-thread LRU.
- **Per-backend call-ABI accommodation (step 4) is the riskiest part.**
  19 backends × N host-import call sites each = a large surface area.
  The exact ABI changes (extra arg register for the key pointer, spill
  slot for the token on register-starved backends, branch-to-trap on
  verify failure) need per-backend verification. **This is why the
  Status is Proposed, not Accepted** — high confidence on the
  algorithm (HMAC-SHA-256 is standard), medium confidence on the
  wiring scope.
- **Lean proof effort.** Step 5 is real work — modeling HMAC-SHA-256
  as an uninterpreted function with the RFC-2104 correctness property
  is ~1 week, and proving `verify_capability` accepts iff signature
  matches is another ~1 week (the statement is simple but the proof
  must thread through the `CapabilityToken` serialization). Budget 2
  weeks for the Lean side; this is included in the catalog's V-16
  "5 weeks (3 weeks code + 2 weeks Lean proof updates)" estimate.

### Neutral

- The `womb/crypto/mac_kdf/hmac.vuma:75-116` implementation stays in
  place — it's the canonical VUMA-source implementation used by
  `.vuma` programs that need HMAC at runtime. The new
  `src/codegen/src/hmac_sha256.rs` is the canonical Rust implementation
  used by the codegen's capability layer. The two are auditable against
  each other (same algorithm, two languages); divergence between them
  would be a red flag in future audits.
- The `__cap_verify_fail` exit code (suggested 143) joins the existing
  trap-exit-code table: `1` (arena overflow), `134` (OOB), `135` (UAF,
  dormant), `142` (float overflow, per ADR-0006). The test harness
  (`scripts/ci_run_tests.sh`) already recognizes numeric exit codes;
  adding 143 is a 1-line change.
- The `pmt-runtime-check` Cargo feature (`Cargo.toml:111-113`) is
  unaffected — capability verification is always on, not opt-in. (The
  old `cap_count == 0` rejection was always on too.)

## Alternatives Considered

### Alternative A: Use the `womb/crypto` HMAC-SHA-256 implementation

Rejected. The `womb/crypto/mac_kdf/hmac.vuma:75-116` implementation is a
`.vuma` source program, not a Rust library. To call it from the codegen's
`compute_signature` (which lives in Rust at `src/codegen/src/ipc.rs`), the
codegen would have to either (a) invoke `lake build` or `vuma compile` on
`hmac.vuma` at build time and link the resulting symbols — chicken-and-egg,
requires a working VUMA toolchain at build time, breaks cross-compilation;
or (b) compile `hmac.vuma` to a Rust staticlib at release time and ship
the staticlib in-tree — adds a binary artifact to the repo, breaks
reproducible builds. Either way, every emitted VUMA binary would depend
on the `womb/crypto` runtime, which defeats the "small self-contained
runtime" property A-4 §2 documented. The hand-written Rust
implementation in step 1 is ~300 LOC and has no such dependencies.

### Alternative B: Use the `sha2` + `hmac` crates from crates.io

Rejected. A-4 §2 documented that the workspace currently has 8 external
crates (5 after ADR-0005 lands), and the "small-deps" policy is
"strongly honored" with two carve-outs (z3 necessary, cc removable).
Adding `sha2` (which pulls in `cpufeatures`, `digest`, `block-buffer`,
`crypto-common`, `generic-array` — 5+ transitive crates) and `hmac`
(which pulls in `digest` again) would double the external crate count
and violate the policy SHA-256 is small enough to hand-write (~150 LOC;
the project has already hand-written `toml_lite`, a JSON parser, and
Debug/Clone derives for the same reason). The hand-written version is
also auditable against the existing `womb/crypto/hash/sha256_sha224.vuma`
implementation, which a crates.io dependency would not be.

### Alternative C: Keep FNV-1a × 4 and document the weakness

Rejected. The SECURITY NOTE at `src/codegen/src/capability.rs:31-54`
already documents the weakness extensively, and the result is that the
verify path is dead code (`capability.rs:49-54`) because no consumer
trusts the signature. Keeping the scheme and adding more documentation
does not close the security gap — it just makes the gap more
thoroughly described. The capability model is either cryptographically
sound or it is not; there is no middle ground that provides partial
forgery resistance. The hardcoded `b"vuma_dev_signing_key"` at
`capability.rs:117` makes the current scheme actively exploitable, not
just theoretically weak.
