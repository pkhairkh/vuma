# ADR-0015: VEEE backend strategy — Cranelift (dev) + VUMA codegen (prod) + MLIR→SPIR-V (GPU)

- **Status**: Proposed
- **Date**: 2026-08-01
- **Decision Maker**: VUMA project lead
- **Supersedes**: (none)
- **Superseded by**: (none)

## Context

VEEE (per ADR-0013, Layer 3) is a higher-level UX language that
compiles to VUMA AST (per ADR-0014). VEEE programs go through VUMA's
full pipeline: AST → SCG → IVE → IR → opt → regalloc → backend.

But VEEE has three distinct compilation needs that VUMA's existing
19-backend codegen doesn't fully cover:

1. **Dev builds** — VEEE developers need fast compilation for tight
   edit-compile-run loops during UI development. VUMA's 19-backend
   codegen is optimized for correctness and verification, not speed.
   A dev build that takes 5 seconds to compile a UI screen is
   acceptable; one that takes 60 seconds is not.

2. **Production builds** — VEEE programs shipped to end users need
   maximum performance and full verification. VUMA's 19-backend codegen
   (with e-graph optimization, PGO, LTO) is the right choice here.

3. **GPU shaders** — VEEE's renderer (WOMB's `womb/ui/render/vector.vuma`)
   needs GPU path-tessellation shaders. VUMA's codegen is CPU-only
   (19 CPU ISAs, zero GPU support — verified by A-2 and F-3). The GPU
   path needs a separate compilation strategy.

The SWE package (`23-vell-redesign-research.md`) proposed: Cranelift
for dev builds, MLIR→SPIR-V for GPU, VUMA's custom codegen for
production. This ADR formalizes that decision but marks it Proposed
pending prototype validation.

## Decision

**Adopt a three-track backend strategy for VEEE:**

### Track 1: Dev builds — Cranelift

- **VEEE → VUMA AST → VUMA IR → Cranelift IR → native code**
- Cranelift is a fast Rust-native code generator (~10× faster compile
  than LLVM, no C++ dependency).
- VEEE adds a `--dev` flag that routes VUMA IR through a new
  `src/codegen/src/cranelift/mod.rs` backend instead of the 19
  native backends.
- Cranelift backend produces native code for the host ISA
  (x86_64 or aarch64) only — no cross-compilation in dev mode.
- **Verification**: dev builds still go through IVE (Z3) — the
  verification happens before codegen, so the backend choice doesn't
  affect verification. Dev builds are verified, just not as optimized.

### Track 2: Production builds — VUMA's 19-backend codegen

- **VEEE → VUMA AST → VUMA IR → opt → regalloc → 19 backends → ELF/Wasm**
- This is VUMA's existing pipeline, unchanged.
- VEEE programs get the full optimization suite: e-graph rewriting,
  loop unrolling, vectorization, PGO, LTO.
- Cross-compilation to all 19 backends (x86_64, aarch64, riscv64,
  wasm32, etc.) is supported.
- **Verification**: full PMT verification + Lean formal spec coverage.

### Track 3: GPU shaders — MLIR→SPIR-V

- **VEEE GPU kernels → MLIR dialect → SPIR-V → Vulkan/Metal/WebGPU**
- VEEE's GPU kernels (path tessellation, glyph rasterization, compositing)
  are written in a VEEE GPU DSL that lowers to MLIR.
- MLIR's `gpu` dialect and `spirv` dialect handle the lowering to
  SPIR-V, which Vulkan/Metal/WebGPU consume.
- This does NOT go through VUMA's codegen (VUMA is CPU-only).
- **Verification**: GPU kernels are NOT covered by PMT verification
  (PMT is a CPU memory model). GPU kernel verification is a separate
  concern, deferred to a future ADR.

### Why not LLVM?

LLVM is rejected for all three tracks:
- **C++ dependency** — LLVM is a large C++ library. Adding it to VUMA
  would violate the 5-crate policy (ADR-0010) and require a C++ build
  toolchain.
- **No e-graphs** — LLVM's optimizer doesn't use e-graphs. VUMA's
  e-graph (`src/codegen/src/egraph.rs`) is the foundation for VEEE's
  incremental-computation optimization. Using LLVM would mean
  duplicating the optimizer.
- **No GPU dialect** — LLVM's GPU support (via `llvm.spiirv`) is less
  mature than MLIR's `spirv` dialect. MLIR is the better GPU path.
- **Compile speed** — LLVM is slower than Cranelift for dev builds.
  For production, VUMA's own codegen is already faster than LLVM
  (no C++ template instantiation overhead).

## Consequences

### Positive
- **Dev builds are fast** — Cranelift compiles in ~1-2 seconds for a
  typical UI screen, vs. ~10-30 seconds for VUMA's 19-backend codegen.
- **Production builds are fully verified** — VUMA's pipeline is
  unchanged, so all existing verification applies.
- **GPU path is principled** — MLIR→SPIR-V is the industry-standard
  GPU compilation path. It avoids the dead-end of writing a custom
  SPIR-V backend in VUMA.
- **No LLVM dependency** — the 5-crate policy is preserved. Cranelift
  is a Rust crate (would become the 6th external dep, requiring an ADR);
  MLIR is a build-time tool, not a runtime dependency.

### Negative
- **Adds Cranelift as a dependency** — this would be the 6th external
  crate, violating ADR-0010's 5-crate cap. Either (a) raise the cap to
  6, (b) make Cranelift dev-only (not in production builds), or (c)
  write a fast native codegen in Rust (huge effort). Option (b) is
  recommended — Cranelift goes in `[dev-dependencies]` only.
- **Adds MLIR as a build-time tool** — MLIR is a C++ tool that must be
  installed on the build host. This is acceptable (like Z3) but adds
  setup complexity.
- **Three backends to maintain** — Cranelift, VUMA codegen, MLIR.
  Each has its own bugs and limitations.
- **GPU kernels are not PMT-verified** — this is a verification gap.
  Mitigated by runtime shader validation (SPIR-V has its own
  validator).

### Neutral
- This ADR is Proposed, not Accepted, because the Cranelift and MLIR
  integrations haven't been prototyped yet. Promotion to Accepted
  requires:
  1. A working Cranelift backend that can compile a "hello world"
     VEEE program to native code.
  2. A working MLIR→SPIR-V pipeline that can compile a simple
     compute shader.
  3. Confirmation that Cranelift as a dev-dependency doesn't bloat
     production builds.

## Alternatives Considered

### Alternative A: Use VUMA's codegen for everything (no Cranelift, no MLIR)
Rejected — dev builds would be too slow (10-30 seconds per screen),
and there's no GPU path. VEEE would be unusable for rapid UI
development.

### Alternative B: Use LLVM for everything
Rejected — C++ dependency, no e-graphs, worse GPU path than MLIR,
slower dev builds than Cranelift.

### Alternative C: Write a custom VUMA GPU backend (Vulkan/Metal/SPIR-V)
Rejected — per the Wave A audit (`22-review-against-vuma.md`), this
is 3-6 months of greenfield work. MLIR→SPIR-V gives the same result
in ~2 months by reusing MLIR's `spirv` dialect.

### Alternative D: Use Cranelift for both dev AND production
Rejected — Cranelift's optimization is weaker than VUMA's e-graph +
PGO + LTO. Production builds need maximum performance.
