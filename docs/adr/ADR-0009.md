# ADR-0009: Re-run full test suite on `main` HEAD before treating V-39 as ground truth

- **Status**: Accepted
- **Date**: 2026-08-01
- **Decision Maker**: VUMA compiler team

## Context

The V-39 entry in `docs/vuma-side-problem-catalog.md:37,354-396` reports a
93.42% pass rate (27 992 of 29 963 runs matching; 1 971 failures across 364
tests) on the full 19-backend × 1 577-test matrix. These numbers are quoted
by A-4 (`docs/research/A-4-pipeline-runtime-tests-deps.md` §"V-39") and by
A-2 (`docs/research/A-2-ir-codegen.md` §"Test data referenced",
`:208`, `:442`, `:611`) as the authoritative baseline for triage work.

The numbers are not authoritative. `test_results/summary.json:2-3` reads:

```json
"timestamp": "2026-07-31 23:46:38 UTC",
"host": "pi-pkhairkh-dev",
```

Per A-2's git audit (`docs/research/A-2-ir-codegen.md:208`), this run was
produced at commit `78e71a6b` (2026-07-31 23:46:38 UTC). The very next
commit, `1d72d296` (2026-08-01 00:37:31 UTC, ~51 minutes later), is the
phi-construction + register-allocator liveness fix whose commit message
explicitly claims it fixed `arith_fibonacci` on 9 backends (x86_64,
aarch64, riscv64, arm32, mips64, loongarch64, s390x, alpha, hppa). The
`test_results/failures.txt` snapshot shows `arith_fibonacci exp=55`
failing with `MM=1` on exactly those 9 backends plus 5 more — meaning
**the catalog's 93.42% baseline predates the fix that addresses a large
fraction of the MM failures**. A-2 estimates the real current pass rate
is likely 2–4 percentage points higher (i.e. ~96%).

The downstream consequences are not cosmetic. The catalog's per-backend
ranking (`docs/vuma-side-problem-catalog.md:363-367`) — strongest
`x86_64`/`aarch64`, weakest `m68k`/`sparc64`/`hppa`/`alpha`/`x86_32` —
and the A-2 root-cause hypothesis of a shared loop-lowering bug on
`{ppc64, ppc64le, x86_32, sparc64, m68k}` (235 failures in the
`nested_loops` + `control_flow` cluster) both rest on the pre-`1d72d296`
data. A-2's per-backend failure tallies (`docs/research/A-2-ir-codegen.md:176-178`)
— m68k alone holds 243 of 302 TOs; ppc64/ppc64le/sparc64/x86_32 are
MM-dominated — were computed from the same stale `failures.txt`. Triage
performed against these numbers risks re-discovering bugs that `1d72d296`
already fixed, or missing new regressions introduced by the same commit
on backends not in its "fixed" list.

The `test_results/history/` directory contains only a `.gitkeep`
(confirmed by A-4 at `docs/research/A-4-pipeline-runtime-tests-deps.md:415`)
— so there is no prior snapshot to diff against, and the `scripts/show_trend.py`
trend view will return no data. The next run will be the new baseline.

The current `main` HEAD is `6dc97e18` (2026-08-01) per the catalog preamble
(`docs/vuma-side-problem-catalog.md:11`) — i.e. 6+ doc-cleanup commits past
`1d72d296`. The full suite has not been run since `78e71a6b`.

## Decision

Re-run the full 19-backend × 1 577-test matrix on `main` HEAD before any
V-39 triage work begins, and refresh the published artifacts in lockstep.

1. **Canonical runner.** Use `scripts/pi5_test_suite.sh`, **not**
   `scripts/ci_run_tests.sh`. Verified by reading both:
   `scripts/ci_run_tests.sh:39-65` runs only 7 native QEMU backends
   plus an x86_64-only gold-standard loop — it does not exercise the
   full 19-backend matrix and is not what produced
   `test_results/summary.json`. `scripts/pi5_test_suite.sh` is the
   full-matrix runner (the file header at
   `scripts/pi5_test_suite.sh:1-3` says "Full Test Suite Runner";
   it produced the `78e71a6b` snapshot per the `pi-pkhairkh-dev`
   hostname in `test_results/summary.json:3`). It supports
   `--workers N` for parallelism, `--release` for the slow LTO
   profile (default is `release-fast` per
   `scripts/pi5_test_suite.sh:15`), `--commit` to auto-commit + push
   the refreshed results, and `--fresh` to clear caches. Suggested
   invocation:
   ```
   bash scripts/pi5_test_suite.sh --workers 4 --commit
   ```
   on a host with all 18 QEMU user-mode emulators (`qemu-aarch64-static`,
   `qemu-riscv64-static`, … `qemu-hppa-static`, `qemu-aarch64_be-static`)
   on `PATH` (the `wasm32` backend is run natively via
   `scripts/wasm32_runner.py` — see `scripts/vuma_test_matrix_19backends.sh:39`).

2. **Overwrite the published artifacts** — `test_results/summary.json`,
   `test_results/failures.txt`, and a new snapshot under
   `test_results/history/<timestamp>_summary.json`. The
   `scripts/pi5_test_suite.sh:467-492` archiving logic is supposed to
   do this automatically; the current empty `history/` (only
   `.gitkeep`) suggests the archive either didn't fire or was cleared.
   Verify post-run that `history/` now contains the new snapshot.

3. **Commit the refreshed results as a separate, single commit** titled
   exactly:
   ```
   [test-results] Refresh on main HEAD <sha>
   ```
   where `<sha>` is the `main` HEAD sha at run time (currently
   `6dc97e18` or later). Do not bundle the refresh with any code
   change — the commit must be revertable in isolation so future
   bisects can attribute regressions to either code or test-data
   changes unambiguously.

4. **Update the V-39 entry** in `docs/vuma-side-problem-catalog.md`
   (§"V-39 — Test suite health", lines 350-396) and the corresponding
   section in `docs/vuma-side-research-draft.md` (§4, "Test-suite
   health", lines 278-300) with the new pass rate, the new failure
   count, the new per-backend ranking, and the new commit sha +
   timestamp. Both files currently cite `78e71a6b` /
   `2026-07-31 23:46:38 UTC` / `pi-pkhairkh-dev`; these must be
   updated in the same commit as the data refresh.

5. **Re-evaluate the ppc64/ppc64le loop-lowering cluster hypothesis**
   against the fresh `failures.txt`. A-2's hypothesis
   (`docs/research/A-2-ir-codegen.md:442-483`) is that ppc64/ppc64le
   (295 failures each, 2nd/3rd weakest) share a single
   register-reuse bug in `src/codegen/src/ppc64/reg_isel.rs` analogous
   to the one `1d72d296` fixed for the other 9 backends — but ppc64
   was *not* in `1d72d296`'s "fixed" list, so its failures should
   survive the refresh. If they do, the hypothesis gains support; if
   they drop materially, the hypothesis must be revised. Either way,
   the per-backend tallies in `docs/research/A-2-ir-codegen.md:176-178`
   must be recomputed and the catalog's weakest-backend list
   (`docs/vuma-side-problem-catalog.md:366`) must be reconciled
   against the new ordering.

## Consequences

### Positive

- The V-39 baseline becomes a faithful representation of `main` HEAD.
  All downstream triage work (A-2's per-backend failure tallies, the
  ppc64/ppc64le cluster hypothesis, the catalog's recommended
  execution order at `docs/vuma-side-problem-catalog.md:433-447`)
  rests on numbers that reflect the current compiler, not a snapshot
  51 minutes stale.
- Regressions introduced by `1d72d296` (if any — A-2 found none in
  its source audit at `docs/research/A-2-ir-codegen.md:512-559` but
  the audit was necessarily source-level, not runtime-level) will
  surface in the fresh run rather than during a future triage PR.
- The empty `test_results/history/` directory gains its first real
  snapshot, enabling `scripts/show_trend.py` to produce trend data
  for the next run.
- The `[test-results]` commit-prefix convention establishes the
  pattern for future refreshes — V-39 explicitly recommends an
  "ongoing" refresh cadence (`docs/vuma-side-problem-catalog.md:394`).

### Negative

- The run is expensive. The `78e71a6b` snapshot was 29 963 runs on a
  Pi 5 (`pi-pkhairkh-dev`); at ~4 workers with the `release-fast`
  profile (default per `scripts/pi5_test_suite.sh:15`), the run takes
  multiple hours. The host must have all 18 QEMU user-mode emulators
  installed; not every contributor's machine qualifies.
- The single-commit refresh policy means the commit will be large
  (a new `summary.json`, a new `failures.txt`, a new
  `history/<ts>_summary.json`, plus edits to two `.md` files). Git
  history will show it as one big diff. This is the price of
  revertability.
- The catalog and research draft will need *another* update if the
  run surfaces new bugs (e.g. a regression on a backend that was
  passing). The doc-update loop is not closed by this ADR — it just
  establishes the cadence.

### Neutral

- The 19-backend × 1 577-test matrix size is unchanged.
- The canonical runner (`scripts/pi5_test_suite.sh`) is unchanged.
- The hard-fail semantics of `compile_dump.rs:240` (which gate
  whether a `.vuma` test even produces a binary) are unchanged.

## Alternatives Considered

### Alternative A: Trust the stale `78e71a6b` data and triage blindly

This would proceed with V-39 triage against the current
`test_results/failures.txt`, ignoring the 51-minute gap to
`1d72d296`. Rejected because (a) `1d72d296`'s commit message
explicitly lists 9 backends as fixed for `arith_fibonacci` — at
least those 9 MM failures are already gone, so triaging them is
wasted effort; (b) A-2's source audit found no regressions from
`1d72d296` *at the source level*, but runtime regressions on
backends outside the "fixed" list are possible and would be missed
without a fresh run; (c) the cost of a single full-suite run (a
few hours on a Pi 5) is trivial compared to the cost of triaging
against wrong numbers (days of misdirected work).

### Alternative B: Run only the failing tests (the 1 971 failures) on `main` HEAD

This would re-run only the 364 currently-failing tests across the
19 backends and diff the new failures against the old. Rejected
because (a) the full matrix is needed to detect regressions
introduced by `1d72d296` on tests that were *passing* at
`78e71a6b` — running only the failing subset would miss them;
(b) the `scripts/pi5_test_suite.sh` runner does not support a
"failures-only" filter — it always runs the full gold-standard
directory tree; (c) the saved `summary.json` schema reports
`total_runs` / `matches` / `pass_rate` per backend, and a
partial run would produce a `summary.json` with a different
denominator, breaking trend comparison; (d) the cost saving is
modest (the 1 971 failures are ~6.6% of the matrix, but they are
concentrated in the slowest backends — m68k alone holds 243 of 302
TOs, and timeouts dominate wall-clock cost).
