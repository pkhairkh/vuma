# ADR-0014: VEEE compiles to VUMA AST, not to VUMA IR

- **Status**: Accepted
- **Date**: 2026-08-01
- **Decision Maker**: VUMA project lead
- **Supersedes**: (none — this is a new decision)
- **Superseded by**: (none)

## Context

VEEE is a higher-level UX language that compiles to VUMA (per
ADR-0013). There are two possible compilation targets:

1. **VUMA AST** — the parser's output (`vuma_parser::ast::AstProgram`).
   VEEE programs lower to AST, then VUMA's full pipeline (parse → AST →
   SCG → IVE → IR → opt → regalloc → backend) runs on the lowered AST.
2. **VUMA IR** — the codegen's SSA-like intermediate representation
   (`vuma_codegen::ir::IRFunction`). VEEE programs lower directly to
   IR, bypassing the parser and SCG.

The choice matters because it determines what verification VEEE
programs receive and what optimizations apply.

### Option 1: VEEE → VUMA AST

**Pros**:
- VEEE programs get the **full VUMA pipeline**: SCG name resolution,
  type checking, monomorphization, effect inference, IVE verification
  (Z3 contract discharge, session-type linearity, information-flow
  lattice, PMT invariants), e-graph optimization, regalloc, 19-backend
  codegen.
- VEEE programs inherit **PMT verification** — the arena memory-safety
  argument applies to VEEE-lowered code because it goes through the
  same SCG → IVE → IR path as hand-written VUMA.
- VEEE's incremental-computation `signal` primitive can lower to
  VUMA's `State<T>` typed-state API, which IVE verifies.
- VEEE's monotonicity types can be encoded as VUMA contracts
  (`requires`/`ensures`), discharged by Z3.
- The VEEE compiler doesn't need to duplicate VUMA's type checker,
  effect inferencer, or verifier — it just emits AST and lets VUMA
  handle them.

**Cons**:
- VEEE's lowering is constrained by what the VUMA parser accepts. If
  VEEE needs a construct VUMA's parser doesn't accept (e.g. pattern
  matching with guards, higher-ranked types), the VEEE compiler must
  desugar it to existing VUMA AST nodes.
- VEEE can't bypass VUMA's type system for experimentation. If VEEE
  wants to try a different type system, it must encode it as VUMA
  contracts.

### Option 2: VEEE → VUMA IR

**Pros**:
- VEEE has full control over the IR. It can emit any IR instruction,
  bypass VUMA's type checker, and experiment with different semantics.
- Faster compilation (no re-parsing, no SCG construction).

**Cons**:
- VEEE programs **lose PMT verification**. The IVE runs on the SCG,
  not on the IR. If VEEE emits IR directly, the IVE can't verify it
  (the `typed_state_meta` bridge requires the SCG).
- VEEE must duplicate VUMA's type checker, effect inferencer, and
  verifier. This is ~10,000 lines of Rust that VEEE would have to
  re-implement.
- VEEE's `signal` primitive can't lower to `State<T>` (that's a
  SCG-level construct). It would have to lower to raw `Load`/`Store`
  IR instructions, losing the typed-state safety.
- The Lean formal spec (`proof/PMT/`) models the SCG → IR path, not
  arbitrary IR. VEEE-emitted IR wouldn't be covered by the Lean proofs.

## Decision

**VEEE compiles to VUMA AST, not to VUMA IR.**

VEEE programs lower to `vuma_parser::ast::AstProgram`, then VUMA's
full pipeline runs. VEEE inherits PMT verification, Z3 contract
discharge, e-graph optimization, and 19-backend codegen.

### Implications for VEEE design

1. **VEEE's type system must be encodable as VUMA contracts.**
   Monotonicity types (Datafun) lower to `requires`/`ensures` clauses
   that Z3 discharges. This is the right abstraction level — VEEE
   doesn't need a separate verifier.

2. **VEEE's `signal` primitive lowers to VUMA's `State<T>`.** The
   incremental-computation invalidation graph lowers to
   `layout_mark_dirty` calls on the state buffer. IVE verifies the
   state accesses.

3. **VEEE's `render` primitive lowers to a VUMA `transform` that
   produces a scene tree.** The scene tree is a VUMA layout
   (`Layout SceneNode = { ... }`) stored in the PMT arena.

4. **VEEE's `schedule` primitive lowers to a VUMA `transform` that
   interprets the scene tree.** WOMB's renderer (`womb/ui/render/`)
   consumes the scene tree.

5. **VEEE's syntax desugars to VUMA AST nodes.** VEEE pattern matching
   desugars to VUMA `match`. VEEE closures desugar to VUMA `transform`
   values. VEEE generics desugar to VUMA generics (monomorphized by
   `src/codegen/src/monomorphize.rs`).

### What VEEE can't do (by design)

- **Bypass VUMA's type system.** If VEEE wants a feature VUMA's type
  system can't express, VEEE must either (a) encode it as a contract,
  (b) desugar it to existing VUMA constructs, or (c) propose a VUMA
  language extension (which goes through the VUMA ADR process).
- **Emit raw IR.** VEEE's compiler output is AST, not IR. This is a
  feature, not a limitation — it ensures VEEE programs are always
  verifiable.
- **Skip verification.** VEEE programs always go through IVE. There's
  no `--no-verify` escape hatch for VEEE (VUMA has `--no-verify` for
  testing, but VEEE programs shouldn't use it).

## Consequences

### Positive
- **VEEE inherits full PMT verification for free.** No separate
  verifier to build.
- **VEEE programs are verifiable by the existing Lean formal spec.**
  The Lean `pmt_soundness` theorem applies to VEEE-lowered code.
- **VEEE's compiler is smaller.** It doesn't duplicate VUMA's type
  checker, effect inferencer, or verifier. Estimated VEEE compiler
  size: ~5,000 lines of Rust (vs. ~15,000 if it lowered to IR).
- **VEEE and VUMA share the e-graph.** VEEE's optimizer can use
  `src/codegen/src/egraph.rs` directly, with VEEE-specific rewrite
  rules added alongside VUMA's.

### Negative
- **VEEE is constrained by VUMA's AST.** If VEEE needs a construct
  VUMA's parser doesn't accept, VEEE must desugar it. This is usually
  fine (most UX language features desugar cleanly) but could be a
  limitation for experimental features.
- **VEEE compilation is slower** than direct IR emission (extra
  parse/SCG step). Acceptable for a UX language — developer experience
  matters more than compile speed.

### Neutral
- The VEEE compiler is a separate Rust binary (`veeec`) that produces
  `.vuma` files (or in-memory AST), then invokes the VUMA pipeline.
  The integration point is `vuma::pipeline::compile_modules`.

## Alternatives Considered

### Alternative A: VEEE → VUMA IR (direct lowering)
Rejected — loses PMT verification, requires duplicating VUMA's type
checker and verifier, breaks the Lean formal spec coverage.

### Alternative B: VEEE → VUMA SCG (skip parser)
Rejected — the SCG is an internal IR, not a stable interface. Lowering
to SCG would couple VEEE to VUMA's internal SCG representation, which
may change. AST is the stable interface (it's what the parser
produces and what the language reference documents).

### Alternative C: VEEE → MLIR → VUMA IR
Rejected — adds MLIR as a dependency (violates the 5-crate policy) and
still loses PMT verification. MLIR is the right choice for the GPU
path (ADR-0018), not for the CPU path.
