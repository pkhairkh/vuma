# ADR-0013: Adopt the three-layer architecture (VUMA / WOMB / VEEE)

- **Status**: Accepted
- **Date**: 2026-08-01
- **Decision Maker**: VUMA project lead
- **Supersedes**: The implicit "VUMA does everything" framing in the
  original catalog and the SWE package's native-first framing in
  `24-rough-draft-vuma-only.md`
- **Superseded by**: (none)

## Context

The SWE package (`vuma-swe-package/26-new-plans-three-layers.md`)
proposes a three-layer architecture for the VUMA ecosystem. This ADR
formalizes that decision and locks in the layer boundaries.

Prior to this ADR, the VUMA project had an ambiguous scope: the
compiler team was responsible for everything (language, codegen,
runtime, UI engine, UX language), and the SWE package's proposals
for UI work (V-01 native backend, V-02 rendering IR, V-08..V-32 UI
feature patches) were being evaluated as VUMA-side patches. The
re-audit (Wave F) showed that most of these don't belong in VUMA-core
— they belong in the WOMB UI engine layer or the VEEE UX-language
layer.

## Decision

**Adopt a three-layer architecture with explicit ownership boundaries.**

```
┌──────────────────────────────────────────────────────────────────────┐
│  Layer 3: VEEE (Verified Expression Evaluation Engine)                │
│  - UX language + compiler (.veee → VUMA AST)                          │
│  - Incremental computation, monotonicity types, algorithm/schedule    │
│  - Owner: VEEE team     Language: Rust (compiler)                     │
│  - Timeline: Months 18-26 (after VUMA v1 + WOMB v1)                   │
│  - Consumes: VUMA AST + e-graph + codegen                             │
│  - Provides: .veee source → verified VUMA programs                    │
└──────────────────────────────┬────────────────────────────────────────┘
                               │ compiles to VUMA AST
                               ▼
┌──────────────────────────────────────────────────────────────────────┐
│  Layer 2: WOMB (UI engine libraries, written in VUMA)                 │
│  - womb/ui/layout, womb/ui/render, womb/ui/text, womb/ui/ime,         │
│    womb/ui/a11y, womb/ui/event, womb/ui/animation, womb/ui/theme      │
│  - womb/crypto, womb/net, womb/kernel (already exist)                 │
│  - Owner: UI engine team  Language: VUMA                              │
│  - Timeline: Months 3-18 (parallel with VUMA)                         │
│  - Consumes: VUMA PMT arena, channels, capability model, codegen      │
│  - Provides: UI engine primitives that VEEE programs call             │
└──────────────────────────────┬────────────────────────────────────────┘
                               │ written in VUMA, compiled by VUMA
                               ▼
┌──────────────────────────────────────────────────────────────────────┐
│  Layer 1: VUMA (compiler + codegen + runtime + verification)          │
│  - Parser, SCG, IVE (Z3), IR, opt, regalloc, 19 backends, Lean proofs │
│  - Owner: VUMA compiler team  Language: Rust (compiler) + Lean        │
│  - Timeline: Months 1-18                                               │
│  - Consumes: nothing (foundational layer)                             │
│  - Provides: verified native codegen + PMT memory model               │
└──────────────────────────────────────────────────────────────────────┘
```

### Layer boundaries

**Layer 1: VUMA** — the systems language + compiler. This is what
lives in the `vuma` repo today: parser, SCG, IVE, IR, codegen, 19
backends, runtime, Lean proofs. VUMA does NOT include UI work (no
`womb/ui/`), GPU backends (no Vulkan/Metal/SPIR-V), or a higher-level
language (no VEEE compiler). The VUMA team owns the compiler and the
verification discipline.

**Layer 2: WOMB** — UI engine libraries written in VUMA. The `womb/`
directory already exists in the VUMA repo (195 `.vuma` files, ~117
kLOC) and contains a complete stdlib: crypto (HMAC-SHA256), net (HTTP,
WebSocket), kernel (IrqRing SPSC pattern), collections, string, etc.
The WOMB UI modules (`womb/ui/layout`, `womb/ui/render`, etc.) are
greenfield — none exist yet. The WOMB team writes VUMA code that
VUMA's compiler verifies and compiles.

**Layer 3: VEEE** — the UX language + compiler. VEEE is a separate
language (`.veee` files) that compiles to VUMA AST. VEEE programs get
full PMT verification (because they lower to VUMA, which is verified).
VEEE is built on incremental computation (Salsa), monotonicity types
(Datafun), algorithm/schedule separation (Halide), and e-graph
optimization (VUMA's existing `src/codegen/src/egraph.rs`). The VEEE
team owns the VEEE compiler (written in Rust) and the language design.

### Cross-layer dependencies

- **VEEE → VUMA**: VEEE compiles to VUMA AST. VEEE programs are
  verified by VUMA's IVE (Z3) and compiled by VUMA's 19 backends.
  VEEE's optimizer uses VUMA's e-graph.
- **WOMB → VUMA**: WOMB modules are VUMA source. They are compiled by
  VUMA and verified by VUMA's IVE. WOMB uses VUMA's PMT arena,
  channels, and capability model.
- **VEEE → WOMB**: VEEE programs call WOMB UI primitives
  (`womb/ui/layout/flex.vuma`, `womb/ui/render/vector.vuma`, etc.).
  VEEE's standard library is a thin wrapper over WOMB.
- **VUMA → WOMB (bootstrap)**: VUMA's capability model
  (`src/codegen/src/capability.rs`) uses `womb/crypto/mac_kdf/hmac.vuma`
  for HMAC-SHA256 (per ADR-0007). This is a bootstrap dependency: the
  compiler depends on its own output. This is acceptable because the
  WOMB HMAC is parity-tested against the Lean model and the Rust
  hand-translation.

### What this means for the catalog

The re-audit (Wave F) already moved V-01 (native backend), V-02
(rendering IR), V-08..V-32 (UI feature patches), V-27 (Metal), V-28
(GPU buffer), and V-GPU (GPU stack) to "out of scope (tracked
separately)." This ADR formalizes that they belong to Layer 2 (WOMB)
or Layer 3 (VEEE), not Layer 1 (VUMA).

Specifically:
- **V-01 (native backend)** → WOMB concern (host imports for
  Vulkan/Metal/IME/a11y). VUMA's existing 19 backends already produce
  native binaries.
- **V-02 (rendering IR instructions)** → WOMB concern (the IR
  extensions are for the WOMB renderer). VUMA's IR stays minimal.
- **V-08..V-32 (UI feature patches)** → WOMB concern (LayoutNode
  fields, font tables, animation, theme, etc.). These are VUMA source
  in `womb/ui/`, not VUMA compiler patches.
- **V-GPU (GPU stack)** → VEEE concern (GPU path via MLIR→SPIR-V, per
  ADR-0018). VUMA codegen stays CPU-only.
- **V-27 (Metal), V-28 (GPU buffer)** → VEEE concern (part of the
  GPU stack).

## Consequences

### Positive
- **Clear ownership** — each layer has a distinct owner, language, and
  timeline. No more "is this a VUMA patch or a WOMB patch?" ambiguity.
- **VUMA stays minimal** — the compiler doesn't grow UI or GPU code.
  The 5-external-crate policy (ADR-0010) is preserved.
- **WOMB is testable in isolation** — WOMB modules are VUMA programs,
  so they can be compiled and tested with the existing VUMA toolchain.
- **VEEE inherits verification for free** — VEEE programs get PMT
  verification because they lower to VUMA. No separate verifier needed.
- **Parallel development** — WOMB (months 3-18) and VEEE (months
  18-26) can proceed in parallel with VUMA (months 1-18) once the
  layer boundaries are locked.

### Negative
- **VEEE is 18+ months away** — no higher-level language until VUMA v1
  + WOMB v1 ship. UI developers must write VUMA directly in the
  interim.
- **Cross-layer bootstrap** — VUMA depends on WOMB's HMAC for the
  capability model. A breaking change in WOMB's HMAC could break the
  VUMA compiler. Mitigated by parity tests (`tests/pmt_parity_test.rs`).
- **Three repos or one?** — This ADR doesn't mandate a repo split.
  VUMA + WOMB can stay in one repo (WOMB is VUMA source). VEEE may be
  a separate repo (it's a Rust compiler). Decision deferred to a
  future ADR.

### Neutral
- The SWE package's `26-new-plans-three-layers.md` is the spiritual
  ancestor of this ADR. The SWE package used "Vell"; this ADR uses
  "VEEE" per ADR-0012.

## Alternatives Considered

### Alternative A: Single-layer (VUMA does everything)
Rejected — the re-audit showed that pulling UI and GPU work into
VUMA-core would balloon the compiler to 10× its current size, violate
the 5-crate dependency policy, and make verification intractable.

### Alternative B: Two-layer (VUMA + VEEE, no WOMB)
Rejected — VEEE programs need UI primitives to call. Without WOMB,
VEEE would either (a) inline UI primitives (bloating VEEE programs)
or (b) call C library UI code (losing verification). WOMB is the
verified UI primitive layer VEEE needs.

### Alternative C: Four-layer (split VUMA into "VUMA compiler" + "VUMA runtime")
Rejected — the VUMA compiler and runtime are tightly coupled (the
runtime is emitted by the compiler). Splitting them adds a boundary
without benefit.
