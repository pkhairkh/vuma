# ADR-0008: Fix `discharge_rate` denominator to include failed obligations (V-A3-3)

- **Status**: Accepted
- **Date**: 2026-08-01
- **Decision Maker**: VUMA compiler team

## Context

The VUMA compiler emits a one-line IVE summary on every `compile_dump`
invocation. The summary line is constructed at
`src/bin/compile_dump.rs:227-236`:

```rust
let summary = format!(
    "passed={} failed={} unverified={} total={} discharge_rate={}%",
    result.summary.passed,
    result.summary.failed,
    result.summary.unverified,
    result.summary.total_checked,
    (100 * result.summary.passed)
        .checked_div(result.summary.passed + result.summary.unverified)
        .unwrap_or(100)
);
```

(The task description cited the file as `src/codegen/src/compile_dump.rs:228`;
that path does not exist in the current tree. The actual location is
`src/bin/compile_dump.rs:228`, confirmed by direct read of the file and by
`grep -rn discharge_rate src/` returning only this hit.)

The formula at `compile_dump.rs:233-235` has two compounding defects,
surfaced independently by subagents A-3 and A-4 (see
`docs/research/A-3-ive-proofs-capability.md` §"V-A3-3" and
`docs/research/A-4-pipeline-runtime-tests-deps.md` §"V-NEW-3"):

1. **`failed` is excluded from the denominator.** The displayed `total=N`
   field uses `result.summary.total_checked` (line 232), which is the
   correct total of `passed + failed + unverified`. But the
   `discharge_rate=M%` percentage uses `passed + unverified` only (line
   234). For a program with 5 passed / 3 failed / 2 unverified, the
   displayed line reads `total=10 discharge_rate=71%` — but the
   architecture spec (`docs/architecture.md:76`) defines
   `discharge_rate` as "the fraction of proof obligations that the IVE
   discharged (via Z3 or trivial-true elision) over the **total
   obligations** collected from the program." The implementation does
   not match the spec. The metric overstates success in direct
   proportion to the failure count.

2. **`.unwrap_or(100)` returns 100% when every obligation fails.** If a
   program has `passed=0`, `failed=5`, `unverified=0`, the denominator
   is `0 + 0 = 0`; `checked_div(0)` returns `None`; and
   `.unwrap_or(100)` substitutes `100`. The displayed line reads
   `passed=0 failed=5 total=5 discharge_rate=100%` — a fully-failed
   program reports 100% discharge. This is mathematically nonsensical
   and actively misleading.

In practice the bug is partially masked because `compile_dump.rs:240`
hard-fails the build (`return Err(...)`) whenever
`result.overall == OverallVerdict::Fail` (i.e. whenever `failed > 0`),
so the misleading 100% / inflated % only escapes to the user on the
`Inconclusive` path (`compile_dump.rs:253-274`) where `failed == 0`
but `unverified > 0`. The bug is nonetheless real: anyone reading the
source, anyone running with `--allow-inconclusive`, and any future
caller that relaxes the hard-fail gate will see wrong numbers. The
`wave3_ive_discharge.md` audit (`scripts/archive/audit/wave3_ive_discharge.md:32`)
reports "Corpus-wide weighted discharge rate: 100.00%" because the
gold-standard suite has zero failures — so the bug never triggered
there, but it would trigger on any real program with violated
invariants.

There is also no regression test exercising the `discharge_rate`
computation on a program with `failed > 0`. The existing test
inventory (`tests/verification_tests.rs`, `tests/pmt_parity_test.rs`)
only feeds programs that pass IVE. The fix therefore must add a
regression test, not just patch the formula.

The metric is published in **every** compile summary
(`compile_dump.rs:238`: `eprintln!("IVE: {} {}", verdict, summary)`),
referenced in `README.md:75,124,134`, and re-stated in
`docs/architecture.md:73,76,107,429,444,454`. Its visibility is high;
its correctness is currently low.

## Decision

Apply a three-line fix to `src/bin/compile_dump.rs:233-235` plus a new
regression test.

1. **Change the denominator** from `result.summary.passed +
   result.summary.unverified` to `result.summary.total_checked`. The
   `total_checked` field already exists on `VerificationSummary` and
   already represents `passed + failed + unverified` (it is what the
   `total=N` field on the same line uses, so the displayed `total` and
   the denominator of `discharge_rate` will now agree). This is
   equivalent to the task-spec wording "discharged + failed + unknown"
   but reuses the existing field rather than recomputing the sum,
   avoiding a future divergence if a new obligation status is added.

2. **Replace `.unwrap_or(100)` with `.unwrap_or(0)`** so an
   all-failed (or genuinely zero-obligation) program reports `0%`,
   not `100%`. Zero obligations is a degenerate case that should
   surface as `0%` (or, ideally, be handled upstream by skipping the
   summary entirely — but `unwrap_or(0)` is the minimal safe
   substitution).

3. **Add a regression test** in `tests/verification_tests.rs` (or a
   new `tests/discharge_rate_test.rs`) that constructs a
   `VerificationSummary { passed: 0, failed: 5, unverified: 0,
   total_checked: 5 }` (and a second case with mixed `passed=5,
   failed=3, unverified=2, total_checked=10`), runs the same
   formatting path, and asserts the printed `discharge_rate` is `0%`
   (respectively `50%`), not `100%` (respectively `71%`). The test
   must cover the all-failed case explicitly to lock in fix (2).

The corrected formula reads:

```rust
(100 * result.summary.passed)
    .checked_div(result.summary.total_checked)
    .unwrap_or(0)
```

No other call site is affected. `compile_dump.rs` is the only consumer
of the `discharge_rate` string (verified by
`grep -rn discharge_rate src/`).

## Consequences

### Positive

- The headline `discharge_rate=N%` metric becomes honest. The
  displayed number will match both the spec
  (`docs/architecture.md:76`) and the displayed `total=N` field
  on the same line.
- An all-failed program no longer prints `discharge_rate=100%` —
  the most embarrassing manifestation of the bug is closed.
- The new regression test locks in the fix and protects against
  future reversion (the existing test suite had zero coverage of
  `failed > 0` paths through the formatter).
- Cost is ~3 lines of source change + ~20 lines of test code. No
  schema migration, no breaking change to the summary string format.

### Negative

- Any external consumer that scrapes the `discharge_rate=N%`
  substring from `compile_dump`'s stderr and treats it as a
  pass-rate KPI will see the number drop on programs that
  previously had `failed > 0` (and were running under
  `--allow-inconclusive`). The previous number was wrong; the new
  number is correct; but the delta is visible. The only known
  such consumer is the wave-3 audit report
  (`scripts/archive/audit/wave3_ive_discharge.md`), which is
  archived and not re-run.
- The bug was effectively invisible on the gold-standard suite
  (which has zero failures), so this fix does not move any test
  number — it is a correctness fix, not a pass-rate fix. Some
  stakeholders may question the priority.

### Neutral

- The `total=N` field on the same summary line is unchanged
  (already correct).
- The hard-fail gate at `compile_dump.rs:240` is unchanged; a
  program with `failed > 0` still aborts compilation unless
  `--allow-inconclusive` is passed.

## Alternatives Considered

### Alternative A: Keep the current denominator; rename the metric to `auto_discharge_rate_of_resolved`

This would relabel `discharge_rate` as "fraction of *resolved*
obligations that were auto-discharged" — making the formula
technically correct under a narrower definition. Rejected because
(a) the architecture spec (`docs/architecture.md:76`) and the
README (`README.md:75`) both describe the metric as the fraction
of *total* obligations discharged, so renaming would require
updating both docs to match a deliberately weaker contract;
(b) the metric is more useful to users when computed over the
total — the whole point of a discharge-rate KPI is to surface how
much proof work remains, and excluding `failed` from the
denominator hides exactly the failures the user most needs to see;
(c) the rename touches more files than the fix.

### Alternative B: Remove the `discharge_rate` metric entirely

The `passed=N failed=N unverified=N total=N` fields already convey
the underlying counts; a user can do the division themselves.
Rejected because (a) the metric is a load-bearing KPI cited in
`README.md:75,124,134` as evidence that VUMA's "V" actually
discharges obligations; (b) the wave-3 audit framework
(`scripts/archive/audit/wave3_ive_discharge.md`) and the
`scripts/archive/dod/wave_3.sh:16` CI grep both consume the
`discharge_rate=NN` substring; removing it breaks both; (c) when
computed correctly, the metric is a genuinely useful signal —
the bug is in the formula, not in the concept.
