# ADR-0022: Hand-written SPIR-V backend (supersedes ADR-0018's MLIR approach)

- **Status**: Accepted
- **Date**: 2026-08-01
- **Decision Maker**: VUMA project lead
- **Supersedes**: ADR-0018 (GPU path via MLIR→SPIR-V)
- **Superseded by**: (none)

## Context

ADR-0018 proposed using MLIR→SPIR-V for VEEE's GPU shader compilation.
The user correctly objected: **VUMA hand-writes everything** — lexer
NFA (no `logos`), TOML parser (no `toml`), JSON (no `serde_json`),
HMAC-SHA256 (no `sha2`/`hmac` crates), 19 backends (no LLVM), e-graph
(no `egg` crate). Pulling in MLIR (a massive C++ toolchain) would
violate the project's entire philosophy and the 5-crate policy
(ADR-0010).

The SWE package's own `16-build-vs-buy.md` is explicit:

| Component | Decision | Effort | Reference |
|-----------|----------|--------|-----------|
| Renderer (GPU path tessellation compute shader) | **Build (VUMA + SPIR-V)** | 6 weeks | Vello (study); Loop-Blinn algorithm |
| Renderer (SPIR-V build tooling) | **Build (Python script)** | 2 weeks | glslangValidator |
| Renderer (GPU host: Vulkan) | Wrap | 4 weeks | Vulkan spec |
| Renderer (GPU host: native Metal) | Wrap | 3 weeks | Metal spec |

The SWE package's `21-rfc-vector-engine.md` confirms the approach:
- "Pre-compiled SPIR-V for the compute shader (V-26, unchanged)"
- "The compute shader is ~500 LOC of GLSL, compiled to SPIR-V at build time"
- "Reference: vello's `euler.wgsl` / `cpu_shader.rs`"

So the plan was always: **hand-write the shader in GLSL, compile to
SPIR-V at build time using glslangValidator (a BSD-3 build-time tool),
embed the SPIR-V bytes as a const byte array (V-26)**. No MLIR, no
Cranelift, no runtime shader compilation.

ADR-0018 was wrong. This ADR corrects it.

## Decision

**The GPU path for VEEE uses pre-compiled SPIR-V embedded as const byte
arrays. No MLIR. No Cranelift. No runtime shader compilation.**

```
VEEE GPU kernel (GLSL source, hand-written)
    │
    ▼ Build-time: glslangValidator (BSD-3, build-time only, NOT a runtime dep)
SPIR-V bytecode (.spv file)
    │
    ▼ Build-time: Python script (per SWE package 16-build-vs-buy.md)
Const byte array literal (V-26: [u8; N] = [/* ... */])
    │
    ▼ VEEE compiler embeds in VUMA AST
VUMA AST (Lit::Bytes or Expr::ArrayLit)
    │
    ▼ VUMA pipeline (parse → SCG → IVE → IR → codegen → .rodata)
VUMA binary with embedded SPIR-V blob in .rodata
    │
    ▼ Runtime: WOMB renderer calls Vulkan/Metal/WebGPU host import
Native GPU execution
```

### Why this is consistent with VUMA's philosophy

1. **glslangValidator is a build-time tool, not a runtime dependency.**
   Like Z3 (build-time verifier) and QEMU (test-time emulator), it's
   installed on the build host but not linked into the binary. The
   5-crate policy (ADR-0010) applies to Rust crates, not build tools.
2. **The SPIR-V bytecode is a static const byte array.** VUMA's V-26
   (const byte arrays) is the only VUMA-side patch needed. No GPU IR
   instructions, no `Effect::Gpu`, no `Resource::GpuBuffer`.
3. **The shader is hand-written GLSL, not VEEE DSL.** The SWE package
   proposed a VEEE GPU DSL that lowers to MLIR; this ADR rejects that.
   The shader is GLSL, compiled by glslangValidator at build time. If
   a VEEE GPU DSL is desired later, it can lower to GLSL source (not
   MLIR) and feed into the same glslangValidator path.
4. **WOMB's `gpu_dispatch` is a host import.** `womb/ui/render/gpu_dispatch.vuma`
   calls `extern "C"` functions (Vulkan/Metal/WebGPU) that are
   provided by the C host runtime. No Rust GPU crates.

### What VUMA provides (small patch)

- **V-26: Const byte arrays** — parser support for `Lit::Bytes(Vec<u8>)`
  and `Expr::ArrayLit`. ~2 weeks (per catalog). This is the ONLY
  VUMA-side patch.
- The `.rodata` lowering (already exists for string literals; extend
  to byte arrays).

### What VEEE provides

- The `gpu kernel` syntax (optional — can be deferred; shaders can be
  hand-written GLSL files compiled by the build script).
- The `#[embed("file.spv")]` attribute that pulls in a pre-compiled
  SPIR-V file as a const byte array.
- The build script that invokes `glslangValidator` on `.glsl` files
  and produces `.spv` files.

### What WOMB provides

- `womb/ui/render/gpu_dispatch.vuma` — the `gpu_dispatch` host import:
  ```vuma
  extern "C" {
      transform vk_create_compute_pipeline_spirv(
          device: Address, spirv: Address, spirv_len: i64
      ) -> i64;
      transform vk_cmd_bind_pipeline(cmd: Address, pipeline: i64) -> i32;
      transform vk_cmd_dispatch(cmd: Address, x: i32, y: i32, z: i32) -> i32;
  }
  ```
- `womb/ui/render/vector.vuma` — the path-tessellation renderer that
  calls `gpu_dispatch` with the embedded SPIR-V blob.

### What the C host runtime provides

- Vulkan linkage (`libvulkan.so` / `vulkan-1.dll` / MoltenVK on macOS)
- Metal linkage (`-framework Metal` on macOS, via MoltenVK or native)
- WebGPU linkage (`libwgpu_native.so` for browser-embedded use)

These are "Wrap" decisions per the SWE package's `16-build-vs-buy.md`:
OS-provided GPU APIs wrapped by a thin C shim. No Rust GPU crates.

### What is NOT used (and why)

| Tool | Why not |
|------|---------|
| **MLIR** | C++ toolchain, massive, violates hand-write philosophy, no e-graphs benefit for shaders |
| **Cranelift** | Rust crate (would be 6th dep, violating ADR-0010); also unnecessary — VUMA's 19-backend codegen is the production path |
| **LLVM** | C++, no e-graphs, violates hand-write philosophy |
| **wgpu / gfx-rs** | Rust crates, violate "pure VUMA kernel, no Rust crates in kernel" (SWE package 16-build-vs-buy.md) |
| **shaderc / glslang rust bindings** | Rust crate wrappers around glslang; use the C tool directly via build script instead |
| **Runtime SPIR-V compilation** | Slow (50-200ms per shader), loses compile-time validation |

## Consequences

### Positive
- **Consistent with VUMA's hand-write-everything philosophy.** No MLIR,
  no Cranelift, no LLVM, no Rust GPU crates. The 5-crate policy is
  preserved (glslangValidator is a build-time tool, like Z3).
- **Simpler than ADR-0018.** No MLIR dialect design, no MLIR→SPIR-V
  pass, no MLIR build dependency. Just GLSL → glslangValidator → SPIR-V
  bytes → embed.
- **Matches the SWE package's plan.** `16-build-vs-buy.md` and
  `21-rfc-vector-engine.md` both specify this approach. ADR-0018
  deviated; this ADR realigns.
- **GPU shaders are pre-validated.** `spirv-val` (part of the SPIR-V
  tools) runs at build time, catching shader bugs before runtime.
- **No runtime shader compilation.** Shaders load as fast as any const
  byte array (memcpy from `.rodata`).

### Negative
- **Shaders are GLSL, not VEEE DSL.** A VEEE GPU DSL would be more
  ergonomic (type-checked, integrated with VEEE's incremental
  computation). But the SWE package's plan is GLSL + build script,
  and that's sufficient for v1. A VEEE GPU DSL can be added later
  (lowering to GLSL source) if needed.
- **glslangValidator is a build-time C++ dependency.** Like Z3, it must
  be installed on the build host. Acceptable but adds setup complexity.
- **GPU kernels are not PMT-verified.** Same as ADR-0018 — PMT is a CPU
  memory model. GPU kernel verification is deferred (would require a
  separate Lean model for GPU memory, out of scope for v1).

### Neutral
- ADR-0018 is superseded. Engineers should read THIS ADR, not ADR-0018.
  ADR-0018 is kept for history (append-only ADR practice per ADR-0011).

## Alternatives Considered

### Alternative A: MLIR→SPIR-V (the original ADR-0018)
Rejected — violates VUMA's hand-write philosophy, adds a massive C++
dependency, no benefit over glslangValidator for the shader sizes
involved (~500 LOC GLSL).

### Alternative B: Write a VUMA SPIR-V backend (generate SPIR-V from VUMA IR)
Rejected — 3-6 months of greenfield work (per Wave A audit) for
something glslangValidator already does. VUMA's codegen is CPU-only by
design; adding GPU support would bloat the compiler.

### Alternative C: Runtime GLSL compilation (shaderc at runtime)
Rejected — slow (50-200ms per shader), loses compile-time validation,
adds a runtime dependency.

### Alternative D: No GPU support (CPU-only rendering)
Rejected — the SWE package's vector renderer (RFC-21) requires GPU
path tessellation for acceptable performance. CPU-only rendering would
be too slow for production UI.
