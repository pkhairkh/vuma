# ADR-0001: Fix `bridge_type_to_ir_type` to map `f32`/`f64`

- **Status**: Accepted
- **Date**: 2026-08-01
- **Decision Maker**: VUMA compiler team
- **Supersedes**: (none)
- **Superseded by**: (none)

## Context

`bridge_type_to_ir_type` in `src/pipeline.rs:6503–6528` converts a parser
`vuma_parser::ast::Type` into a codegen `IRType`. It is called from two
sites (both inside `pipeline.rs`): the recursive `Type::Channel { inner, .. }`
arm at `:6524`, and `build_layout_registry` Pass 3 at `:6684` (which assigns
an `IRType` to every field of every registered layout).

The `Type::BDBase(name)` arm matches the eight integer primitives
(`i8`/`i16`/`i32`/`i64`/`u8`/`u16`/`u32`/`u64`) but omits `"f32"` and
`"f64"`. Both float names fall through to the catch-all `_ =>
vuma_codegen::ir::IRType::U64` at `src/pipeline.rs:6515`:

```rust
6503  fn bridge_type_to_ir_type(ty: &vuma_parser::ast::Type) -> vuma_codegen::ir::IRType {
6504      use vuma_parser::ast::Type;
6505      match ty {
6506          Type::BDBase(name) => match name.as_str() {
6507              "i8"  => vuma_codegen::ir::IRType::I8,
...
6514              "u64" => vuma_codegen::ir::IRType::U64,
6515              _    => vuma_codegen::ir::IRType::U64,   // ← "f32","f64" land here
6516          },
6517          Type::Ptr(_) | Type::RegionPtr { .. } => vuma_codegen::ir::IRType::U64,
...
6526          _    => vuma_codegen::ir::IRType::U64,
6527      }
6528  }
```

The `_ => IRType::U64` is silent. The downstream `build_layout_registry`
Pass 3 records the field's `IRType` as `U64` (`pipeline.rs:6684`), and
every consumer that reads that field type — most importantly the SCG→IR
lowering for `StateRead`/`StateWrite` (see ADR-0003) and every backend's
`Load`/`Store` lowering — emits an integer-width memory access instead of
a floating-point-width one. On x86_64, an `f32` state field is loaded
with `mov rax, [addr]` (8-byte integer load) instead of `movss xmm0,
[addr]` (4-byte float load); on every backend that uses the `ty` field
of `IRInstruction::Load`/`Store` to pick a register class (XMM vs GPR),
the float ends up in a GPR and float arithmetic on it silently produces
garbage.

Both the catalog (`docs/vuma-side-problem-catalog.md:56–82`, V-34) and
two Wave-A research subagents (`docs/research/A-2-ir-codegen.md:12–34`
and `docs/research/A-4-pipeline-runtime-tests-deps.md:12–45`) verified
this line-for-line against the current `main` HEAD. The catalog quotes
the buggy `:6506–6516` block; A-4's caller inventory confirms there are
exactly two callers, both internal to `pipeline.rs` — so the blast
radius of the fix is bounded.

This is the smallest, highest-confidence fix in the bridge-fix epic. It
is a prerequisite for ADR-0003 (the `StateRead`/`StateWrite` IRType
threading needs a correct `bridge_type_to_ir_type` to consult) and for
unblocking the `tests/gold_standard/float_mem/{f32,f64}_store_load.vuma`
gold-standard tests, which currently fail on all 17 non-wasm32 backends
with `MM=0` (per `docs/research/A-2-ir-codegen.md:234–245`).

## Decision

Add two arms to the `Type::BDBase(name)` inner match in
`bridge_type_to_ir_type`, mapping the float primitive names to the
already-existing `IRType::F32` / `IRType::F64` variants. Concretely,
insert before the `_ => IRType::U64` catch-all at
`src/pipeline.rs:6515`:

```rust
Type::BDBase(name) => match name.as_str() {
    "i8"  => vuma_codegen::ir::IRType::I8,
    "i16" => vuma_codegen::ir::IRType::I16,
    "i32" => vuma_codegen::ir::IRType::I32,
    "i64" => vuma_codegen::ir::IRType::I64,
    "u8"  => vuma_codegen::ir::IRType::U8,
    "u16" => vuma_codegen::ir::IRType::U16,
    "u32" => vuma_codegen::ir::IRType::U32,
    "u64" => vuma_codegen::ir::IRType::U64,
    "f32" => vuma_codegen::ir::IRType::F32,   // ← new
    "f64" => vuma_codegen::ir::IRType::F64,   // ← new
    _     => vuma_codegen::ir::IRType::U64,
},
```

The `IRType::F32` and `IRType::F64` variants already exist (see
`src/codegen/src/ir.rs:43–272`, where A-2 confirmed both are full enum
variants with `is_float()`/`is_register_passable()` predicates wired
through). No new IRType variant, no new file, no new caller. The
catch-all `_ => IRType::U64` is left in place — it still legitimately
catches pointer-typed and unknown layout-typed fields, which A-1
(`docs/research/A-1-parser-scg.md:244–294`) and A-2 confirmed should be
addressed separately (V-35 for layout names, V-42 for parser-side
propagation, V-44 for alignment).

This fix is intentionally minimal: it does **not** touch the catch-all
itself. The catch-all is addressed by ADR-0002 (parser-side
`type_size_from_name` and `type_alignment`) and ADR-0004 (pipeline-side
`build_pmt_layout_specs` migration and IVE-side `rederive_layout`).
Keeping the four fixes scoped to their four ADRs is what makes the
bridge-fix epic revertable in case of regression.

## Consequences

### Positive
- A `state.v: f32` field now records `IRType::F32` in the layout
  registry's per-field IRType slot, so backend `Load`/`Store` lowering
  can pick the correct memory width and register class without further
  plumbing.
- Unblocks ADR-0003 (`StateRead`/`StateWrite` IRType threading) — that
  ADR's `bridge_type_to_ir_type(field_type)` call returns a real `F32`/
  `F64` instead of `U64`.
- Unblocks the `tests/gold_standard/float_mem/{f32_store_load,
  f64_store_load,f64_struct_field}.vuma` tests once ADR-0003 also lands
  (these are currently `MM=0` on all 17 non-wasm32 backends).
- Two-line diff, ~3 days total effort including regression tests (per
  `docs/vuma-side-problem-catalog.md:81`).

### Negative
- A bare V-34 fix on its own does **not** make `f32`/`f64` state fields
  end-to-end functional — ADR-0003 must also land for `StateRead`/
  `StateWrite` to actually use the now-correct `IRType`. Landing V-34
  alone may surface latent bugs in backends that previously received
  `U64` for float fields and happened to encode that as a GPR move; a
  full audit of every backend's `IRType::F32`/`F64` `Load`/`Store` arm
  is required as part of the ADR-0003 work.
- The `_ => IRType::U64` catch-all at `:6515` remains; user-defined
  layout names (e.g. `Transform`) still map to `U64` here. This is by
  design — the catch-all is closed by ADR-0002 + ADR-0004, not here —
  but reviewers must be told that ADR-0001 is necessary-but-not-
  sufficient for the type-bridge bug class.

### Neutral
- No public API change. `bridge_type_to_ir_type` is `pub(crate)`-private
  (per A-4's caller inventory, no external callers).
- No Lean-proof impact: `proof/PMT/PmtInstr.lean:186–187` already
  declares `IRType.f32`/`f64` as bare tag constructors, and
  `:810–821` proves every arithmetic variant `True`-well-typed —
  A-3 (`docs/research/A-3-ive-proofs-capability.md`) confirmed no Lean
  change is needed.
- No test-snapshot impact until ADR-0003 lands; the `float_mem` tests
  will keep failing on the same backends until both ADRs ship.

## Alternatives Considered

### Alternative A: Unified `VumaType` refactor (replace string-based `Type::BDBase` with a typed enum)

The architectural root cause (per `docs/vuma-side-research-draft.md`
§5.1 and `docs/research/A-1-parser-scg.md:846–853`) is the three-way
string-based type representation: parser `Type::BDBase(String)`,
canonical SCG `String`, codegen `IRType`. Every bridge between them is
string matching with a `_ => <default>` arm, and every default arm is a
silent miscompile. Replacing the string with a unified `VumaType` enum
would eliminate V-34, V-35, V-42, V-44, V-46, V-03, and V-NEW-2 in one
stroke — but it is a 2–3 week refactor touching parser, SCG, IVE,
codegen, and every backend's `lower_instruction`. The
`docs/vuma-side-research-draft.md:506–512` open question recommends
doing the unified refactor **after** the bridge-fix epic, not before,
to ship fixes faster and avoid throwaway work. This ADR follows that
recommendation: ship the 1-line fix now, defer the refactor.

### Alternative B: Panic on unknown `Type::BDBase(name)` instead of returning `IRType::U64`

Make the `_ => IRType::U64` arm at `:6515` panic (or return `Result`):
unknown primitive names would surface as compile errors rather than
silent miscompiles. Rejected because (1) the catch-all is the only
thing keeping forward-referenced and user-defined layout names working
during `build_layout_registry` — `LayoutDef` items appear in source
order, and `bridge_type_to_ir_type` is called on field types whose
layout may be defined later in the same compilation unit; (2) the
right fix for "user-defined layout name passed to
`bridge_type_to_ir_type`" is to consult the layout registry
(`bridge_type_size_with_layouts` already does this for size), which is
ADR-0004's job, not ADR-0001's; (3) panicking in a compiler backend is
hostile — every existing `.vuma` program that uses a non-primitive
field type would crash instead of compiling. The `_ => U64` catch-all
must stay until ADR-0004 closes the layout-name path.
