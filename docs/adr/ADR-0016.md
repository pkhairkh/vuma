# ADR-0016: VEEE's incremental computation engine lives in VEEE, not VUMA

- **Status**: Accepted
- **Date**: 2026-08-01
- **Decision Maker**: VUMA project lead
- **Supersedes**: (none)
- **Superseded by**: (none)

## Context

VEEE's defining feature (per the SWE package's
`23-vell-redesign-research.md`) is **incremental computation** based
on Salsa/Adapton: demand-driven reactivity without virtual DOM
diffing. When a VEEE `signal` changes, only the UI parts that depend
on it re-evaluate — no tree-walk, no diffing.

There are two possible places this engine could live:

1. **In VEEE** — the VEEE compiler lowers `signal` primitives to VUMA
   `State<T>` + `layout_mark_dirty` calls. The incremental-computation
   runtime (the dependency graph, the invalidation algorithm) is
   VEEE-layer code, compiled to VUMA.

2. **In VUMA** — VUMA's IR gains a new `Signal` instruction and a new
   `Effect::Incremental` variant. The incremental-computation runtime
   is a VUMA runtime feature, like PMT.

The SWE package proposed option 1 (VEEE-layer) but didn't formally
decide. This ADR locks in option 1.

## Decision

**The incremental computation engine lives in VEEE (Layer 3), not in
VUMA (Layer 1).**

### How it works

1. **VEEE source** declares signals:
   ```veee
   signal count: i32 = 0
   signal label: String = derive { format!("Count: {}", count) }
   ```
   `count` is a root signal. `label` is a derived signal that depends
   on `count`.

2. **VEEE compiler** lowers each signal to:
   - A VUMA `layout` for the signal's value type:
     ```vuma
     layout SignalI32 = { version: u64, value: i32 }
     ```
   - A VUMA `transform` that reads the signal:
     ```vuma
     transform read_signal_i32(s: State<SignalI32>) -> i32 {
         return s.value;
     }
     ```
   - A VUMA `transform` that writes the signal and marks dependents
     dirty:
     ```vuma
     transform write_signal_i32(s: State<SignalI32>, v: i32) {
         s.value = v;
         s.version = s.version + 1;
         // mark_dirty is a WOMB call that walks the dependency graph
         mark_dirty(dependents_of(s));
     }
     ```

3. **WOMB** provides `mark_dirty` (`womb/ui/reactive/graph.vuma`) — a
   dependency-graph walker that flags dependent signals as stale. The
   dependency graph is built at VEEE compile time and stored as a
   static array in the PMT arena.

4. **VUMA** provides `State<T>` (typed-state API, PMT-verified) and
   the PMT arena. VUMA does NOT know about signals, dependency graphs,
   or incremental computation. VUMA just sees `State<SignalI32>` reads
   and writes, which it verifies like any other state access.

### Why VEEE-layer, not VUMA-layer

- **VUMA stays minimal.** Adding `Signal` to VUMA's IR would require
  new IR instructions, new Effect variants, new IVE verifier logic,
  new Lean proofs, and new backend lowering for all 19 backends. This
  is ~5,000 lines of VUMA code for a feature that only VEEE uses.
- **VUMA's PMT model is memory-safety, not reactivity.** Conflating
  the two would muddle the verification discipline. PMT proves
  `used + size ≤ capacity` (memory safety); incremental computation
  proves `dependent re-evaluates after dependency changes`
  (reactivity). These are different properties.
- **VEEE can experiment.** If the incremental-computation algorithm
  turns out to be wrong (e.g. Salsa's algorithm doesn't fit VEEE's
  use case), VEEE can change it without touching VUMA. If it were in
  VUMA, changing it would require a VUMA ADR and a compiler release.
- **WOMB provides the runtime primitives.** `mark_dirty` is a WOMB
  function, not a VUMA builtin. WOMB is the right layer for UI-runtime
  utilities.

### What VEEE's incremental computation engine contains

- **Dependency graph** — built at compile time from VEEE's `derive`
  annotations. Stored as a static array of `(signal_id, dependent_id)`
  pairs.
- **Invalidation algorithm** — seminaïve delta evaluation (per
  Datafun). When a root signal changes, walk the dependency graph and
  flag dependents as stale. When a derived signal is read, re-evaluate
  if stale.
- **Memoization** — derived signals cache their last-computed value
  and the version of their dependencies. If dependencies haven't
  changed, return the cached value.
- **Cycle detection** — at compile time, VEEE rejects cyclic
  dependencies (`signal a = derive { b }; signal b = derive { a }`).

### What VUMA provides (unchanged)

- `State<T>` typed-state API (PMT-verified)
- PMT arena (memory-safety verified by Lean)
- `Load`/`Store` IR instructions (with `__oob_trap` runtime bounds check)
- Z3 contract discharge (for `requires`/`ensures` on signal transforms)
- 19-backend codegen

### What WOMB provides

- `womb/ui/reactive/graph.vuma` — dependency-graph data structure
- `womb/ui/reactive/mark_dirty.vuma` — the `mark_dirty` transform
- `womb/ui/reactive/memo.vuma` — memoization cache

## Consequences

### Positive
- **VUMA stays minimal** — no IR changes, no new verifier, no new Lean
  proofs. The 5-crate policy is preserved.
- **VEEE can iterate on the algorithm** — changing from Salsa to
  Adapton (or vice versa) is a VEEE-compiler change, not a VUMA change.
- **Reactivity is verified through PMT** — signal reads/writes are
  `State<T>` accesses, so they get PMT memory-safety verification for
  free. The reactivity property (dependents re-evaluate) is a VEEE-layer
  invariant, not a VUMA-layer invariant.
- **WOMB's `mark_dirty` is testable in isolation** — it's a VUMA
  transform, so it can be compiled and tested with the existing
  toolchain.

### Negative
- **VEEE's compiler is more complex** — it must build the dependency
  graph at compile time and emit the `mark_dirty` calls. This is
  ~2,000 lines of Rust in the VEEE compiler.
- **Reactivity verification is weaker than memory safety.** PMT
  proves memory safety (no OOB). Reactivity (dependents re-evaluate)
  is proven by VEEE's type system (monotonicity types, per ADR-0017),
  not by Z3. This is a weaker guarantee — but it's the same guarantee
  React/SwiftUI/Compose provide (they don't formally verify
  reactivity either).

### Neutral
- The `derive` keyword is VEEE syntax, not VUMA syntax. VUMA's parser
  never sees it.

## Alternatives Considered

### Alternative A: Add `Signal` to VUMA's IR
Rejected — bloats VUMA, conflates memory safety with reactivity,
prevents VEEE iteration. See "Why VEEE-layer, not VUMA-layer" above.

### Alternative B: Use VUMA's e-graph for incremental computation
Rejected — the e-graph (`src/codegen/src/egraph.rs`) is an
optimization-time data structure, not a runtime reactivity engine.
It's used during compilation to find equivalent expressions; it
doesn't track runtime dependencies.

### Alternative C: Skip incremental computation; re-evaluate everything on every change
Rejected — this is the virtual DOM approach (React). It works but is
O(n) per change. VEEE's value proposition is O(dependents) per change.
Without incremental computation, VEEE is just another React.
