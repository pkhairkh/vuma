# ADR-0002: Fix `type_size_from_name` to consult layouts table (V-35 + V-44)

- **Status**: Accepted
- **Date**: 2026-08-01
- **Decision Maker**: VUMA compiler team
- **Supersedes**: (none)
- **Superseded by**: (none)

## Context

`type_size_from_name` in `src/parser/src/to_scg.rs:4057–4065` returns
the byte size of a type given its display string. It matches the eight
integer primitives plus `bool` and `ptr`, then falls through to `_ => 8`
for any unrecognized name:

```rust
4057  fn type_size_from_name(&self, name: &str) -> u64 {
4058      match name {
4059          "u8" | "i8" | "bool" => 1,
4060          "u16" | "i16" => 2,
4061          "u32" | "i32" | "f32" => 4,
4062          "u64" | "i64" | "f64" | "ptr" => 8,
4063          _ => 8,    // ← "Transform", "Point", "Rect", "WaitQueue", … land here
4064      }
4065  }
```

A `transform: Transform` field is treated as 8 bytes regardless of
`sizeof(Transform)`. Every field after it in the same layout gets a
wrong offset. This is the actual blocker for nested-struct layouts
(`docs/vuma-side-problem-catalog.md:84–116`, V-35).

The same anti-pattern exists in `type_alignment` at
`src/parser/src/to_scg.rs:3839–3865`, where the `Some(Type::BDBase(name))`
arm has an identical `_ => 8` catch-all at `:3846`. A-1 surfaced this as
V-44 — a "twin" of V-35 that corrupts alignment computation for any
user-defined type name (`docs/research/A-1-parser-scg.md:371–416`):

```rust
3839  fn type_alignment(&self, ty: Option<&Type>) -> u64 {
3840      match ty {
3841          Some(Type::BDBase(name)) => match name.as_str() {
3842              "u8" | "i8" | "bool" => 1,
3843              "u16" | "i16" => 2,
3844              "u32" | "i32" | "f32" => 4,
3845              "u64" | "i64" | "f64" => 8,
3846              _ => 8,    // ← "Transform" lands here
3847          },
3848          Some(Type::Ptr(_)) | Some(Type::RegionPtr { .. }) => 8,
...
3864      }
3865  }
```

**Caller inventory (from `docs/research/A-1-parser-scg.md:16–73` and
the worklog A-1 stage summary)**: `type_size_from_name` has 6 direct
callers in `to_scg.rs`:

| Line | Caller | Purpose |
|------|--------|---------|
| `:614` | `register_layout` (via `type_size(Type)`) | First-pass layout field sizes |
| `:3870` | `type_size(Type::BDBase(name))` dispatcher | Public `type_size` entry point |
| `:3981` | Deref/array probe (inner-type size for `*T` / `[T; N]`) | Deref size |
| `:3992` | Deref/array probe | Deref size |
| `:3996` | Deref/array probe | Deref size |
| `:4068–4069` | `is_lossless_cast(from, to)` | Cast width check |

Plus indirect propagation: `register_layout` calls `type_alignment`
(`:189`) and `type_size` (`:190`); `layout_total_size` (`:214–234`)
calls `type_alignment` (`:222`) and `type_size` (`:223`); `lookup_field`
(`:238–247`) calls `type_size` (`:242`); `resolve_field_chain`
(`:256+`) calls `lookup_field`. So the V-35 catch-all propagates into
the parser-side layout table (`self.layouts`) — A-1 named this V-42
(`docs/research/A-1-parser-scg.md:244–294`) — which is then consumed by
every `StateRead`/`StateWrite`/`StateTransform` lowering in `to_scg`.

The `_ => 8` arms are silent. A layout `Outer = { t: Transform, x: u32 }`
where `Transform` is a 24-byte layout is silently miscompiled: `t`
occupies offset 0 with size 8 (wrong), `x` is placed at offset 8 (wrong,
should be 24), and `Outer`'s `total_size` is recorded as 16 (wrong,
should be 28 rounded up to alignment). The downstream IVE-side
`verify_layout_consistency` (`src/ive/src/verification.rs:336–365`) is
structurally blind to this because `rederive_layout` (see ADR-0004)
intentionally reproduces the same `_ => 8` bug for parity.

This ADR fixes V-35 and V-44 together because they share the same
catch-all pattern, share the same fix (consult the layouts table), and
must land together for any nested-layout program to type-check
correctly — fixing only V-35 leaves the alignment table wrong, which
re-introduces the same miscompile via spurious padding.

## Decision

Add a `&self.layouts` lookup to the catch-all arms of both
`type_size_from_name` (`src/parser/src/to_scg.rs:4063`) and the
`Type::BDBase(name)` arm of `type_alignment` (`:3846`). The
`self.layouts` field already exists — it is populated by
`register_layout` (`:184–205`) and read by `lookup_layout` (`:208`),
`layout_total_size` (`:214–234`), and `lookup_field` (`:238–247`).

**Change 1 — `type_size_from_name` at `:4057–4065`**:

```rust
fn type_size_from_name(&self, name: &str) -> u64 {
    match name {
        "u8" | "i8" | "bool" => 1,
        "u16" | "i16" => 2,
        "u32" | "i32" | "f32" => 4,
        "u64" | "i64" | "f64" | "ptr" => 8,
        _ => self.layout_total_size(name),   // ← was: 8
    }
}
```

`layout_total_size` (`:214–234`) already does the right thing: it walks
`self.layouts[name]`, sums field sizes with alignment padding, and
tail-pads to `max_align`. It returns `0` when `name` is not a registered
layout (`:217`); for backward compatibility with the existing `_ => 8`
callers that pass primitive-like names (e.g. `"str"`, `"future"`,
`"task"`, `"null"`, `"unknown"` from `infer_expr_type` at
`:3887–3929`), the fallback must remain `8` for unknown names. So the
actual implementation is:

```rust
_ => {
    let registered = self.layout_total_size(name);
    if registered > 0 { registered } else { 8 }
}
```

**Change 2 — `type_alignment` at `:3839–3865`**: add the same
`self.layouts` lookup to the `_ => 8` arm at `:3846`. Because there is
no `layout_total_alignment` helper today, either (a) add one mirroring
`layout_total_size` (walks `self.layouts[name]` and returns
`max_align`), or (b) reuse `lookup_layout(name)` and compute `max_align`
inline. Approach (a) is preferred for symmetry with
`layout_total_size`; the helper is ~10 lines:

```rust
fn layout_total_alignment(&self, name: &str) -> u64 {
    let fields = match self.lookup_layout(name) {
        Some(f) => f,
        None => return 0,
    };
    fields
        .iter()
        .map(|(_, ftype, _)| self.type_alignment(Some(ftype)).max(1))
        .max()
        .unwrap_or(1)
}
```

Then the `type_alignment` arm becomes:

```rust
Some(Type::BDBase(name)) => match name.as_str() {
    "u8" | "i8" | "bool" => 1,
    "u16" | "i16" => 2,
    "u32" | "i32" | "f32" => 4,
    "u64" | "i64" | "f64" => 8,
    _ => {
        let registered = self.layout_total_alignment(name);
        if registered > 0 { registered } else { 8 }
    }
},
```

**Important — fix forward-reference handling in `register_layout`**:
`register_layout` (`:184–205`) is called by `convert()` (line 156)
once per `LayoutDef` in source order. When `LayoutDef Outer` is
processed before `LayoutDef Transform`, the call to
`self.type_alignment(Some(ftype=Type::BDBase("Transform")))` at
`:189` will return `8` (the fallback) because `self.layouts` does not
yet contain `Transform`. This is the same forward-reference problem
that ADR-0004 solves on the pipeline side with a two-pass loop. The
parser-side fix mirrors it: either (a) make `register_layout`
**deferred** (store the raw `(name, fields)` and compute
offset/align/size lazily via `layout_total_size` /
`layout_total_alignment` on first read), or (b) add a two-pass
pre-walk before `register_layout` is called. Approach (a) is simpler
because `register_layout`'s output is already only consumed via
`lookup_layout` / `layout_total_size` / `lookup_field` (all of which
are call-site-driven), so the stored `(name, ftype, foffset)` tuples
in `self.layouts` can simply have `foffset` lazily recomputed on first
read. The simpler interim implementation: in `register_layout`, store
the raw field list without computing offsets, and have `lookup_field`
+ `layout_total_size` compute offsets on demand using the
fully-populated `self.layouts` table.

**Scope note**: this ADR does **not** fix V-42 ("register_layout
propagates V-35 to layout field offsets and total_size") as a separate
work item — per `docs/research/A-1-parser-scg.md:251–253`, V-42 is
"additional blast radius for V-35", not a separate bug. Fixing V-35
correctly (with the deferred-offsets or two-pass pre-walk above) closes
V-42 automatically. Likewise V-43 (`infer_expr_type` returns variable
names not types — `docs/research/A-1-parser-scg.md`, §2.1 table) is
out of scope: it is a P1 sibling that compounds V-35 but is not
load-bearing for nested-layout size/alignment correctness.

## Consequences

### Positive
- `layout Outer = { t: Transform, x: u32 }` now records `t`'s size as
  `sizeof(Transform)` and `x`'s offset as `align_up(sizeof(Transform),
  alignof(u32))`, matching the codegen-side `build_layout_registry`
  output (ADR-0004).
- Closes V-35 (size), V-44 (alignment), and V-42 (propagation) in one
  ADR — three of the eight P0 entries in the type-bridge cluster
  (`docs/vuma-side-research-draft.md:130–137`).
- Unblocks every WOMB layout that nests another layout as a field
  (channels holding protocol state, UI nodes holding `Transform`/
  `Rect`).
- The IVE-side `verify_layout_consistency` becomes a real check
  rather than a no-op: once ADR-0004 lands and `rederive_layout` is
  migrated to use the layouts table, the parser-side and pipeline-side
  layout tables will agree.

### Negative
- `register_layout`'s forward-reference behavior changes. Any code
  that today reads `self.layouts[name]`'s precomputed `foffset` field
  immediately after `register_layout` returns — but before all
  `LayoutDef`s are registered — will see stale offsets under the
  deferred-offsets approach. The audit (A-1's caller inventory) shows
  no such reader exists in `to_scg.rs` (all reads go through
  `lookup_field` / `layout_total_size`, which would recompute), but
  the regression-test plan below must cover this.
- The fallback `8` for genuinely unknown names (`"str"`, `"future"`,
  `"task"`, `"null"`, `"unknown"` returned by `infer_expr_type`) is
  preserved for backward compatibility — these are not real types and
  should never have been passed to `type_size_from_name` in the first
  place, but they are, and changing that is V-43's job.
- The `_ => 8` catch-all in `type_size_from_name` remains, just with
  a `layout_total_size` lookup prepended. A future unified `VumaType`
  refactor (per `docs/vuma-side-research-draft.md:506–512`) would
  eliminate it entirely; this ADR is a tactical fix, not the
  architectural one.

### Neutral
- No public API change. `type_size_from_name` and `type_alignment` are
  private to `AstToScg` (per A-1's caller inventory, all callers are
  inside `to_scg.rs`).
- No IR/codegen impact — this is parser-only. The downstream effect
  on `build_pmt_layout_specs` and `build_layout_registry` is via the
  AST `LayoutDef` items they consume, which are unchanged; those
  functions have their own `_ => 8` arms addressed by ADR-0004.
- No Lean-proof impact — the parser's `self.layouts` table is not
  modeled in any Lean proof.
- Regression-test plan: per `docs/research/A-1-parser-scg.md:682–687`,
  add three tests in `parser/tests/edge_cases.rs`:
  1. `layout Outer = { t: Transform, x: u32 }` where `Transform` is
     a 24-byte layout — assert `StructDefNode` for `Outer` has
     `total_size >= 24` and `x`'s `offset >= 24` (covers V-35 + V-42).
  2. `layout ByteBag = { a: u8, b: u8, c: u8 }` — assert
     `StructDefNode`'s `alignment == 1` and `total_size == 3` (covers
     V-44).
  3. Forward-reference variant: `layout Outer = { t: Inner, x: u32 }`
     defined before `layout Inner = { a: u64 }` — assert `t`'s size
     is 8 and `x`'s offset is 8 (covers the deferred-offsets path).

## Alternatives Considered

### Alternative A: Unified `VumaType` refactor (replace string-based `Type::BDBase` with a typed enum)

Same as ADR-0001 Alternative A. The unified `VumaType` enum (per
`docs/vuma-side-research-draft.md:142–147`) would eliminate V-35,
V-44, V-42, and four other bridge bugs in one stroke. Estimated 2–3
weeks. Rejected for the bridge-fix epic — ship the targeted fix now,
evaluate the refactor after (per `docs/vuma-side-research-draft.md:
506–512`).

### Alternative B: Make `_ => 8` a panic (`unreachable!()` or `Result`)

Force unknown type names to surface as compile errors rather than
silent 8-byte defaults. Rejected because:
1. `register_layout` is called once per `LayoutDef` in source order
   (line 156 of `to_scg.rs`); a layout that references another layout
   defined later in the source would panic during the first pass.
   A-1's analysis (`docs/research/A-1-parser-scg.md:280–294`)
   explicitly notes this — "register_layout is the pre-pass that
   builds `self.layouts`" — and the two-pass / deferred-offsets
   approach in this ADR's Decision section is the proper fix.
2. `infer_expr_type` (`:3887–3929`) returns strings like `"str"`,
   `"future"`, `"task"`, `"null"`, `"unknown"` that are not real
   types and would panic. Those are V-43's problem to fix; making
   V-35 panic on them would break every program that uses an
   `Expr::Async`/`Spawn`/`Null` today.
3. The fallback `8` for genuinely unknown names is load-bearing for
   forward references during `register_layout`; removing it requires
   the deferred-offsets refactor, which is what this ADR specifies.

### Alternative C: Fix V-35 only, defer V-44 to a separate ADR

Treat V-44 (`type_alignment` `_ => 8`) as a separate work item. Rejected
because V-35 and V-44 are the same pattern in the same function
(`type_alignment` is the alignment-side twin of `type_size_from_name`
— `docs/research/A-1-parser-scg.md:371–416`), share the same fix
(consult `self.layouts`), and must land together for nested layouts
to type-check. Fixing only V-35 leaves the alignment table wrong,
which reintroduces the same miscompile via spurious inter-field
padding. The cost of bundling V-44 into this ADR is ~10 lines and one
helper function; the cost of splitting is a coordinated two-PR landing
with a broken intermediate state.
