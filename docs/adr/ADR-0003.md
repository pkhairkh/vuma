# ADR-0003: Thread `IRType` and offset through `StateRead`/`StateWrite` (V-36 + V-A2-1)

- **Status**: Accepted
- **Date**: 2026-08-01
- **Decision Maker**: VUMA compiler team
- **Supersedes**: (none)
- **Superseded by**: (none)

## Context

The `PmtOpStmt::StateRead` and `PmtOpStmt::StateWrite` lowering in
`src/codegen/src/scg_to_ir.rs:6002–6028` hardcodes both the field
offset (`0`) and the field type (`IRType::I64`) on every state access:

```rust
6002  // StateRead(src, layout, field) → Load(offset=0 placeholder)
6003  P::StateRead { dst, src, layout_name, field_name } => {
6004      let addr = self.resolve_expr(src, names, ir_func)?;
6005      let dst_vreg = self.alloc_vreg();
6006      ir_func.register_vreg(VirtualRegister::named(dst_vreg, dst));
6007      names.insert(dst.clone(), dst_vreg);
6008      ir_func.current_block().push(IRInstruction::Load {
6009          dst: IRValue::Register(dst_vreg),
6010          addr,
6011          offset: 0,                // ← placeholder
6012          ty: IRType::I64,          // ← HARDCODED (V-36)
6013      });
6014      let _ = (layout_name, field_name);    // ← discarded
6015      Ok(())
6016  }
6017  // StateWrite(ptr, val, layout, field) → Store(offset=0 placeholder)
6018  P::StateWrite { ptr, val, layout_name, field_name } => {
6019      let addr = self.resolve_expr(ptr, names, ir_func)?;
6020      let value = self.resolve_expr(val, names, ir_func)?;
6021      ir_func.current_block().push(IRInstruction::Store {
6022          value, addr,
6023          offset: 0,                // ← placeholder
6024          ty: IRType::I64,          // ← HARDCODED (V-36)
6025      });
6026      let _ = (layout_name, field_name);    // ← discarded
6027      Ok(())
6028  }
```

The catalog (`docs/vuma-side-problem-catalog.md:118–150`, V-36)
verified this line-for-line. Two Wave-A subagents confirmed and
amplified:

- **A-2** (`docs/research/A-2-ir-codegen.md:35–74`): the underlying
  problem is worse than cataloged. `StateInit` at `:5990–6000`,
  `ArenaNew` at `:6044–6054`, and `ArenaAlloc` at `:6056–6067` all
  emit `IRInstruction::Alloc { dst, size: 0 }` with the comment
  "placeholder — BD LayoutRegistry not plumbed here". The x86_64
  backend's `Alloc` lowering at
  `src/codegen/src/x86_64/stack_slot_isel.rs:1059–1067` computes the
  aligned stack size as `(*size as i32 + 15) & !15` — for `size=0`
  this gives **0**, not 16. The alloc pointer
  (`alloc_offsets[id]` at `:1088–1089`) then points to `[rbp - 0]` =
  the saved RBP, so subsequent `StateWrite`/`StateRead` clobber the
  saved frame pointer. A-2 named this V-A2-1 and listed it as P0:
  "blocks the entire typed-state API"
  (`docs/research/A-2-ir-codegen.md:214–250`).
- **A-4** confirmed the test impact:
  `tests/gold_standard/float_mem/{f32_store_load,f64_store_load,
  f64_struct_field}.vuma` all fail with `MM=0` on **all 17 non-wasm32
  backends** — the strongest signal of a systematic bug in the entire
  failure file (per `docs/research/A-2-ir-codegen.md:234–245` and the
  worklog A-4 stage summary).

The compound effect: even after ADR-0001 (`bridge_type_to_ir_type`
returns real `F32`/`F64`) lands, a `state.v: f32` field still emits:

1. `Alloc { size: 0 }` (V-A2-1) — the state buffer is zero-sized.
2. `Store { ty: IRType::I64, offset: 0 }` (V-36) — the store writes
   8 bytes of integer-typed data at the wrong offset, clobbering the
   saved frame pointer.
3. `Load { ty: IRType::I64, offset: 0 }` (V-36) — the load reads 8
   bytes of integer-typed data from the wrong offset, returning
   whatever is at `[rbp]`.

So ADR-0001 alone does not make `f32`/`f64` state fields work. ADR-0003
must land in lockstep to actually consume the now-correct `IRType`
from `bridge_type_to_ir_type` and to allocate a real-sized buffer for
the state.

A-2's fix sketch (`docs/research/A-2-ir-codegen.md:247`) recommends
threading the same `layout_sizes: &HashMap<String, u64>` table that
ADR-0004 produces for `build_pmt_layout_specs` into `IRBuilder`, plus
a per-field `(offset, IRType)` table so `StateRead`/`StateWrite` can
look up `layout_name` + `field_name` and get `(offset, ty)` without
re-deriving. The plumbing is shared between V-36 and V-A2-1, so they
must land in the same ADR.

## Decision

Thread two pieces of layout context into the SCG→IR builder
(`IRBuilder` in `src/codegen/src/scg_to_ir.rs`):

1. **`layout_sizes: &HashMap<String, u64>`** — the same table that
   `build_layout_registry` (pipeline.rs:6641–6669) already produces.
   This is the pre-computed `total_size` for every registered layout
   name. Used by the V-A2-1 fix below.
2. **`layout_fields: &HashMap<String, Vec<(String /*field_name*/,
   u64 /*offset*/, u64 /*size*/, IRType /*ty*/)>>`** — a per-layout
   per-field table giving `(offset, size, IRType)`. Used by the V-36
   fix below. This is a thin projection of `build_layout_registry`'s
   existing output (which already stores `(String, IRType, u64, u64,
   String)` tuples per field at `pipeline.rs:6676–6689`).

Both tables are produced in `build_layout_registry` (ADR-0004's
two-pass algorithm) and threaded into `IRBuilder::new(...)` via a new
constructor parameter. The `IRBuilder` already receives a reference
to the program-level context; this adds two more `&HashMap` fields.

**Change 1 — V-36: `StateRead` at `:6002–6015`**:

Replace the hardcoded `offset: 0, ty: IRType::I64` with a lookup:

```rust
P::StateRead { dst, src, layout_name, field_name } => {
    let addr = self.resolve_expr(src, names, ir_func)?;
    let dst_vreg = self.alloc_vreg();
    ir_func.register_vreg(VirtualRegister::named(dst_vreg, dst));
    names.insert(dst.clone(), dst_vreg);

    // V-36 fix: look up (offset, IRType) from the layout table.
    let (offset, ty) = self.lookup_field_offset_type(layout_name, field_name);
    ir_func.current_block().push(IRInstruction::Load {
        dst: IRValue::Register(dst_vreg),
        addr,
        offset,         // ← was: 0
        ty,             // ← was: IRType::I64
    });
    Ok(())
}
```

Where `lookup_field_offset_type` is a new `IRBuilder` method:

```rust
fn lookup_field_offset_type(
    &self,
    layout_name: &str,
    field_name: &str,
) -> (i64, IRType) {
    // Walk self.layout_fields[layout_name] for field_name; return
    // (offset as i64, ty). Fallback: (0, IRType::I64) for unknown
    // layouts/fields (preserves existing behavior on malformed input).
    match self.layout_fields.get(layout_name) {
        Some(fields) => {
            for (name, offset, _size, ty) in fields {
                if name == field_name {
                    return (*offset as i64, ty.clone());
                }
            }
            (0, IRType::I64)   // field not found — keep current behavior
        }
        None => (0, IRType::I64),   // layout not found — keep current behavior
    }
}
```

The fallback is preserved deliberately so that programs with malformed
state accesses (e.g. a `StateRead` against a layout name the parser
didn't see) keep the current `(0, I64)` behavior rather than panicking.
This keeps the ADR scoped to the type-bridge fix and avoids a
behavior change for unverified programs.

**Change 2 — V-36: `StateWrite` at `:6017–6028`**: identical
transformation — replace `offset: 0, ty: IRType::I64` with the same
`lookup_field_offset_type(layout_name, field_name)` call. `Store`
shares the `(offset, ty)` shape with `Load`.

**Change 3 — V-A2-1: `StateInit` at `:5990–6000`**: replace the
hardcoded `size: 0` with a lookup against `self.layout_sizes`:

```rust
P::StateInit { dst, layout_name } => {
    let dst_vreg = self.alloc_vreg();
    ir_func.register_vreg(VirtualRegister::named(dst_vreg, dst));
    names.insert(dst.clone(), dst_vreg);

    // V-A2-1 fix: look up the layout's real total_size.
    let size = self
        .layout_sizes
        .get(layout_name)
        .copied()
        .unwrap_or(0);   // unknown layout — keep current behavior
    ir_func.current_block().push(IRInstruction::Alloc {
        dst: IRValue::Register(dst_vreg),
        size,             // ← was: 0
    });
    Ok(())
}
```

**Change 4 — V-A2-1: `ArenaNew` at `:6044–6054`**: the `capacity`
expression is the size argument; the current code resolves it via
`self.resolve_expr(capacity, ...)` then **discards** the result
(`let _ = self.resolve_expr(capacity, names, ir_func)?;` at `:6045`).
The fix is to keep the resolved capacity and use it as the Alloc size:

```rust
P::ArenaNew { dst, capacity } => {
    let capacity_val = self.resolve_expr(capacity, names, ir_func)?;
    let dst_vreg = self.alloc_vreg();
    ir_func.register_vreg(VirtualRegister::named(dst_vreg, dst));
    names.insert(dst.clone(), dst_vreg);

    // V-A2-1 fix: use the capacity expression's value, not a
    // placeholder. If capacity is a literal, lower it directly;
    // otherwise emit a runtime Alloc-with-dynamic-size path.
    let size = self.eval_const_int_expr(&capacity_val)
        .or_else(|| self.layout_sizes.get("__default_arena__").copied())
        .unwrap_or(0);
    ir_func.current_block().push(IRInstruction::Alloc {
        dst: IRValue::Register(dst_vreg),
        size,             // ← was: 0
    });
    Ok(())
}
```

(If `eval_const_int_expr` returns `None` for non-literal capacities,
the fallback path is to emit a `Call { func: "__vuma_alloc", args:
[capacity_val] }` node instead — see `docs/research/A-4-pipeline-
runtime-tests-deps.md:451–456` for the analogous V-NEW-1 pattern. The
exact fallback strategy for `ArenaNew` is left to the implementer; the
load-bearing requirement is that the placeholder `size: 0` is gone.)

**Change 5 — V-A2-1: `ArenaAlloc` at `:6056–6067`**: same fix as
`StateInit` — look up `layout_name` in `self.layout_sizes`:

```rust
P::ArenaAlloc { dst, arena, layout_name } => {
    let _ = self.resolve_expr(arena, names, ir_func)?;
    let dst_vreg = self.alloc_vreg();
    ir_func.register_vreg(VirtualRegister::named(dst_vreg, dst));
    names.insert(dst.clone(), dst_vreg);

    // V-A2-1 fix: look up the layout's real total_size.
    let size = self
        .layout_sizes
        .get(layout_name)
        .copied()
        .unwrap_or(0);
    ir_func.current_block().push(IRInstruction::Alloc {
        dst: IRValue::Register(dst_vreg),
        size,             // ← was: 0
    });
    Ok(())
}
```

**Scope note**: this ADR does **not** fix V-A2-2
(`inttofloat`/`floattoint` hardcoded to `I64 ↔ F64` at
`scg_to_ir.rs:5250–5291`, P1) — that is a separate cast-lowering bug
that requires its own plumbing (threading source/dest types from the
SCG cast node, per `docs/research/A-2-ir-codegen.md:281`). V-A2-2 is
not a blocker for the typed-state API and is deferred to a follow-up
ADR.

## Consequences

### Positive
- A `state.v: f32` field, after ADR-0001 + ADR-0002 + ADR-0004 also
  land, now emits:
  1. `Alloc { size: sizeof(Layout) }` (V-A2-1 fix) — the buffer is
     real-sized.
  2. `Store { ty: IRType::F32, offset: real_offset }` (V-36 fix) —
     the store writes 4 bytes of float-typed data at the correct
     offset.
  3. `Load { ty: IRType::F32, offset: real_offset }` (V-36 fix) —
     the load reads 4 bytes of float-typed data from the correct
     offset, into an XMM register on x86_64 / a V register on
     AArch64.
- Unblocks `tests/gold_standard/float_mem/{f32_store_load,
  f64_store_load,f64_struct_field}.vuma` — currently `MM=0` on all
  17 non-wasm32 backends.
- Unblocks `tests/gold_standard/{pmt_state,pmt_session,pointers,
  atomics}/*` tests that use `state_new(Layout)`.
- Closes V-36 and V-A2-1 in one ADR — both share the same plumbing
  (`layout_sizes` + `layout_fields` threaded into `IRBuilder`), so
  bundling avoids a broken intermediate state.

### Negative
- `IRBuilder::new(...)` gains two new `&HashMap` parameters. Every
  constructor call site (the audit found them only in
  `src/codegen/src/scg_to_ir.rs` itself — A-2's caller inventory
  confirmed `IRBuilder` is `pub(crate)`-internal) must be updated to
  pass the new tables. The pipeline.rs `compile_*` entry points that
  instantiate `IRBuilder` (per the `build_layout_registry` callsite at
  `:5810`) must thread the layout tables through.
- The fallback `(0, IRType::I64)` for unknown layouts/fields is
  preserved. This means a `StateRead` against a layout name the
  parser didn't register (e.g. a typo, or a forward reference the
  parser's `self.layouts` doesn't yet contain) still silently
  miscompiles. The proper fix for that is ADR-0002 + ADR-0004
  (parser-side and pipeline-side layouts table) — once those land,
  the fallback path is unreachable for well-formed programs.
- The `ArenaNew` non-literal-capacity path requires a runtime
  allocation call (`__vuma_alloc`), which is partially out-of-scope
  for this ADR (it overlaps with V-NEW-1's `allocate(<non-literal>)`
  fix at `pipeline.rs:9228`). The implementer may choose to land
  `ArenaNew`'s literal-only path in this ADR and defer the
  non-literal path to a follow-up. Either way, the placeholder
  `size: 0` is gone for the literal case.
- Test coverage gap (per `docs/research/A-2-ir-codegen.md:584–590`):
  zero code-level regression tests exist for V-36 or V-A2-1 today.
  The `float_mem/*` gold-standard tests would catch the regression
  at the test-matrix level but are not in `cargo test`. The
  regression-test plan below must add code-level tests.

### Neutral
- No public API change. `IRBuilder` is `pub(crate)`-internal; the new
  parameters are not exposed.
- No Lean-proof impact. The Lean `PMT/PmtInstr.lean` model already
  has `IRType.f32`/`f64` and treats every arithmetic variant as
  `True`-well-typed (per A-3's audit at
  `docs/research/A-3-ive-proofs-capability.md`).
- No backend-specific changes. Every backend's `Load`/`Store`/`Alloc`
  lowering already receives the `ty`/`size` field from the IR
  instruction; the backends do not need to change. The behavioral
  change is: backends now see correct `ty`/`size` values where they
  previously saw `IRType::I64` / `0`.
- Regression-test plan: add to `src/tests/src/regression.rs` (per
  A-2's gap analysis at `docs/research/A-2-ir-codegen.md:619`):
  1. `test_state_read_f32_field_type` — build a small program with
     `layout Cell = { v: f32 }; state c = state_new(Cell); c.v = 7.5;
     return floattoint(c.v)`, compile to IR, assert the emitted
     `Load` has `ty: IRType::F32` and `offset: 0`.
  2. `test_state_init_alloc_size_nonzero` — same program, assert the
     emitted `Alloc` has `size: 4` (sizeof(f32)) rather than `0`.
  3. `test_state_write_offset_for_nested_layout` — `layout Inner =
     { a: u64 }; layout Outer = { i: Inner, x: u32 }` (after
     ADR-0002 lands so the parser computes `Inner`'s size correctly),
     assert `c.x = 5` emits `Store { offset: 8, ty: IRType::U32 }`.

## Alternatives Considered

### Alternative A: Cast `I64`→`F32` at use site (leave `StateRead` hardcoded to `IRType::I64`)

Keep `StateRead` emitting `Load { ty: IRType::I64 }` and insert a
synthetic `Cast { kind: IntToFloat, src_ty: I64, dst_ty: F32 }` at
every consumer of a float-typed state field. Rejected because:
1. Loses type safety — the `Cast` is a no-op at the IR level (the bits
   are already `f32` in memory) but the `IntToFloat` CastKind is
   semantically an integer-to-float conversion, which backends lower
   via `cvtsi2ss` (x86_64) or `scvtf` (AArch64) — reinterpreting the
   bits through the FP unit's int→float path, which gives wrong
   results for values whose bit pattern isn't a valid `i64`.
2. Ugly — every `state.measured_w + 1.0` expression grows an extra
   `Cast` node, polluting the IR and complicating every optimization
   pass.
3. Does not fix V-A2-1 (the `Alloc { size: 0 }` placeholder) — that
   fix requires the same `layout_sizes` plumbing this ADR specifies
   anyway, so the cast approach saves no plumbing work.

### Alternative B: Defer V-36 and V-A2-1 until the unified `VumaType` refactor lands

Same logic as ADR-0001 Alternative A and ADR-0002 Alternative A.
Rejected because the `float_mem/*` tests are currently `MM=0` on all
17 non-wasm32 backends — this is the strongest signal of a systematic
bug in the entire `test_results/failures.txt` (per A-4's stage
summary). Waiting 2–3 weeks for the unified refactor before fixing it
is unacceptable; the bridge-fix epic is the prerequisite for the
refactor, not the other way around (per
`docs/vuma-side-research-draft.md:506–512`).

### Alternative C: Fix V-36 only, defer V-A2-1 to a separate ADR

Treat V-A2-1 (`Alloc { size: 0 }`) as a separate work item. Rejected
because V-36 and V-A2-1 share the same `layout_sizes` plumbing into
`IRBuilder` (per A-2's fix sketch at
`docs/research/A-2-ir-codegen.md:247–248` — "thread `BD
LayoutRegistry` (or a pre-computed `layout_sizes: &HashMap<String,
u64>` table — the same one V-03 needs) into `IRBuilder`"). Splitting
them would either (a) duplicate the plumbing, or (b) leave V-A2-1
broken until the follow-up ADR lands, in which case `StateRead` /
`StateWrite` would read/write through a zero-sized buffer — the
correct `IRType` would be applied to the wrong memory location.
Bundling is the only coherent option.
