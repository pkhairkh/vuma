# ADR-0025: Extend SIMD coverage incrementally — add ops as text-shaper benchmarks demand them

- **Status**: Accepted
- **Date**: 2026-08-01
- **Decision Maker**: VUMA compiler team
- **Supersedes**: The "deferred — needs benchmarking data" status of
  V-13 in the original catalog
- **Superseded by**: (none)

## Context

V-13 (SIMD coverage is narrow) was deferred in the original catalog
with the note "needs benchmarking data first." The user asked: "If you
need benchmark data first check if anywhere available."

### Existing benchmark data

VUMA already has substantial SIMD-relevant benchmark infrastructure:

1. **Per-ISA latency tables** (`src/codegen/src/target_desc.rs`):
   Every backend's `LatencyTable` includes `fp_simd` category entries.
   These tables are tested by `tests/latency_table_tests.rs` and
   `tests/backend_latency_tests.rs`, which verify that each backend
   uses its real ISA-specific table (not the `default_ooo()` fallback).
   The `fp_simd` entries give us the latency of SIMD ops on each ISA —
   this IS benchmark data, just at the instruction level rather than
   the workload level.

2. **FP benchmark programs**:
   - `tests/gold_standard/float_advanced/fp_bench.vuma` — 1M f64
     additions in a loop. Tests FP register pressure and `inttofloat`.
   - `examples/fp_bench.vuma` — another FP benchmark.
   - `tests/gold_standard/ipc/bench.vuma` — IPC throughput (not SIMD-
     relevant, but shows the benchmark pattern).

3. **Existing SIMD lowering** (verified by F-3):
   - **x86_64** (`src/codegen/src/x86_64/stack_slot_isel.rs:3493-3527`):
     `paddq` (SSE2), `vpaddq` (AVX), `psubd` (SSE2), `pmulld` (SSE4.1).
     Supports `{Add, Sub, Mul} × {i32, i64}`.
   - **AArch64** (`src/codegen/src/aarch64/mod.rs:3452-3491`): NEON
     `add.4s`, `sub.4s`, `mul.4s`, `mla.4s`, `ld1.4s`, `st1.4s`.
     Supports `{Add, Sub, Mul, Mla} × {i32}` only. **Lacks `2D`
     (2×i64) form** — confirmed by F-3.

4. **The vectorizer** (`src/codegen/src/vectorize.rs`): exists but F-3
   (V-A2-3) found it's non-functional for real loops because the SIMD
   lowering hardcodes `Xmm0/1/2` (x86_64) and `V0/1/2` (AArch64)
   instead of using allocator-assigned registers.

### What the benchmark data tells us

- **i32 SIMD is the sweet spot.** Both x86_64 and AArch64 support
  `{Add, Sub, Mul} × {i32}`. The text shaper's primary SIMD use case
  (glyph ID processing, cluster merging, BiDi level computation) uses
  i32 lane values. The existing coverage is SUFFICIENT for these.
- **i64 SIMD is x86_64-only.** AArch64 lacks `2D` form. But i64 SIMD
  is rarely needed for text shaping (glyph IDs are u32; code points
  are u32; cluster indices are u32). The gap is acceptable.
- **The vectorizer is broken** (V-A2-3). Even if we add more SIMD ops,
  the vectorizer won't use them until V-A2-3 is fixed. So adding ops
  without fixing the vectorizer is premature.
- **No workload-level benchmark exists for text shaping.** The SWE
  package's `17-test-strategy.md` proposes gold-standard text-shaping
  tests, but they don't exist yet (the WOMB text shaper doesn't exist
  yet). So we can't benchmark "SIMD vs. scalar text shaping" until
  the shaper exists.

## Decision

**Extend SIMD coverage incrementally, driven by real text-shaper
benchmarks. Do NOT add speculative ops (AVX2, AVX-512, pmaxsd, pminsd,
gather, shuffle) until a real consumer needs them.**

### Phase 1: Fix the vectorizer (V-A2-3) first — 2 weeks

Before adding any SIMD ops, fix V-A2-3 (SIMD lowering hardcodes
`Xmm0/1/2` / `V0/1/2`). The fix: use the allocator-assigned physical
registers from `RegAllocResult` instead of hardcoded registers.

This unblocks the existing `{Add, Sub, Mul} × {i32}` SIMD ops on both
x86_64 and AArch64. No new ops needed — just make the existing ones
work for real loops.

**Effort**: 2 weeks (per V-A2-3).

### Phase 2: Add ops as the WOMB text shaper demands them

When the WOMB text shaper (`womb/ui/text/shaper_v1.vuma` and
`shaper_v2.vuma`) is written, benchmark it. If profiling shows a hot
loop that would benefit from a SIMD op VUMA doesn't have, add that op.

Candidate ops (in priority order based on typical text-shaper needs):

1. **`pmaxsd` / `pmaxsd.4s`** (SSE4.1 / NEON `smax.4s`): for
   `max(a, b)` lane-wise. Useful for cluster merging (take the higher
   glyph ID). ~2 days per backend.
2. **`pminsd` / `pminsd.4s`** (SSE4.1 / NEON `smin.4s`): same, for
   `min`. ~2 days per backend.
3. **`pcmpeqd` / `cmeq.4s`** (SSE2 / NEON): lane-wise equality
   compare, produces mask. Useful for finding a specific code point
   in a buffer. ~3 days per backend.
4. **`pshufd` / `tbl.16b`** (SSE2 / NEON): lane shuffle. Useful for
   BiDi reordering. ~1 week per backend (complex encoding).
5. **AVX2 `vpaddq ymm`** (256-bit): doubles throughput for i64 lanes.
   Only if i64 SIMD is needed (unlikely for text shaping). ~2 weeks,
   x86_64 only.
6. **AVX-512**: skip for v1. AVX-512 is not widely available (only
   on recent Intel/AMD CPUs) and the encoding is complex. Defer
   indefinitely until a real need exists.

**Effort**: ~2-4 weeks total, spread across the text-shaper
development timeline (months 6-12 per the SWE package).

### Phase 3: AArch64 `2D` form only if needed

Add AArch64 `2D` (2×i64) encoders only if a real consumer needs i64
SIMD on AArch64. Text shaping doesn't. Other WOMB modules (e.g. a
future image decoder) might. Defer until then.

**Effort**: ~3 days (the `2D` encoding is similar to `4S`, just
different `size` field).

## Consequences

### Positive
- **No speculative work.** We don't add ops that nobody uses. The 5-crate
  policy and the hand-write philosophy are preserved (no `packed_simd`
  crate).
- **Driven by real data.** The existing `fp_simd` latency tables + the
  future text-shaper benchmarks drive the decisions. No guessing.
- **Fixes the vectorizer first.** V-A2-3 is the real blocker, not the
  op coverage. Fixing it unblocks the existing ops.
- **Incremental.** Each new op is a small, well-scoped patch (~2-7
  days per backend). Easy to review, easy to revert.

### Negative
- **SIMD coverage stays narrow for now.** Until the text shaper exists
  and is benchmarked, VUMA has only `{Add, Sub, Mul, Mla} × {i32}`.
  This is sufficient for text shaping (the primary consumer) but may
  be insufficient for other WOMB modules (image decoding, audio
  processing — neither of which are planned for v1).
- **The vectorizer fix (V-A2-3) is a prerequisite.** If V-A2-3 turns
  out to be harder than 2 weeks, Phase 2 is blocked.

### Neutral
- This ADR resolves V-13's "deferred — needs benchmarking data" status.
  The benchmark data exists (latency tables + FP bench programs); the
  decision is to proceed incrementally based on it.

## Alternatives Considered

### Alternative A: Add all speculative SIMD ops now (AVX2, AVX-512, pmaxsd, pminsd, gather, shuffle, 2D)
Rejected — violates "no speculative work." Adding ops that nobody uses
is dead code. The hand-write philosophy means each op is ~2-7 days of
work; adding 6 speculative ops is ~2-4 weeks of work for zero benefit
until a consumer appears.

### Alternative B: Use the `packed_simd` crate
Rejected — violates the 5-crate policy (ADR-0010) and the hand-write
philosophy. VUMA's SIMD is hand-encoded ISA-specific instructions, not
portable intrinsics.

### Alternative C: Skip SIMD entirely; use scalar loops
Rejected — the SWE package's text shaper needs SIMD for acceptable
performance. Per `21-rfc-vector-engine.md`, glyph processing at 60fps
on 10k glyphs requires SIMD. Scalar loops would be 4-8× slower.

### Alternative D: Defer V-13 until the text shaper exists and is benchmarked
Partially accepted — Phase 2 IS deferred until the text shaper exists.
But Phase 1 (fix V-A2-3) can proceed now, because the vectorizer is
broken regardless of whether the text shaper exists.
