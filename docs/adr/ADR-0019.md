# ADR-0019: WOMB UI modules live in womb/ui/; IrqRing generalizes to womb/sync/

- **Status**: Accepted
- **Date**: 2026-08-01
- **Decision Maker**: VUMA project lead
- **Supersedes**: The SWE package's implicit assumption that WOMB UI
  modules would live in a separate crate
- **Superseded by**: (none)

## Context

The Wave J audit (`docs/research/J-1-womb-layer.md`) inventoried the
existing `womb/` directory: 195 `.vuma` files across 50 subdirectories,
~117 kLOC. Key findings:

1. **`womb/` is much larger than the SWE package assumed.** It
   includes a complete kernel (VWK, 43 kLOC), a complete crypto suite
   (26 kLOC), a self-hosted VUMA bootstrap compiler (4 kLOC), a
   POSIX-shaped libc (21 kLOC), and an RFC-grade networking stack
   (15 kLOC).

2. **There is NO `womb/ui/` directory.** Every WOMB UI module proposed
   in the SWE package (W-0 through W-9, ~50 files) is greenfield.

3. **`womb/kernel/trap/irq_ring.vuma` (472 LOC) is a working SPSC
   event ring** — the SWE package (`26-new-plans-three-layers.md`
   line 201) explicitly says to generalize this for W-0 (the event
   pipeline).

4. **`womb/crypto/mac_kdf/hmac.vuma` (193 LOC) is RFC 2104
   HMAC-SHA-256** — F-2 confirmed this is the canonical HMAC for
   VUMA's capability model (ADR-0007).

5. **6 existing artifacts are directly reusable** as UI engine
   substrate (IrqRing, HMAC, UTF-8, JSON, time/math, collections/graph).

## Decision

### Decision 1: WOMB UI modules live in `womb/ui/`

The WOMB UI engine modules will live in `womb/ui/` as VUMA source
files, sibling to the existing `womb/kernel/`, `womb/crypto/`,
`womb/net/`, etc.

Proposed structure (per the SWE package's `26-new-plans-three-layers.md`):

```
womb/ui/
├── layout/
│   ├── flex.vuma          # Flexbox, f32 coordinates
│   ├── stacking.vuma      # Stacking contexts, z-index
│   └── position.vuma      # position: absolute/fixed
├── render/
│   ├── vector.vuma        # GPU path tessellation (calls gpu_dispatch)
│   ├── scene.vuma         # SceneNode tree data structure
│   └── gpu_dispatch.vuma  # Host import: Vulkan/Metal/WebGPU
├── text/
│   ├── font_parse.vuma    # OpenType tables (fvar, gvar, COLR, CPAL)
│   ├── shaper_v1.vuma     # cmap + hmtx (naive shaper)
│   ├── shaper_v2.vuma     # GSUB + GPOS (95% of languages)
│   ├── bidi.vuma          # UAX #9 bidirectional
│   └── hint.vuma          # TrueType hinting (simplified)
├── ime/
│   ├── composition.vuma   # IME state machine
│   └── bridge.vuma        # OS IME integration (IBus/IMM32/IMK)
├── a11y/
│   ├── semantics.vuma     # SemanticsNode tree
│   └── bridge.vuma        # OS a11y (AT-SPI/UIA/NSA11y)
├── event/
│   ├── ring.vuma          # SPSC UiEvent ring (generalized from irq_ring)
│   └── dispatch.vuma      # Event dispatch to handlers
├── animation.vuma         # Animation primitives
└── theme.vuma             # Theme manager + auto-switch
```

### Decision 2: Generalize `irq_ring.vuma` to `womb/sync/spsc.vuma`

The existing `womb/kernel/trap/irq_ring.vuma` (472 LOC) is a working
SPSC (single-producer single-consumer) ring buffer for IRQ events. The
WOMB UI event pipeline needs the same pattern but for `UiEvent` (64
bytes) instead of IRQ vectors (8 bytes).

**Generalization**:
- Move the SPSC ring logic from `womb/kernel/trap/irq_ring.vuma` to a
  new `womb/sync/spsc.vuma` (parameterized by element type and size).
- `womb/kernel/trap/irq_ring.vuma` becomes a thin wrapper that
  instantiates `SpscRing<u64, 32>` (32-entry ring of u64 IRQ vectors).
- `womb/ui/event/ring.vuma` becomes a thin wrapper that instantiates
  `SpscRing<UiEvent, 256>` (256-entry ring of 64-byte UiEvents).

**Why generalize**:
- The SPSC pattern is reusable beyond IRQ and UI events (channel
  buffers, log buffers, etc.).
- A single tested implementation is better than copy-pasted variants.
- The generalization is ~100 LOC; the alternative (copy-paste) would
  be ~472 LOC duplicated.

### Decision 3: WOMB UI modules are VUMA source, not a separate crate

The WOMB UI modules are `.vuma` files, not Rust crates. They compile
with the existing VUMA toolchain. No new Cargo crate is needed.

This preserves:
- **The 5-crate policy** (ADR-0010) — no new Rust dependencies.
- **PMT verification** — WOMB UI code is VUMA source, so it gets full
  IVE verification (Z3 + Lean formal spec).
- **Single-repo simplicity** — `womb/` stays in the `vuma` repo.

### Decision 4: WOMB UI modules use `womb/crypto/`, `womb/collections/`, `womb/string/` directly

The WOMB UI modules import existing WOMB stdlib modules:
- `womb/ui/render/vector.vuma` imports `womb/crypto/mac_kdf/hmac.vuma`
  for capability-token signing of GPU dispatch calls.
- `womb/ui/text/shaper_v1.vuma` imports `womb/collections/hashmap.vuma`
  for glyph caching.
- `womb/ui/event/ring.vuma` imports `womb/sync/spsc.vuma` (the
  generalized ring).

No duplication. The existing WOMB stdlib is the foundation.

## Consequences

### Positive
- **WOMB UI modules are VUMA source** — they get PMT verification for
  free. No separate verifier needed.
- **Single repo** — `womb/ui/` lives in the `vuma` repo. No
  multi-repo coordination overhead.
- **Reusable SPSC ring** — the generalization benefits kernel, UI, and
  future use cases (channels, logging).
- **No new Cargo crates** — the 5-crate policy is preserved.
- **Existing WOMB stdlib is reused** — crypto, collections, string,
  net are already there.

### Negative
- **`womb/` grows significantly.** Adding ~50 UI module files (~10-15
  kLOC) will increase the WOMB tree from ~117 kLOC to ~130 kLOC. This
  is manageable but means the `womb/` tree is no longer "just a
  stdlib" — it's a UI engine too.
- **The `womb/kernel/` and `womb/ui/` coupling.** If the kernel
  changes (e.g. trap handling), the UI event ring may need updates.
  Mitigated by the generalization (kernel and UI both use
  `womb/sync/spsc.vuma`, so changes happen in one place).
- **Bootstrap complexity.** VUMA's capability model depends on
  `womb/crypto/mac_kdf/hmac.vuma`. Adding `womb/ui/` that depends on
  more WOMB modules increases the bootstrap surface. Acceptable
  because the bootstrap is parity-tested.

### Neutral
- The SWE package's W-0 through W-9 module proposals are the design
  blueprint. This ADR locks in the location (`womb/ui/`) and the
  reuse strategy (existing WOMB stdlib), not the module designs
  themselves (which are tracked in the SWE package RFCs).

## Alternatives Considered

### Alternative A: WOMB UI modules in a separate Cargo crate
Rejected — would require a new Rust crate (`vuma-womb-ui`), violating
the 5-crate policy. Also unnecessary: WOMB UI modules are VUMA source,
not Rust.

### Alternative B: WOMB UI modules in a separate repo
Rejected — splits the WOMB stdlib across repos, complicates
bootstrapping (VUMA depends on `womb/crypto/`, which would be in a
different repo). Single repo is simpler.

### Alternative C: Copy-paste `irq_ring.vuma` for the UI event ring
Rejected — duplicates 472 LOC. The generalization is ~100 LOC and
benefits all SPSC use cases.

### Alternative D: Put the UI event ring in `womb/kernel/` alongside `irq_ring.vuma`
Rejected — UI events are not kernel concerns. The kernel owns IRQs;
the UI owns UI events. `womb/sync/` is the right home for the shared
SPSC primitive.
