# ADR-0021: Delete the `Effect` enum (it is dead code)

- **Status**: Accepted
- **Date**: 2026-08-01
- **Decision Maker**: VUMA compiler team
- **Supersedes**: The implicit "keep the Effect enum for future use"
  stance in the original catalog
- **Superseded by**: (none)

## Context

The Wave A audit (A-3) discovered that the `Effect` enum in
`src/codegen/src/effects.rs` is **dead code**:

- `analyze_program_effects` is called at `pipeline.rs:4431`, but its
  result is used ONLY for a `vuma_log!(debug)` pure-function count.
- The optimizer (`src/codegen/src/opt.rs`) uses its own
  `has_side_effects` function at `opt.rs:527`, not the `Effect` enum.
- The IVE (`src/ive/`) has **zero references** to `Effect`,
  `EffectSet`, or `analyze_program_effects`.
- `Effect::ExternCall` (which the catalog's V-A3-7 flagged) is
  completely unreferenced.

The Wave F re-audit (F-1) confirmed this: `analyze_program_effects` is
called once, at `pipeline.rs:4431`, for debug logging only. The
optimizer doesn't use it. IVE doesn't use it.

The original catalog (V-A3-7) marked this as P2 and deferred the
decision ("wire-vs-delete needs usage analysis"). The usage analysis
is now complete: **nobody uses it.**

## Decision

**Delete the `Effect` enum, `EffectSet`, `analyze_program_effects`,
and the `pipeline.rs:4431` debug-logging call site.**

### What to delete

1. `src/codegen/src/effects.rs` — the entire file (~200 LOC).
2. The `analyze_program_effects` call at `src/pipeline.rs:4431`.
3. Any imports of `Effect`, `EffectSet`, or `analyze_program_effects`
   in other files (grep to find them — likely zero, since IVE has no
   references).
4. The `Effect` re-export in `src/codegen/src/lib.rs` (if any).
5. Any test files that test `analyze_program_effects` (grep
   `tests/` for `analyze_program_effects`).

### What NOT to delete

- The optimizer's `has_side_effects` function at `opt.rs:527` — this
  is a separate, IN-USE effect analysis. It doesn't use the `Effect`
  enum; it has its own logic.
- The `Effect::ExternCall` concept — if VEEE (Layer 3) or WOMB (Layer 2)
  ever needs effect tracking, they should build their own effect
  analysis, not revive the dead `Effect` enum. The optimizer's
  `has_side_effects` is the model to follow.

## Consequences

### Positive
- **Removes ~200 LOC of dead code.** The `effects.rs` file, its
  imports, and its call site.
- **Eliminates confusion.** Engineers reading `effects.rs` might think
  it's load-bearing (it has docstrings claiming IVE uses it — false).
  Deleting it removes the false documentation.
- **Simplifies the codebase.** One fewer module in `src/codegen/src/`.
- **No behavior change.** Since nobody uses it, deleting it changes
  nothing at runtime.

### Negative
- **Loses the debug-logging pure-function count.** The
  `vuma_log!(debug, "pure functions: N")` at `pipeline.rs:4431` will
  disappear. If anyone relies on this debug output (unlikely), they'll
  need to re-add it using `has_side_effects` from the optimizer.
- **Future re-implementation cost.** If VEEE or WOMB later needs
  effect tracking, they'll have to re-build it. This is acceptable —
  the current `Effect` enum doesn't model the effects VEEE would care
  about (GPU effects, reactivity effects, etc.).

### Neutral
- The `Effect` enum was added in an earlier VUMA version when the
  plan was to have IVE consume it. The plan changed (IVE uses Z3
  directly, not an effect system). The `Effect` enum was left behind.
  This ADR cleans up the leftover.

## Alternatives Considered

### Alternative A: Keep the `Effect` enum; wire it into IVE
Rejected — IVE uses Z3 directly. An effect system would be a
duplication. The IVE verifiers (`state_read.rs`, `state_write.rs`,
`session_type.rs`, `information_flow.rs`) already track effects
implicitly via Z3 constraints. Wiring the `Effect` enum into IVE would
add a layer of indirection without benefit.

### Alternative B: Keep the `Effect` enum for VEEE (Layer 3)
Rejected — VEEE's effects are different from VUMA's (reactivity,
incremental computation, GPU dispatch). The current `Effect` enum
(`Alloc`, `Free`, `IO`, `Modifies`, `Atomic`, `ExternCall`) doesn't
model VEEE's effects. If VEEE needs effect tracking, it should design
its own effect system, not revive VUMA's dead one.

### Alternative C: Mark `#[deprecated]` instead of deleting
Rejected — `#[deprecated]` still leaves the code in the tree, still
needs to compile, still confuses readers. Delete is cleaner.
