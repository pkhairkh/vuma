# ADR-0006: Defer f32 PMT Lean proof to v2; use runtime float-trap checks only

- **Status**: Accepted
- **Date**: 2026-08-01
- **Decision Maker**: VUMA compiler team

## Context

A-3's audit of the Lean PMT proof layer (`research/A-3-ive-proofs-capability.md`
§1 "V-14") confirms the catalog's claim: the Lean model is purely
memory-safety, with no arithmetic-verification infrastructure to extend.

The `Arena` model at `proof/PMT/Basic.lean:38-42` is three `Nat` fields
(`base`, `capacity`, `used`) — `Nat`, not `Float` or IEEE-754 bit-pattern.
The `Field` model at `Basic.lean:51-56` is `(name, offset, size, type_name)`,
all `Nat`/`String` — no value payload, no IEEE bits field. The only arithmetic
lemma in the entire `proof/PMT/` tree is `alloc_preserves_capacity` at
`Basic.lean:134-143`, discharged by `omega`, which proves only
`a.used + l.total_size ≤ a.capacity`. There is no lemma about value contents,
no `FloatArena`, no `verified_float_add`, no NaN/±inf/ULP/rounding reasoning.

The `IRType` inductive at `proof/PMT/PmtInstr.lean:177-194` does carry `f32`
and `f64` as constructors (lines 186-187), but they are **bare tags with no
semantic content**. The docstring at `PmtInstr.lean:206-208` is explicit:
*"They are pure tag types: `PmtInstr.well_typed` does not inspect them (the
arithmetic `PmtInstr` variants are all `True`-well-typed), so the Lean
variants are present solely to faithfully mirror the Rust IR shape for
`instr_sim_intra_lean` / `block_sim` traversal in `PMT.SimRel`."*

Concretely, every arithmetic `PmtInstr` variant is `True`-well-typed at
`PmtInstr.lean:810-821`:

```lean
| .bin_op _ _ _ _ _ => True
| .unary_op _ _ _ _ => True
| .cast _ _ _ _ _ => True
| .add _ _ _ _ => True
| .sub _ _ _ _ => True
| .mul _ _ _ _ => True
| .div _ _ _ _ => True
| .cmp _ _ _ _ _ => True
| .select _ _ _ _ _ => True
| .ct_select _ _ _ _ _ => True
| .ct_eq _ _ _ _ => True
| .get_address _ _ => True
```

`pmt_soundness` (`proof/PMT/Soundness.lean:245-525`) proves capacity
preservation (`final_used ≤ s.arena.capacity`) and trap canonicality
(`code = 1 ∨ code = 134 ∨ code = 135`); it says nothing about NaN, ±inf,
ULP error, rounding, distributivity, or associativity. There is no
arithmetic-verification infrastructure to extend — building a verified
`f32` PMT model is greenfield.

Realistic estimate: 3-6 months of greenfield work. One would need to (a)
build a new `FloatArena` model with IEEE-754 bit-pattern fields, (b)
re-implement `verified_float_add`/`sub`/`mul`/`div` with rounding-mode
tracking, (c) inject NaN/±inf trap checks into the codegen, (d) prove a
new `float_alloc_preserves_finite` lemma from scratch, and (e) re-prove
`pmt_soundness` against the extended step relation. None of this overlaps
with the existing `omega`-closed proof.

On the runtime side, the only existing trap is `arena_overflow_trap`
(`src/codegen/src/runtime/arena.rs:107`, exit code 1) — it fires when the
bump allocator would exceed capacity. There is **no** `__float_overflow_trap`
in the source today: a `grep -rn '__float_overflow_trap|float_overflow_trap|exit\(142\)'`
across `src/` returns zero matches. The `__float_overflow_trap` (exit 142)
mentioned in `docs/vuma-side-problem-catalog.md:289` and
`docs/vuma-side-research-draft.md:488` is an *aspiration* in the docs, not
an existing runtime stub. (This is a doc/source divergence; it must be
resolved as part of this ADR's implementation — see Decision step 2.)

The SWE package's original 4-week estimate for "extend the Lean model to
f32" (per catalog V-14) is wrong by ~5-10×. There is no existing
arithmetic-verification infrastructure to extend.

## Decision

For v1, **do NOT attempt formal verification of f32/f64 arithmetic** in the
Lean PMT model. Use runtime trap checks only. This is a known soundness gap,
documented as such, with a clear v2 revisit trigger.

Implementation steps:

1. **Add the runtime `__float_overflow_trap` stub** that the catalog and
   research draft already reference. The stub must (a) be emitted on all
   19 backends (mirroring the `__oob_trap` exit-134 pattern from
   `src/codegen/src/backend.rs:4050-4058` and the per-backend emitters
   enumerated in A-4 §1), and (b) call `exit(142)` (128 + SIGFPE(14) = 142,
   matching the convention `__oob_trap` uses for SIGABRT). Wire it into
   the codegen at every `IRInstr::BinOp`/`Add`/`Sub`/`Mul`/`Div` site
   where the result `IRType` is `F32` or `F64`, behind a runtime check
   that the result is finite (i.e., not NaN, not ±inf). ~2 weeks of work
   (one stub per backend + codegen threading).

2. **Document the gap in `proof/PMT/README.md`** under a new
   "Known soundness gaps" section: *"The Lean PMT model does not verify
   f32/f64 arithmetic. The `IRType.f32`/`f64` constructors are bare tags;
   every arithmetic `PmtInstr` variant is `True`-well-typed at
   `PmtInstr.lean:810-821`. Soundness of f32 arithmetic relies on the
   runtime `__float_overflow_trap` (exit 142) check, which is a
   necessary-but-not-sufficient condition (it catches NaN/±inf but not
   ULP error, rounding, or associativity). Revisit in v2."*

3. **Document the gap in `docs/pmt-formal-spec.md`** with the same content
   and a forward-pointer to this ADR.

4. **Resolve the doc/source divergence**: the catalog and research draft
   both reference `__float_overflow_trap` (exit 142) as if it already
   exists. After step 1 lands, this becomes accurate. Until then, the
   docs must say "planned runtime check" or step 1 must land in the same
   PR.

5. **Revisit trigger for v2**: re-evaluate if (a) a downstream consumer
   requires formal f32 soundness (e.g., a safety-critical kernel
   subsystem), (b) a third-party verified-float library becomes
   acceptable under the small-deps policy, or (c) the Lean community
   ships a maintained IEEE-754 bit-level library we can depend on
   without OCaml/Coq-side transitive deps.

## Consequences

### Positive

- v1 ships without a 3-6 month Lean proof blocker. The f32 codegen
  pipeline (V-34, V-35, V-36 fixes per ADR-0002/0003/0004) can proceed
  unblocked.
- The Lean PMT model's existing sorry-free status is preserved
  (`scripts/check-lean.sh` strict mode continues to pass). No `sorry`
  tokens are introduced to paper over the gap.
- The gap is *documented*, not silently assumed-away. A future auditor
  reading `proof/PMT/README.md` will see the explicit scope limit.
- The runtime trap is a real defense-in-depth measure: even without
  formal verification, NaN/±inf propagation is caught at the point of
  production, with a deterministic exit code (142) that test harnesses
  can recognize.
- The runtime `__float_overflow_trap` stub is reusable: it can be
  extended in v2 to also catch subnormal-flush-to-zero or ULP-violation
  cases if a verified-float library ever needs it.

### Negative

- **Soundness gap**: a `vuma` program that performs `f32` arithmetic
  and produces a NaN that the runtime check doesn't catch (e.g., a
  quiet NaN that slips through a `is_finite` guard due to a codegen
  bug) will silently produce wrong results. The Lean proof provides no
  backstop. This is the same trust model as Rust's `f32`/`f64` —
  acceptable for v1 UI-engine work, not acceptable for safety-critical
  kernel code.
- **Runtime cost**: every `f32`/`f64` arithmetic op gains a finiteness
  check. On x86_64 this is ~2 instructions (`ucomisd` + `jp`); on
  soft-float backends (hppa per `src/codegen/src/hppa/mod.rs:2281`,
  m68k per `src/codegen/src/m68k/mod.rs:3904`) it's more expensive.
  Estimated 5-15% perf regression on float-heavy workloads; should be
  feature-gated behind `pmt-runtime-check` (which already exists per
  `Cargo.toml:111-113` and `src/codegen/Cargo.toml:22-31`) and
  disabled in the `release-fast` profile.
- **Doc/source divergence**: until step 1 lands, the catalog and
  research draft continue to reference a runtime trap that doesn't
  exist. Anyone reading the docs first will be confused. This must be
  resolved in the same PR as step 1.
- **Effort estimate revision**: the catalog's V-14 effort line ("3-6
  months (defer to v2)") is honest, but the SWE package's original
  4-week estimate for "extend the Lean model" is wrong. Anyone
  re-planning v2 must use the 3-6 month number, not the 4-week one.

### Neutral

- The `IRType.f32`/`f64` constructors stay in `PmtInstr.lean:186-187`
  unchanged. They're harmless (used only for `SimRel` traversal shape
  mirroring per the docstring at `PmtInstr.lean:206-208`).
- The runtime `arena_overflow_trap` (`src/codegen/src/runtime/arena.rs:107`,
  exit 1) is unaffected — it already catches arena-capacity overflow, a
  separate concern from float-arithmetic overflow.
- The `__oob_trap` exit-134 stub on all 19 backends (A-4 §1 table) is
  unaffected — it catches out-of-bounds memory access, not float
  overflow.
- The v2 effort estimate (3-6 months) is unaffected by any v1 work
  except the runtime trap stub, which v2 could reuse.

## Alternatives Considered

### Alternative A: Build the f32 Lean proof for v1

Rejected. The 3-6 month estimate blocks every UI-engine consumer of f32
state fields (the WOMB layout/renderer modules that depend on V-34/V-35/V-36
landing). The blast radius is the entire v1 UI roadmap. The proof would
also need to model IEEE-754 rounding modes, subnormals, NaN propagation
through arithmetic, and the interaction between hardware FPU semantics
(19 backends, each with subtly different behavior — e.g. hppa's soft-float
stubs at `src/codegen/src/hppa/mod.rs:2688-2719` that return 0 for sub/mul/div)
and the abstract Lean semantics. This is a research project, not an
engineering task.

### Alternative B: Use a third-party verified-float library (e.g. Flocq bindings)

Rejected. Flocq is a Coq library, not a Lean library; using it would
either (a) require an OCaml/Coq toolchain in the build (violates the
small-deps policy documented in the worklog and reaffirmed by A-4 §2),
or (b) require porting Flocq's IEEE-754 model to Lean (months of work,
plus a permanent maintenance burden to keep the port in sync with
upstream Flocq). The Lean ecosystem has no maintained, audited
IEEE-754 bit-level library as of 2026-08; depending on an immature one
would trade a known gap for an unknown one.

### Alternative C: Drop f32 entirely and use fixed-point

Rejected. WOMB's subpixel text rendering requires true `f32` precision
for glyph hinting and gamma correction. A fixed-point representation
with sufficient range and precision for subpixel positioning would
need at least 16.16 fixed-point (32-bit), and the rounding behavior
would differ from hardware `f32` in ways that produce visible
rendering artifacts. Worse, every downstream consumer that expects
`f32` (font formats like OpenType `glyf`/`gvar` tables, GPU shader
interoperability, IEEE-754-mandated NaN propagation in compositing)
would need a translation layer. The cost of dropping `f32` exceeds the
cost of carrying an unverified arithmetic path.
