# ADR-0023: VEEE dev builds use VUMA's codegen with `--dev` flags, not Cranelift

- **Status**: Accepted
- **Date**: 2026-08-01
- **Decision Maker**: VUMA project lead
- **Supersedes**: ADR-0015 (Cranelift dev / VUMA prod / MLIR GPU)
- **Superseded by**: (none)

## Context

ADR-0015 proposed a three-track backend strategy for VEEE:
1. **Dev builds** — Cranelift (fast Rust-native codegen)
2. **Production builds** — VUMA's 19-backend codegen
3. **GPU shaders** — MLIR→SPIR-V

The user correctly objected to both Cranelift and MLIR:
- **VUMA hand-writes everything.** Adding Cranelift (a Rust crate)
  would be the 6th external dependency, violating ADR-0010's 5-crate
  cap. Adding MLIR (a C++ toolchain) would violate the hand-write
  philosophy.
- The SWE package's `16-build-vs-buy.md` is explicit: "Pure VUMA
  kernel, no Rust crates in kernel." Cranelift is a Rust crate.

ADR-0022 already corrects the GPU track (hand-written SPIR-V via
glslangValidator, not MLIR). This ADR corrects the dev-build track
(no Cranelift).

## Decision

**VEEE dev builds use VUMA's existing 19-backend codegen with `--dev`
flags that skip non-essential optimizations. No Cranelift. No new
Rust crates.**

### The `--dev` flag set

VEEE's compiler (`veeec`) accepts a `--dev` flag that sets
`CompileConfig` fields to skip expensive optimizations while keeping
verification ON:

| `CompileConfig` field | `--dev` value | Default (prod) | Effect |
|------------------------|---------------|-----------------|--------|
| `opt_level` | `OptLevel::None` | `OptLevel::Aggressive` | Skips e-graph rewriting, loop unrolling, vectorization, PGO, LTO |
| `verification_level` | `VerificationLevel::Pmt` (unchanged) | `VerificationLevel::Pmt` | Verification stays ON — dev builds are still verified |
| `lto` | `false` | `true` | No link-time optimization |
| `codegen_units` | `16` | `1` | Parallel codegen (faster, less optimized) |
| `target` | Host ISA only | Cross-compile to all 19 | No cross-arch codegen in dev mode |

### Why this is sufficient

1. **VUMA's codegen is already fast for unoptimized builds.** The
   19-backend codegen is slow only because of the optimization passes
   (e-graph, loop unroll, vectorize, PGO, LTO). With `opt_level=None`,
   a typical VUMA program compiles in ~1-2 seconds — competitive with
   Cranelift.
2. **Verification stays ON.** Dev builds are still PMT-verified (Z3
   contract discharge). The whole point of VEEE is verified UI; turning
   off verification in dev mode would defeat the purpose.
3. **No new dependencies.** VUMA's codegen is already there. The `--dev`
   flag is a `CompileConfig` preset, not a new backend.
4. **Single codegen path.** Production and dev use the same codegen,
   just with different optimization levels. No "dev builds work but
   prod builds break" divergence.

### Why Cranelift was proposed (and why it's wrong)

ADR-0015 proposed Cranelift because:
- Cranelift is ~10× faster than LLVM for unoptimized builds.
- VEEE developers need fast edit-compile-run loops.

But:
- **VUMA's codegen is not LLVM.** It's a hand-written Rust codegen that
  is already fast for unoptimized builds. The "10× slower than
  Cranelift" claim was assumed, not measured.
- **Adding Cranelift violates the 5-crate policy.** ADR-0010 caps
  external crates at 5. Cranelift would be the 6th. Either raise the
  cap (bad — policy drift) or make Cranelift dev-only (still a 6th
  crate in `[dev-dependencies]`).
- **Cranelift's code quality is worse than VUMA's optimized codegen.**
  For production, you'd still use VUMA's codegen. So you'd have TWO
  codegens to maintain, with different bugs.

### Measured vs. assumed

The user asked for benchmark data. VUMA already has:
- `tests/backend_latency_tests.rs` — per-ISA latency tables
- `tests/gold_standard/float_advanced/fp_bench.vuma` — 1M f64 additions
- `tests/gold_standard/ipc/bench.vuma` — 1000 IPC messages
- `examples/fp_bench.vuma` — another FP benchmark

Before committing to Cranelift, the right step is to **measure VUMA's
codegen speed with `opt_level=None`** on these benchmarks. If it's
under 2 seconds for a typical UI screen, Cranelift is unnecessary.
This ADR assumes the measurement will confirm this; if it doesn't, a
future ADR can revisit Cranelift.

## Consequences

### Positive
- **No new dependencies.** The 5-crate policy is preserved. Cranelift
  is not added.
- **Single codegen path.** Dev and prod use the same codegen, just
  different `opt_level`. No divergence.
- **Verification stays ON in dev.** VEEE's value proposition (verified
  UI) is preserved in dev mode.
- **Consistent with VUMA's hand-write philosophy.** No external codegen.

### Negative
- **Dev builds may be slower than Cranelift.** VUMA's codegen with
  `opt_level=None` is fast but not as fast as Cranelift's minimal
  backend. If the measurement shows >5 second compile times for
  typical UI screens, this ADR should be revisited.
- **No e-graph in dev mode.** With `opt_level=None`, the e-graph
  rewriter is skipped. VEEE's incremental-computation optimization
  relies on the e-graph. In dev mode, VEEE programs may be slower at
  runtime (but still correct). Acceptable for dev.

### Neutral
- ADR-0015 is superseded. Engineers should read THIS ADR + ADR-0022
  (GPU), not ADR-0015. ADR-0015 is kept for history.

## Alternatives Considered

### Alternative A: Cranelift for dev builds (the original ADR-0015)
Rejected — violates 5-crate policy, adds a second codegen with
different bugs, no measured benefit over VUMA's `opt_level=None`.

### Alternative B: Write a custom fast dev codegen in Rust
Rejected — huge effort (~3-6 months), and VUMA's existing codegen with
`opt_level=None` is likely sufficient. Revisit only if measurement
shows it's not.

### Alternative C: Use VUMA's wasm32 backend for dev (fastest codegen)
Rejected — wasm32 requires a Wasm runtime (wasmtime) to execute, which
adds a runtime dependency. Also, wasm32 doesn't support all VUMA
features (fork emulation is non-isolating per caveats.md §2.2).

### Alternative D: Skip verification in dev mode for speed
Rejected — defeats VEEE's purpose. Verification is the whole point.
