# ADR-0017: VEEE's monotonicity types are a VEEE-layer type-system feature

- **Status**: Accepted
- **Date**: 2026-08-01
- **Decision Maker**: VUMA project lead
- **Supersedes**: (none)
- **Superseded by**: (none)

## Context

The SWE package (`23-vell-redesign-research.md`) proposed that VEEE
borrow **monotonicity types** from Datafun: a type-system feature
where collection types track whether their contents can only grow
(monotone) or can shrink (antitone). This enables seminaïve delta
evaluation — when a monotone collection changes, you only re-evaluate
the parts that depend on the NEW elements, not the whole collection.

There are two possible places this type-system feature could live:

1. **In VEEE** — VEEE's type checker enforces monotonicity. VEEE
   programs with monotonicity violations are rejected at VEEE compile
   time. The lowering to VUMA AST emits `requires`/`ensures` contracts
   that Z3 discharges.

2. **In VUMA** — VUMA's type system gains a `Monotone<T>` type
   constructor. VUMA's IVE verifies monotonicity. VEEE programs use
   `Monotone<T>` directly.

This ADR locks in option 1 (VEEE-layer).

## Decision

**Monotonicity types are a VEEE-layer type-system feature, not a VUMA
IR feature.**

### How it works

1. **VEEE source** declares monotone collections:
   ```veee
   monotone set visible_items: Set<ItemId>
   antitone set hidden_items: Set<ItemId>
   derive filtered: Set<Item> = visible_items.map(|id| lookup(id)).filter(|i| !hidden_items.contains(i.id))
   ```
   `visible_items` is monotone (can only grow). `hidden_items` is
   antitone (can only shrink). `filtered` is a derived collection.

2. **VEEE type checker** verifies:
   - `visible_items.insert(x)` is allowed (monotone grow).
   - `visible_items.remove(x)` is rejected (monotone shrink).
   - `hidden_items.remove(x)` is allowed (antitone shrink).
   - `hidden_items.insert(x)` is rejected (antitone grow).
   - `filtered`'s derivation is monotone in `visible_items` and
     antitone in `hidden_items` (so adding to `visible_items` or
     removing from `hidden_items` only adds to `filtered`).

3. **VEEE compiler** lowers each monotone collection to:
   - A VUMA `layout` with a version counter:
     ```vuma
     layout MonotoneSetItemId = { version: u64, count: u64, items: [ItemId; 256] }
     ```
   - A VUMA `transform` for insertion (with `ensures` contract):
     ```vuma
     transform insert_item(s: State<MonotoneSetItemId>, item: ItemId)
         requires s.count < 256
         ensures s.count == old(s.count) + 1
         ensures s.version == old(s.version) + 1
     {
         s.items[s.count] = item;
         s.count = s.count + 1;
         s.version = s.version + 1;
     }
     ```
   - Z3 discharges the `ensures` clauses, proving the count and
     version advance correctly.

4. **VEEE runtime** (compiled to VUMA) uses the version counter to
   detect changes. When `filtered` is re-evaluated, it compares the
   versions of `visible_items` and `hidden_items` to its cached
   versions. If unchanged, return the cache. If changed, re-evaluate
   only the delta (the new elements in `visible_items` or the removed
   elements from `hidden_items`).

### Why VEEE-layer, not VUMA-layer

- **Monotonicity is a type-system property, not a memory-layout
  property.** VUMA's `IRType` is about memory layout (I32, F64, etc.).
  Adding `Monotone<T>` to `IRType` would conflate type-system level
  (compile-time checking) with IR level (runtime representation).
- **VUMA's IVE verifies memory safety, not collection semantics.**
  Monotonicity is a collection-semantics property. PMT proves `used +
  size ≤ capacity` (memory safety); monotonicity proves `count only
  grows` (collection semantics). These are different properties at
  different abstraction levels.
- **VEEE's type checker is the right place.** The monotonicity check
  happens at VEEE compile time, before lowering to VUMA. VUMA never
  sees `monotone` or `antitone` — it just sees `requires`/`ensures`
  contracts on the lowered transforms.
- **Z3 discharge is sufficient.** The `ensures count == old(count) + 1`
  contract is trivially dischargeable by Z3. No new VUMA verifier
  needed.

### What VEEE's monotonicity type system contains

- **Type constructors**: `Monotone<T>`, `Antitone<T>` (for sets/maps).
- **Type checker**: verifies that monotone collections only grow,
  antitone collections only shrink.
- **Delta evaluation**: when a monotone collection changes, the
  derived collections re-evaluate only on the delta.
- **Seminaïve fixpoint**: for recursive derivations (e.g. transitive
  closure), VEEE uses seminaïve evaluation — iterate to fixpoint by
  processing only the new elements each round.

### What VUMA provides (unchanged)

- `State<T>` typed-state API (the monotone collections lower to this)
- `requires`/`ensures` contracts (Z3 discharges them)
- PMT arena (memory safety for the collection storage)
- 19-backend codegen

### What WOMB provides

- `womb/collections/monotone_set.vuma` — the monotone set data structure
  (uses VUMA arrays + version counters)
- `womb/collections/delta.vuma` — delta-tracking helpers

## Consequences

### Positive
- **VUMA stays minimal** — no IR changes, no new type constructor,
  no new verifier. The 5-crate policy is preserved.
- **Monotonicity is checked at compile time** — VEEE rejects
  monotonicity violations before any VUMA code is generated.
- **Z3 discharge is reused** — VEEE's `ensures` contracts go through
  VUMA's existing Z3 infrastructure. No new verifier.
- **VEEE can iterate on the type system** — changing the monotonicity
  rules is a VEEE-compiler change, not a VUMA change.

### Negative
- **VEEE's type checker is non-trivial** — ~3,000 lines of Rust to
  implement monotonicity inference, delta evaluation, and seminaïve
  fixpoint.
- **Monotonicity is not formally verified at the VUMA level.** The
  `ensures` contracts prove that `count` advances, but they don't
  prove that the collection is semantically monotone (i.e. that no
  element is ever removed). The semantic monotonicity is enforced by
  VEEE's type checker rejecting `remove` calls, not by Z3. This is a
  weaker guarantee than if VUMA's IVE verified it — but it's the same
  guarantee Datafun provides.

### Neutral
- The `monotone` and `antitone` keywords are VEEE syntax, not VUMA
  syntax.

## Alternatives Considered

### Alternative A: Add `Monotone<T>` to VUMA's IR
Rejected — conflates type-system level with IR level, bloats VUMA,
requires new Lean proofs for collection semantics.

### Alternative B: Skip monotonicity types; re-evaluate everything
Rejected — this is the naive approach. Without monotonicity, delta
evaluation is impossible. VEEE would be O(n) per change, same as
React.

### Alternative C: Use VUMA's e-graph for monotonicity
Rejected — the e-graph is an optimization-time data structure. It
can detect equivalent expressions but doesn't track collection
monotonicity.
