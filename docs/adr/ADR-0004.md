# ADR-0004: Migrate `build_pmt_layout_specs` + IVE `rederive_layout` to `_with_layouts` (V-03 + V-NEW-2 + V-40)

- **Status**: Accepted
- **Date**: 2026-08-01
- **Decision Maker**: VUMA compiler team
- **Supersedes**: (none)
- **Superseded by**: (none)

## Context

`build_pmt_layout_specs` in `src/pipeline.rs:6715–6756` is the
IVE-public counterpart of `build_layout_registry`. It walks every
`Item::LayoutDef` in the AST and emits a
`HashMap<String, vuma_ive::PmtLayoutSpec>` — the table the IVE's
`VerificationLevel::Pmt` consults when running the 3 state verifiers
(`state_read` / `state_write` / `state_transform`). The function's
docstring at `:6701–6714` explicitly says it "is the IVE-public
counterpart of the internal `build_layout_registry`: it walks the same
`Item::LayoutDef` AST nodes and computes the same per-field
offset/size using the same `bridge_type_*` helpers".

But it does **not** use the same `bridge_type_*` helpers. It uses the
**legacy** `bridge_type_size` (defined at `:6532`) at line `:6724`,
not the fixed `bridge_type_size_with_layouts` (defined at `:6557`).
The legacy function has a `_ => 8` catch-all at `:6540` for any
user-defined layout name:

```rust

6716      let mut layouts: HashMap<String, vuma_ive::PmtLayoutSpec> = HashMap::new();
6717      for item in &program.items {

```

The catalog (`docs/vuma-side-problem-catalog.md:153–178`, V-03)
verified this. Two Wave-A subagents confirmed and amplified:

- **A-4** (`docs/research/A-4-pipeline-runtime-tests-deps.md:47–113`,
  V-03/V-40): the only external caller of legacy `bridge_type_size` is
  `build_pmt_layout_specs:6724`. The fixed
  `bridge_type_size_with_layouts` is called by `build_layout_registry`
  Pass 2 (`:6652`) and Pass 3 (`:6679`). V-37 ("trailing padding
  missing") is **refuted** — the trailing padding at `:6741–6744` is
  already correct; the real gap is the single-pass + legacy size fn
  (subsumed by V-03).
- **A-3** (`docs/research/A-3-ive-proofs-capability.md`, V-A3-1 /
  V-NEW-2): `src/ive/src/verification.rs:268–291` (`rederive_layout`)
  and `:299–327` (`type_align_size`) **intentionally reproduce the
  same `_ => 8` bug** for parity. The docstring at
  `src/ive/src/verification.rs:264–267` is explicit:

  > "anything else (user-defined layout name, etc.) → align 8, size 8
  > (matches the pipeline's `_ => 8` catch-all — **known small-layout
  > bug; this verifier faithfully reproduces it so that consistency
  > checks pass on pipeline-provided layouts**)."

  And the body at `:325`:

  ```rust
  match t {
      "i8" | "u8" | "bool" => (1, 1),
      "i16" | "u16" => (2, 2),
      "i32" | "u32" | "f32" => (4, 4),
      "i64" | "u64" | "f64" => (8, 8),
      _ => (8, 8),    // ← catch-all: user-defined layout names, etc.
  }
  ```

  `verify_layout_consistency` (`:336–365`) calls `rederive_layout`
  and compares its output against the pipeline-provided
  `PmtLayoutSpec`. After V-03 is fixed on the pipeline side,
  `build_pmt_layout_specs` will produce correct sizes for nested
  layouts — but `rederive_layout` will still return `8` for
  user-defined names. The consistency check will then **FAIL** for
  every program with a nested layout, and the IVE will refuse to
  discharge. A-4 named this V-NEW-2 and flagged it P0 ("silently
  defeats V-03 fix" — `docs/research/A-4-pipeline-runtime-tests-deps.md:457–483`).

So the migration has three parts that must land in lockstep:

1. **`build_pmt_layout_specs`** migrates to the two-pass
   `_with_layouts` algorithm (mirroring `build_layout_registry` at
   `:6625–6699`).
2. **`rederive_layout`** in IVE migrates to consult a layouts table
   (so the consistency check passes against the now-correct pipeline
   output).
3. After both land, **legacy `bridge_type_size`** is deleted (V-40 —
   `docs/vuma-side-problem-catalog.md:317–328`, verified by A-4 at
   `docs/research/A-4-pipeline-runtime-tests-deps.md:194–196`: "after
   `:6724` migrates, the legacy function has only its self-recursive
   `Type::Array` arm at `:6547` as a caller — i.e., zero external
   callers").

## Decision

Three changes, landed as one PR (or three tightly-coupled PRs in
sequence with no intermediate `main` state where any one is missing).

### Change 1 — `build_pmt_layout_specs` migrates to two-pass `_with_layouts`

Replace the single-pass body at `src/pipeline.rs:6715–6756` with the
same two-pass structure already used by `build_layout_registry` at
`:6625–6699`. The mechanical translation:

```rust
pub fn build_pmt_layout_specs(program: &AstProgram) -> HashMap<String, vuma_ive::PmtLayoutSpec> {
    // Multi-pass: first compute all layout sizes (resolving nested layout
    // references), then compute field offsets using the real sizes.
    // Mirrors `build_layout_registry` at :6625–6699.

    // Pass 1: collect all layout definitions.
    let mut layout_defs: Vec<(&str, &Vec<(String, vuma_parser::ast::Type)>)> = Vec::new();
    for item in &program.items {
        if let Item::LayoutDef(ld) = item {
            layout_defs.push((ld.name.as_str(), &ld.fields));
        }
    }

    // Pass 2: iteratively compute layout sizes. Repeat until no changes
    // (handles forward references and nested layouts).
    let mut layout_sizes: HashMap<String, u64> = HashMap::new();
    let mut changed = true;
    let mut iterations = 0;
    while changed && iterations < 10 {
        changed = false;
        iterations += 1;
        for (name, fields) in &layout_defs {
            let mut size: u64 = 0;
            let mut max_align: u64 = 1;
            for (_fname, ftype) in *fields {
                let falign = bridge_type_align(ftype).max(1);
                let fsize = bridge_type_size_with_layouts(ftype, &layout_sizes);
                if falign > 1 && !size.is_multiple_of(falign) {
                    size = (size + falign - 1) & !(falign - 1);
                }
                max_align = max_align.max(falign);
                size += fsize;
            }
            let alignment = max_align.max(1);
            if size > 0 && !size.is_multiple_of(alignment) {
                size = (size + alignment - 1) & !(alignment - 1);
            }
            let prev = layout_sizes.get(*name).copied();
            if prev != Some(size) {
                layout_sizes.insert((*name).to_string(), size);
                changed = true;
            }
        }
    }

    // Pass 3: compute field offsets using the resolved layout sizes,
    // and emit the IVE-public PmtLayoutSpec shape.
    let mut layouts: HashMap<String, vuma_ive::PmtLayoutSpec> = HashMap::new();
    for (name, fields) in &layout_defs {
        let mut offset: u64 = 0;
        let mut max_align: u64 = 1;
        let mut field_list: Vec<vuma_ive::PmtFieldSpec> = Vec::new();
        for (fname, ftype) in *fields {
            let falign = bridge_type_align(ftype).max(1);
            let fsize = bridge_type_size_with_layouts(ftype, &layout_sizes);
            if falign > 1 && !offset.is_multiple_of(falign) {
                offset = (offset + falign - 1) & !(falign - 1);
            }
            max_align = max_align.max(falign);
            let type_name = match ftype {
                vuma_parser::ast::Type::BDBase(n) => n.clone(),
                other => other.to_string(),
            };
            field_list.push(vuma_ive::PmtFieldSpec {
                name: fname.clone(),
                offset,
                size: fsize,
                type_name,
            });
            offset += fsize;
        }
        let alignment = max_align.max(1);
        if offset > 0 && !offset.is_multiple_of(alignment) {
            offset = (offset + alignment - 1) & !(alignment - 1);
        }
        layouts.insert((*name).to_string(), vuma_ive::PmtLayoutSpec {
            name: (*name).to_string(),
            total_size: offset,
            fields: field_list,
        });
    }
    layouts
}
```

This is mechanically equivalent to `build_layout_registry:6625–6699`
with two differences: (a) it emits `PmtLayoutSpec` /
`PmtFieldSpec` instead of `(u64, Vec<(String, IRType, u64, u64,
String)>)`; (b) it does not call `bridge_type_to_ir_type` (the
`PmtFieldSpec` shape doesn't carry an `IRType` field — see ADR-0003
for the IRType-table side-channel).

**Optional refactor**: extract the two-pass loop into a shared
`compute_layout_sizes(program) -> HashMap<String, u64>` helper and
have both `build_layout_registry` and `build_pmt_layout_specs` call
it. This is the right architectural cleanup (eliminates the
duplication the docstring at `:6707–6714` acknowledges) but is **not
required** for the V-03 fix to land. The implementer may choose
either approach; the shared helper is preferred for long-term
maintenance, the inline copy is preferred for minimum-diff landing.

### Change 2 — `rederive_layout` in IVE migrates to consult layouts table

Extend `src/ive/src/verification.rs:268–291` (`rederive_layout`) to
accept a `&HashMap<String, (u64 /*align*/, u64 /*size*/)>` of known
layout sizes (or equivalently a `&HashMap<String,
&PmtLayoutSpec>` — the IVE-side `VerificationInput` already carries
`PmtLayoutSpec`s, so threading them through is cheap). The
`type_align_size` helper at `:299–327` consults this table instead
of falling through to `_ => (8, 8)` at `:325`:

```rust
pub fn rederive_layout(
    fields: &[PmtFieldSpec],
    layout_table: &HashMap<String, (u64, u64)>,   // ← new parameter
) -> (u64, Vec<(u64, u64)>) {
    let mut offset: u64 = 0;
    let mut max_align: u64 = 1;
    let mut result = Vec::with_capacity(fields.len());
    for field in fields {
        let (align, size) = type_align_size(&field.type_name, layout_table);
        if align > 1 && !offset.is_multiple_of(align) {
            offset = (offset + align - 1) & !(align - 1);
        }
        max_align = max_align.max(align);
        result.push((offset, size));
        offset += size;
    }
    let total = if max_align > 1 && !offset.is_multiple_of(max_align) {
        (offset + max_align - 1) & !(max_align - 1)
    } else {
        offset
    };
    (total, result)
}

fn type_align_size(
    type_name: &str,
    layout_table: &HashMap<String, (u64, u64)>,
) -> (u64, u64) {
    let t = type_name.trim();
    // Array: `[T; N]`
    if t.starts_with('[') && t.ends_with(']') {
        let inner = &t[1..t.len() - 1];
        if let Some(semi) = inner.rfind(';') {
            let elem_str = inner[..semi].trim();
            let count_str = inner[semi + 1..].trim();
            if let Ok(count) = count_str.parse::<u64>() {
                let (elem_align, elem_size) = type_align_size(elem_str, layout_table);
                return (elem_align, elem_size.saturating_mul(count));
            }
        }
        return (8, 8);
    }
    if t.starts_with('*') || t.starts_with("Ptr<") || t.starts_with("RegionPtr<") || t == "Channel"
    {
        return (8, 8);
    }
    match t {
        "i8" | "u8" | "bool" => (1, 1),
        "i16" | "u16" => (2, 2),
        "i32" | "u32" | "f32" => (4, 4),
        "i64" | "u64" | "f64" => (8, 8),
        _ => {
            // V-NEW-2 fix: consult the layout table for user-defined names.
            if let Some(&(align, size)) = layout_table.get(t) {
                (align, size)
            } else {
                (8, 8)   // fallback for genuinely unknown names
            }
        }
    }
}
```

Update the sole caller, `verify_layout_consistency` at `:336–365`,
to pass the `layout_table`. The caller already receives
`&HashMap<String, PmtLayoutSpec>` as its argument (parameter
`layouts`); build the `HashMap<String, (u64, u64)>` projection
inline or extend `PmtLayoutSpec` with a pre-computed
`(align, size)` field.

**Update the docstring** at `:264–267` to remove the "known
small-layout bug; this verifier faithfully reproduces it" note —
the bug is fixed, the parity is now real.

### Change 3 — Delete legacy `bridge_type_size` (V-40)

After Change 1 lands, `build_pmt_layout_specs:6724` no longer calls
the legacy function. A-4's caller inventory
(`docs/research/A-4-pipeline-runtime-tests-deps.md:51–61`) confirms
the legacy function's only remaining caller is its own
self-recursion on `Type::Array` at `:6547`. Delete the entire
function at `src/pipeline.rs:6530–6550` (including the docstring at
`:6530–6531`).

**Also delete the stale doc references** at:
- `src/ive/src/verification.rs:247, 255, 295` (stale line refs to
  `pipeline.rs:8669` / `8870` / `8880–8881` / `8727` — actual lines
  are `:6590` / `:6532` / `:6715` / `:6723` per A-4's V-NEW-7 table
  at `docs/research/A-4-pipeline-runtime-tests-deps.md:565–587`).
- `womb/kernel/ipc/shm.vuma:296–297` (cites `pipeline.rs lines
  8154–8207` for `bridge_type_to_ir_type` — actual line is `:6503`).

These stale references are part of V-41 / V-NEW-7 and are best
cleaned up in the same PR that deletes the function, to avoid
leaving dangling references.

**Scope note**: this ADR does **not** change the IVE's
`verify_layout_consistency` semantics — it still flags mismatches
between pipeline-provided and IVE-derived layouts. The change is
that the IVE-derived side now uses the same `_with_layouts`
algorithm, so the comparison is meaningful.

## Consequences

### Positive
- `build_pmt_layout_specs` produces correct sizes for nested layouts
  (`layout Outer = { t: Transform, x: u32 }` where `Transform` is a
  24-byte layout now correctly records `t`'s size as 24 and `x`'s
  offset as 24, not 8 and 8).
- IVE `verify_layout_consistency` becomes a real check rather than a
  no-op parity test — it now catches pipeline-side layout bugs
  rather than reproducing them.
- Closes V-03, V-NEW-2, V-37 (subsumed — trailing padding was
  already correct), and V-40 in one ADR. Four P0/P2 entries from the
  catalog.
- Unblocks ADR-0003's `layout_sizes` / `layout_fields` tables
  (`build_layout_registry` already produces them; this ADR ensures
  the IVE-public `PmtLayoutSpec` table agrees).
- The `:6707–6714` docstring's "this is the IVE-public counterpart
  of the internal `build_layout_registry`" claim becomes true.

### Negative
- `build_pmt_layout_specs`'s signature is unchanged (still takes
  `&AstProgram`, returns `HashMap<String, PmtLayoutSpec>`), but its
  runtime cost roughly triples (three passes over `LayoutDef`s
  instead of one). For programs with many layouts, the Pass 2
  iteration loop runs up to 10 times (the `iterations < 10` cap at
  `:6644`). This is acceptable — `build_layout_registry` already
  pays this cost on the codegen side, and `LayoutDef` count is
  small in practice (the largest VUMA program has <50 layouts per
  A-4's audit).
- `rederive_layout` gains a new parameter (`layout_table`), breaking
  its callers. A-3's audit (`docs/research/A-3-ive-proofs-capability.md`,
  V-A3-1) found the sole caller is `verify_layout_consistency` at
  `:336–365`; that one call site must be updated. Any external
  caller of `rederive_layout` (none found by the audit — the
  function is `pub` in `vuma_ive::verification` but the only
  consumer is `verify_layout_consistency`) would also need updating.
- The fallback `_ => (8, 8)` in `type_align_size` remains for
  genuinely unknown names. This means a `PmtFieldSpec` whose
  `type_name` is neither a primitive, a pointer-like, an array, nor
  a registered layout name still silently miscompiles. In practice
  this should never happen for well-formed programs (the parser
  guarantees every field type is one of those four categories), but
  the fallback is preserved for robustness.
- Deleting legacy `bridge_type_size` is a breaking change for any
  out-of-tree consumer of `pipeline.rs`. A-4's caller inventory
  (`docs/research/A-4-pipeline-runtime-tests-deps.md:51–61`)
  confirms zero external callers, but the function is technically
  `pub` (per its declaration at `:6532`); the deletion must be
  announced in the changelog.
- Test coverage gap (per `docs/research/A-2-ir-codegen.md:587`):
  zero code-level regression tests exist for V-03 today. The
  `framework.rs:665, 703` callers of `build_pmt_layout_specs` don't
  test its correctness. The regression-test plan below must add
  code-level tests.

### Neutral
- No public API change for `build_pmt_layout_specs` (same signature).
  The `rederive_layout` signature change is internal to `vuma_ive`
  (its only caller is `verify_layout_consistency`).
- No Lean-proof impact. The Lean `PMT/Basic.lean` model does not
  model `PmtLayoutSpec` field offsets; A-3's audit
  (`docs/research/A-3-ive-proofs-capability.md`) confirmed no Lean
  change is needed.
- No backend-specific changes. `build_pmt_layout_specs` feeds the
  IVE, not the codegen backends. The codegen-side
  `build_layout_registry` already uses `_with_layouts` and is
  unchanged.
- Regression-test plan: add to `src/tests/src/regression.rs` (per
  A-2's gap analysis at `docs/research/A-2-ir-codegen.md:619`):
  1. `test_build_pmt_layout_specs_nested_layout` — build an AST with
     `layout Inner = { a: u64 }; layout Outer = { i: Inner, x: u32 }`,
     call `build_pmt_layout_specs(&ast)`, assert `Outer.total_size ==
     16` (8 for `Inner.a`, 4 for `Outer.x`, 4 padding) and
     `Outer.fields[1].offset == 8`.
  2. `test_build_pmt_layout_specs_forward_reference` — same but
     `Outer` defined before `Inner`; assert the same result.
  3. `test_ive_rederive_layout_consistency_with_nested` — call
     `verify_layout_consistency(&layouts)` with the above
     `build_pmt_layout_specs` output; assert the returned
     `mismatches` Vec is empty (would be non-empty before this ADR
     due to V-NEW-2).
  4. `test_legacy_bridge_type_size_deleted` — `cargo check` will
     fail if any caller remains; this is the regression guard for
     V-40.

## Alternatives Considered

### Alternative A: Make `build_pmt_layout_specs` use the IVE-side `rederive_layout` instead of duplicating the algorithm

Have `build_pmt_layout_specs` call `vuma_ive::rederive_layout` for
each layout, eliminating the duplication between the two functions.
Rejected because:

1. The dependency direction is wrong. `pipeline.rs` (the `vuma` root
   crate) depends on `vuma_ive`; `vuma_ive` does **not** depend on
   `vuma` (per A-3's audit, `src/ive/src/verification.rs:255–257`
   explicitly says "IVE cannot call [the pipeline's
   `bridge_type_align`/`bridge_type_size`] directly"). So
   `build_pmt_layout_specs` could in principle call
   `vuma_ive::rederive_layout`, but then `rederive_layout` would
   need to consult a layout table produced by `build_pmt_layout_specs`
   — a circular dependency.

2. `rederive_layout` operates on `&[PmtFieldSpec]` (already-flat
   field list), while `build_pmt_layout_specs` operates on
   `&AstProgram` (raw `Item::LayoutDef`s). The two-pass size
   resolution must happen on the AST side (where forward references
   are resolvable), not on the flattened `PmtFieldSpec` side.

3. Even if the circular dependency were resolved (e.g. by extracting
   `rederive_layout` into a shared `vuma_layout` crate), the
   algorithmic duplication is small (~30 lines) and the cost of the
   new crate outweighs the benefit. The shared-helper refactor in
   Change 1's "Optional refactor" note achieves the same maintenance
   benefit without a new crate.

### Alternative B: Leave IVE `rederive_layout` buggy, document the gap

Migrate `build_pmt_layout_specs` to `_with_layouts` (Change 1) but
leave `rederive_layout` reproducing the `_ => 8` bug. Document the
gap in a follow-up issue. Rejected because:

1. **Soundness**. The whole point of `verify_layout_consistency` is
   to catch pipeline-side layout bugs. If it intentionally
   reproduces the same bug, it provides zero verification value.
   A-3's audit (`docs/research/A-3-ive-proofs-capability.md`,
   V-A3-1) confirmed the check is "structurally blind to V-03".

2. **V-NEW-2 is a P0 blocker**. After Change 1 lands,
   `build_pmt_layout_specs` produces correct sizes for nested
   layouts; `rederive_layout` still produces wrong sizes; the
   consistency check **FAILS** for every program with a nested
   layout. The IVE refuses to discharge. The bridge-fix epic's
   entire purpose — making nested layouts work — is defeated.
   `docs/research/A-4-pipeline-runtime-tests-deps.md:479` is
   explicit: "The catalog misses this hidden coupling."

3. The fix is small (one new parameter, one new lookup in the
   catch-all arm, ~10 lines), and the only caller is
   `verify_layout_consistency` itself. The cost of bundling is far
   smaller than the cost of leaving it broken.

### Alternative C: Defer V-40 (delete legacy `bridge_type_size`) to a separate ADR

Migrate `build_pmt_layout_specs` (Change 1) and `rederive_layout`
(Change 2) in this ADR, but defer the deletion of legacy
`bridge_type_size` (Change 3 / V-40) to a follow-up. Rejected
because:

1. V-40's entire content is "delete the function after V-03 lands".
   `docs/vuma-side-problem-catalog.md:317–328` (V-40) and
   `docs/research/A-4-pipeline-runtime-tests-deps.md:194–196`
   (A-4 verification) both confirm that after `:6724` migrates, the
   legacy function has zero external callers. Deferring the deletion
   leaves a dead function in the codebase, which is exactly the
   "dead-code risk" V-40 warns about.

2. The deletion is mechanical (1-day effort per V-40's catalog
   entry) and the stale-doc cleanup (the `src/ive/src/verification.rs
   :247, 255, 295` stale line refs and `womb/kernel/ipc/shm.vuma
   :296–297`) is best done in the same PR to avoid leaving dangling
   references.

3. Bundling V-40 into this ADR makes the V-03 fix atomic: the
   legacy function is gone in the same commit that makes it dead.
   Splitting creates an intermediate state where the function is
   dead but still present, which is exactly the state V-40 was
   filed to prevent.
