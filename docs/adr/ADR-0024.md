# ADR-0024: Promote ADR-0007 from Proposed to Accepted (IVE l1l3_collapse wiring verified)

- **Status**: Accepted
- **Date**: 2026-08-01
- **Decision Maker**: VUMA compiler team
- **Supersedes**: The "Proposed" status of ADR-0007
- **Superseded by**: (none)

## Context

ADR-0007 was marked Proposed because the per-backend call-ABI wiring
step was medium-confidence: "wire `verify_capability` into every
capability-checked host import." The Wave F re-audit (F-2) corrected
this framing: capability verification happens at **IVE compile time**
(in `l1l3_collapse`), not in emitted binaries. The compile-time-only
design is correct by design.

### Verification performed (2026-08-01)

I read the actual source to confirm both the bug and the fix path:

**Bug 1 — Hardcoded signing key** (`src/codegen/src/capability.rs:117`):
```rust
let mut signing_key: Vec<u8> = b"vuma_dev_signing_key".to_vec();
signing_key.extend_from_slice(&parent_token_id.to_le_bytes());
```
Confirmed: the signing key is the literal string `b"vuma_dev_signing_key"`
concatenated with the parent token ID. Any attacker who reads the VUMA
source can forge capability tokens.

**Bug 2 — IVE capability verifier stub** (`src/ive/src/verification.rs:2379`):
```rust
let is_intrinsic = matches!(c.kind, ComputationKind::Intrinsic(_));
if !is_intrinsic {
    continue;
}
let known = true; // All Intrinsic variants are known capability ops
if !known {
    failures.push(format!("unknown capability operation: {}", c.kind.label()));
    continue;
}
l2_checks_folded += 1;
```
Confirmed: `let known = true` is a stub. The IVE folds L2 capability
checks WITHOUT actually verifying any HMAC-SHA256 signature. The
`l2_checks_folded` counter increments regardless of whether the
signature is valid.

**The fix path** (per ADR-0007 as revised by ADR-0011):
1. Hand-written HMAC-SHA256 in pure Rust at `src/codegen/src/hmac_sha256.rs`
   (~300 LOC, no external deps — SHA-256 is ~150 LOC, HMAC wrapper is
   ~50 LOC). This is consistent with VUMA's hand-write philosophy and
   the 5-crate policy (ADR-0010).
2. Replace the FNV-1a × 4 signature function at `src/codegen/src/ipc.rs:996-1007`
   with the new HMAC-SHA256.
3. Replace the hardcoded `b"vuma_dev_signing_key"` at `capability.rs:117`
   with a per-process random 32-byte secret (read from `/dev/urandom`
   at compiler startup; fail-closed if unavailable).
4. **Replace `let known = true` at `verification.rs:2379`** with a real
   HMAC-SHA256 signature verification call. The IVE `l1l3_collapse`
   should call `hmac_sha256::verify(key, message, signature)` and
   push a failure if the signature is invalid.

### Why the "per-backend ABI wiring" concern is moot

ADR-0007's original "Proposed" status was because the task description
said "wire `verify_capability` into every capability-checked host
import (the import call site checks the signature before invoking the
host function)." F-2 established that this is the WRONG layer —
capability verification happens at IVE compile time, not at runtime
host-import call sites.

The correct wiring is:
- **Compile time (IVE)**: `l1l3_collapse` verifies HMAC-SHA256
  signatures. If invalid, the pipeline hard-fails with
  `VumaError::Verification`.
- **Runtime (emitted binary)**: no `verify_capability` calls. Only the
  `cap_id` (low 64 bits of the token) survives into the binary, as
  `BinOp(Add, cap_id_immediate, 0)`. The runtime trusts the
  compile-time verification.

This means there is NO per-backend ABI work. The fix is entirely in
`src/ive/src/verification.rs` and `src/codegen/src/capability.rs`.
Both are ISA-agnostic. All 19 backends inherit the fix for free.

## Decision

**Promote ADR-0007 from Proposed to Accepted.**

The technical fix (per ADR-0007 as revised by ADR-0011) is:

1. **New file**: `src/codegen/src/hmac_sha256.rs` (~300 LOC)
   - `pub fn sha256(data: &[u8]) -> [u8; 32]` — SHA-256 hash
   - `pub fn hmac_sha256(key: &[u8], message: &[u8]) -> [u8; 32]` — HMAC
   - `pub fn verify(key: &[u8], message: &[u8], expected: &[u8; 32]) -> bool` — constant-time compare
   - No external dependencies. Pure Rust. Consistent with VUMA's
     hand-write philosophy.

2. **Modify**: `src/codegen/src/ipc.rs:996-1007`
   - Replace the FNV-1a × 4 signature function with `hmac_sha256::hmac_sha256`.
   - The signature is now 32 bytes (was 32 bytes for FNV-1a × 4 — same
     size, but cryptographically secure).

3. **Modify**: `src/codegen/src/capability.rs:117`
   - Replace `b"vuma_dev_signing_key"` with a per-process random 32-byte
     secret read from `/dev/urandom` (or `getrandom` syscall on Linux,
     `BCryptGenRandom` on Windows, `SecRandomCopyBytes` on macOS).
   - The secret is generated once at compiler startup and held in
     `CompileConfig::capability_signing_key: [u8; 32]`.
   - Fail-closed: if the OS random source is unavailable, the compiler
     aborts with a clear error message.

4. **Modify**: `src/ive/src/verification.rs:2379`
   - Replace `let known = true;` with:
     ```rust
     let signature_valid = hmac_sha256::verify(
         &compile_config.capability_signing_key,
         &capability_token_message,
         &capability_token_signature,
     );
     if !signature_valid {
         failures.push(format!(
             "invalid capability signature for token {}",
             c.kind.label()
         ));
         continue;
     }
     ```
   - This requires threading `compile_config.capability_signing_key`
     into `l1l3_collapse`. The function signature changes from
     `l1l3_collapse(scg: &SCG)` to
     `l1l3_collapse(scg: &SCG, signing_key: &[u8; 32])`.

5. **New tests**: `tests/capability_signature_tests.rs`
   - Test that a valid signature passes `l1l3_collapse`.
   - Test that an invalid signature fails `l1l3_collapse` with a
     `VerificationStatus::Violated` result.
   - Test that the signing key is random (not deterministic across
     compiler invocations).

6. **Update Lean model**: `proof/PMT/IVE/Soundness/Capability.lean` (if
   it exists — verify during implementation). The Lean model should
   reflect that capability verification is HMAC-SHA256, not FNV-1a × 4.

## Consequences

### Positive
- **Closes the P0 security gap.** V-A3-2 (hardcoded key) and V-A3-6
  (`let known = true` stub) are both fixed.
- **No per-backend work.** The fix is ISA-agnostic. All 19 backends
  inherit it.
- **Consistent with VUMA's hand-write philosophy.** No `sha2` or `hmac`
  crates. The 5-crate policy is preserved.
- **Compile-time verification.** The runtime pays no cost for
  capability verification — it's all done at IVE compile time.

### Negative
- **SHA-256 is ~150 LOC of non-trivial code.** A bug in the hand-written
  SHA-256 would be a security vulnerability. Mitigated by: using the
  NIST FIPS 180-4 test vectors as regression tests, and by the fact
  that `womb/crypto/mac_kdf/hmac.vuma` already has a working
  HMAC-SHA-256 (F-2 confirmed) that can serve as a reference
  implementation.
- **The signing key is per-process.** This means capability tokens
  minted by one compiler invocation won't validate in another. This is
  correct for the threat model (tokens are compile-time artifacts, not
  shared across invocations) but may surprise users who expect
  deterministic compilation. Document this in the language reference.
- **`l1l3_collapse` signature changes.** This is a breaking change for
  any code that calls `l1l3_collapse` directly (tests, the IVE
  pipeline). Mechanical update.

### Neutral
- ADR-0007's "Proposed" status is removed. This ADR-0024 documents the
  promotion and the verification that made it possible.

## Alternatives Considered

### Alternative A: Keep ADR-0007 as Proposed; do more verification first
Rejected — the verification is complete. The `l1l3_collapse` stub is
confirmed at `verification.rs:2379`, the hardcoded key is confirmed at
`capability.rs:117`, and the fix path (hand-written HMAC-SHA256 + IVE
verifier wiring) is clear. No more verification needed.

### Alternative B: Use the `sha2` + `hmac` crates from crates.io
Rejected — violates the 5-crate policy (ADR-0010) and VUMA's
hand-write philosophy. SHA-256 is small enough to hand-write (~150 LOC).

### Alternative C: Use `womb/crypto/mac_kdf/hmac.vuma` (the WOMB-side HMAC)
Rejected for the VUMA-side fix — `womb/` is VUMA source, not Rust.
The VUMA compiler (Rust) can't import a `.vuma` file. However, the
WOMB HMAC serves as the **reference implementation** — the Rust
hand-translation in `src/codegen/src/hmac_sha256.rs` should be
parity-tested against `womb/crypto/mac_kdf/hmac.vuma` (which is what
`tests/pmt_parity_test.rs` already does for PMT checkers).
