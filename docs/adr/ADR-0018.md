# ADR-0018: GPU path for VEEE goes through MLIR→SPIR-V, not through VUMA's codegen

- **Status**: Proposed
- **Date**: 2026-08-01
- **Decision Maker**: VUMA project lead
- **Supersedes**: The implicit "VUMA will grow GPU backends" assumption
  in the SWE package's `01-vuma-side-changes.md` (V-26 SPIR-V embedding,
  V-27 Metal, V-28 GPU buffer)
- **Superseded by**: (none)

## Context

The Wave A audit (`22-review-against-vuma.md`) verified that VUMA has
**zero GPU support**: no `BackendKind::Vulkan/Metal/WebGPU`, no
`IRInstr::GpuDraw`, no `Effect::Gpu`, no `Resource::Gpu*`. VUMA's 19
backends are all CPU ISAs.

The SWE package proposed three VUMA-side patches for GPU:
- **V-26**: SPIR-V embedding via const byte arrays
- **V-27**: Native Metal backend
- **V-28**: Persistent GPU buffer abstraction

Per ADR-0013 (three-layer architecture), these belong to Layer 3
(VEEE), not Layer 1 (VUMA). The question is: how does VEEE get GPU
shaders compiled?

## Decision

**The GPU path for VEEE goes through MLIR→SPIR-V, not through VUMA's
codegen.**

```
VEEE GPU kernel (.veee)
    │
    ▼ VEEE compiler (Rust)
MLIR dialect (gpu + spirv)
    │
    ▼ MLIR compiler (C++ tool, build-time only)
SPIR-V bytecode
    │
    ▼ Embedded in VEEE program as a const byte array
VUMA AST (const bytes literal)
    │
    ▼ VUMA pipeline (parse → SCG → IVE → IR → codegen)
VUMA binary with embedded SPIR-V blob
    │
    ▼ Runtime: WOMB renderer calls Vulkan/Metal/WebGPU with the SPIR-V
Native GPU execution
```

### Why MLIR→SPIR-V, not a VUMA GPU backend

- **VUMA's codegen is CPU-only by design.** The 19 backends target CPU
  ISAs with register-based emission. GPU shaders use a fundamentally
  different execution model (SIMD lanes, workgroups, shared memory).
  Adding GPU support to VUMA's codegen would require a new `BackendKind`
  variant, new IR instructions (`GpuDraw`, `GpuDispatch`), new Effect
  variants, new Resource variants, and new Lean proofs for the GPU
  memory model. This is 3-6 months of greenfield work (per Wave A
  audit).
- **MLIR already has a mature SPIR-V backend.** MLIR's `gpu` dialect
  and `spirv` dialect handle the lowering from high-level GPU
  abstractions to SPIR-V bytecode. Reusing MLIR saves 4+ months of
  work vs. writing a custom SPIR-V backend in VUMA.
- **SPIR-V is the universal GPU IR.** Vulkan, Metal (via MoltenVK),
  and WebGPU all consume SPIR-V. A single SPIR-V backend covers all
  three GPU APIs.
- **VUMA stays minimal.** No GPU code in VUMA's codegen. The 5-crate
  policy is preserved (MLIR is a build-time tool, not a runtime
  dependency).

### How the GPU kernel flows

1. **VEEE source** declares a GPU kernel:
   ```veee
   gpu kernel tessellate_path(
       path: Buffer<PathSegment>,
       vertices: Buffer<Vertex>,
   ) {
       let segment = path[global_id.x];
       let (v0, v1) = tessellate(segment);
       vertices[global_id.x * 2] = v0;
       vertices[global_id.x * 2 + 1] = v1;
   }
   ```

2. **VEEE compiler** lowers the kernel to MLIR:
   - The kernel body becomes an MLIR `gpu.func` operation.
   - Buffer accesses become MLIR `gpu.buffer_load` / `gpu.buffer_store`.
   - `global_id` becomes MLIR `gpu.thread_id`.

3. **MLIR compiler** (invoked as a build-time tool) lowers the MLIR to
   SPIR-V bytecode:
   - `gpu.func` → `spirv.func`
   - `gpu.buffer_load` → `spirv.Load`
   - `gpu.thread_id` → `spirv.BuiltinGlobalVariable`
   - The MLIR `spirv` dialect has a `ConvertToSPIRV` pass that handles
     this.

4. **VEEE compiler** embeds the SPIR-V bytecode in the VEEE program
   as a const byte array:
   ```veee
   const TESSELLATE_PATH_SPIRV: [u8; 4096] = #[embed("tessellate_path.spv")]
   ```

5. **VEEE compiler** lowers the const byte array to a VUMA AST `Lit::Bytes`
   (requires V-26: parser support for const byte arrays — still a
   VUMA-side patch, but a small one).

6. **VUMA pipeline** compiles the VUMA AST to a native binary. The
   SPIR-V blob lives in `.rodata` as a byte array.

7. **WOMB renderer** (`womb/ui/render/vector.vuma`) calls the GPU API
   (Vulkan/Metal/WebGPU) with the SPIR-V blob:
   ```vuma
   transform render_path(path: Buffer<PathSegment>) {
       let vertices = allocate(1024 * sizeof(Vertex));
       gpu_dispatch(TESSELLATE_PATH_SPIRV, path, vertices);
       // gpu_dispatch is a WOMB host import (Vulkan/Metal/WebGPU)
   }
   ```

### What VUMA provides (small patch)

- **V-26: Const byte arrays** — parser support for `Lit::Bytes(Vec<u8>)`
  and `Expr::ArrayLit`. This is the only VUMA-side patch needed for
  the GPU path. ~2 weeks (per the catalog).
- The `.rodata` lowering (already exists for string literals; extend
  to byte arrays).

### What VEEE provides

- The `gpu kernel` syntax.
- The VEEE → MLIR lowering (~3,000 lines of Rust).
- The MLIR invocation (subprocess call to `mlir-translate`).
- The SPIR-V embedding (`#[embed("file.spv")]` attribute).

### What WOMB provides

- `womb/ui/render/gpu_dispatch.vuma` — the `gpu_dispatch` host import
  (calls Vulkan/Metal/WebGPU via `extern "C"`).
- `womb/ui/render/vector.vuma` — the path-tessellation renderer that
  uses `gpu_dispatch`.

### What MLIR provides (build-time tool)

- The `gpu` and `spirv` dialects.
- The `ConvertToSPIRV` pass.
- The `mlir-translate` tool (invoked as a subprocess by the VEEE
  compiler).

## Consequences

### Positive
- **No GPU code in VUMA** — the 19-backend codegen stays CPU-only.
  VUMA's verification discipline (PMT, Z3, Lean) is unchanged.
- **Reuses MLIR's mature SPIR-V backend** — saves 4+ months of work
  vs. a custom VUMA SPIR-V backend.
- **SPIR-V covers all three GPU APIs** (Vulkan, Metal via MoltenVK,
  WebGPU). One backend, three targets.
- **The only VUMA-side patch is V-26** (const byte arrays) — a small,
  well-scoped change that's useful for non-GPU purposes too (font
  subsetting, embedded assets).

### Negative
- **Adds MLIR as a build-time tool** — MLIR is a C++ tool that must be
  installed on the build host. This is similar to Z3 (a build-time
  dependency) but adds setup complexity.
- **GPU kernels are not PMT-verified.** PMT is a CPU memory model.
  GPU kernels use a different memory model (workgroup-shared memory,
  global memory, image memory). Verifying GPU kernels would require a
  new Lean model, which is out of scope for v1.
- **MLIR is a C++ dependency.** While it's build-time only (not linked
  into the VUMA binary), it violates the "Rust-only" spirit of the
  5-crate policy. Mitigated by: MLIR is a tool (like Z3), not a crate.
  The 5-crate policy applies to Rust crates, not build tools.
- **SPIR-V validation is runtime.** SPIR-V has its own validator
  (`spirv-val`), but VEEE can't verify shader correctness at compile
  time. A malformed shader will fail at GPU dispatch time.

### Neutral
- This ADR is Proposed, not Accepted, because the MLIR→SPIR-V pipeline
  hasn't been prototyped. Promotion to Accepted requires:
  1. A working MLIR→SPIR-V pipeline for a simple compute shader.
  2. Confirmation that `#[embed("file.spv")]` works with V-26's
     const byte arrays.
  3. A WOMB `gpu_dispatch` host import that successfully runs a SPIR-V
     shader on at least one GPU API (Vulkan recommended first).

## Alternatives Considered

### Alternative A: Write a custom VUMA SPIR-V backend
Rejected — 3-6 months of greenfield work (per Wave A audit). MLIR
already does this.

### Alternative B: Use LLVM's SPIR-V backend
Rejected — LLVM is C++, has no e-graphs, and its SPIR-V backend is
less mature than MLIR's `spirv` dialect. Also violates the "no LLVM"
decision (ADR-0015).

### Alternative C: Write GPU shaders in GLSL/WGSL, compile at runtime
Rejected — runtime shader compilation is slow (50-200ms per shader)
and loses the compile-time validation. Embedding pre-compiled SPIR-V
is faster and more reliable.

### Alternative D: Use Vulkan's GLSL compiler (shaderc) at build time
Rejected — GLSL is a less expressive language than VEEE's kernel DSL.
VEEE's kernel DSL can leverage VEEE's type system (monotonicity types,
incremental computation) for shader optimization.
